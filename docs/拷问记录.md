## Q2 · 「比 Hindsight 强」的胜负判据怎么定？ ✅ 已由我裁定（2026-11-02）

**主人授权**：「关于 q2，你再决定稳不稳。」

**裁定**（`docs/对标-Hindsight.md` §2）：
> **主判据 = 收益**：`repeatFailureRate` 相对无记忆的下降幅度，且在同一批留出会话上**不劣于** Hindsight 的同一指标。

## 主人的"定式论"（2026-11-02 · 本项目最重要的设计输入之一）

> 「为什么围棋有定式存在呢？**过拟合真的是完全负面效果吗？** 定式就是公认的棋局最佳下法，即默认对方会走我也会走的一个约定俗成，因为对双方都是正常棋力的时候这才是合理，但是如果有一方不会定式就会吃大亏。那么我们的库是不是应该整理出定式？**每一招都指引向源头棋谱**，这样就能把相关的连起来了。而且当一个厂商出现不会定式的情况，就能瞬间击破。如果一个厂商的水平高出定式的范围，那就可能需要更新定式了。」

**落地方案（v0.5，`方案.md` §4.8 / §5.1b / §6.1b）**：

| 主人的话 | 落地 |
|---|---|
| 定式是公认最佳下法 | `joseki` 数据结构：steps + preconditions + assumptions + support/counter，state = candidate/standard |
| 每一招指引向源头棋谱 | 每个 step 带 `source:{episode,nodeId,edgeId,seq,quote}` |
| 把相关的连起来 | `shares-joseki` 边（比主题词更硬的连接）+ 每招回指 ⇒ 定式↔棋谱↔节点菱形 |
| 厂商不会定式就能击破 | **定式体检**：对手会话逐招比对 ⇒ 只产出"偏离事实 + 指针"，不产出"该打哪"（行动归 AGENTS/persona） |
| 水平高出定式范围就要更新 | 更新规则：同条件下更好结果的新线 ⇒ 候选 → 多源印证 → `version+1` + `supersedes`，旧版留档 |
| 过拟合是否纯负面 | **不是**：定式 = **受控泛化**（多源+适用条件+可更新+可溯源）；失控的泛化才是过拟合（§6.1b） |

## Q5 · 定式的准入与更新判据 ✅ 已裁定（2026-11-02）

**日期**：2026-11-02
**影响面**：M2 提炼算法、M4 更新机制、定式库可信度；也决定"击破"时的判断依据是否可靠。

**背景**：定式一旦被当成"公认下法"，它就会影响注入与体检。定太松 = 把个案当定式（F1/F7）；定太严 = 永远只有 candidates，形不成"公认"。现在需要定三件事：**多少局算公认**、**什么算反例**、**什么时候该出新版本**。

**候选答案**：

- **甲（推荐）**：**证据门槛 + 反例分级 + 机械更新**——
  - 候选：≥2 局独立支撑，无反例，每步有 source，preconditions 可核；
  - 公认（standard）：≥3 局，或 ≥2 局 + 一次跨线索复用未被否定；
  - 反例分级：一次失败 = 记 counter（不降级）；同一 preconditions 下复现 ≥2 次 = 强反例 → disputed → 停用；
  - 更新：同条件下"步数更少/失败更少/约束更满足"的新线 ≥2 局印证 ⇒ `version+1` + `supersedes`，旧版留档。
- **乙**：**只看成功终局**——只从"整局成功"的棋谱里提炼定式，失败局只作反例。更保守，但会漏掉"局部成功"。
- **丙**：**人工钦定优先**——人可以标"这是定式/不是定式"，机器只维护证据。最贴你想要的控制力，但违背"机械可判优先"。
- **丁**：**先只做候选，不设 standard**——M2 只产出 candidates，等 M5 有实测再定"公认"阈值。

**我的推荐是甲，但把"人工钦定"作为甲的旁路**（人是最终裁定者，钦定要记账、可被证据推翻）。理由：① 与项目"机械可判优先"一致；② 反对例分级，能区分"偶然一次失败"和"条件真的变了"；③ 更新规则用"结果更好"这种可机械比较的量，不靠模型说"这个更好"。

**问题（只此一个）**：选 **甲 / 乙 / 丙 / 丁** 里的哪一个？（甲可以附加"人工钦定旁路"，说不要也行。）

**主人裁定（原话）**：
> 「甲，但是人工可能还不如多成员独立解析？这种困难的，多跑几个成员不是比问人更好？只在人指出错误的时候反思才对？」

**裁定**：

| # | 裁定 | 落点 |
|---|---|---|
| R5.1 | **准入与更新按"甲"**：候选 2 局 / 公认 3 局；反例分级（一次失败记 counter、同条件复现 ≥2 次 = 强反例 → disputed → 停用）；同条件更优新线 ≥2 局印证 ⇒ `version+1` + `supersedes` | §5.1b |
| R5.2 | **取消"人工钦定"旁路**——难判的不问人，交给**多成员独立解析 + 机械共识**（N 个独立成员各判一次；结构化票；一致度不足 → 保持 disputed） | §5.4 |
| R5.3 | **人只纠错**：人指出错误 = 最高优先级证据，触发一次纠错反思（记 counter、修正/失效、校准共识）；**不设常规审批** | §5.4 / §8.2 |
| R5.4 | 反思的唯一合法来源 = **被纠错触发**；不做后台自省 | §5.4 |

**为什么**：① 多个独立视角通常比单个人更稳（且可复算）；② 审批会变成瓶颈且不可复算；③ 人的纠错是唯一的外部真相信号，必须当一等证据，但不该被日常化。

**版本**：v0.5 → v0.6。

## Q6 · 知识来源边界：记忆只吃会话历史，还是也吃外部文档/代码库？ ✅ 已裁定（2026-11-02）

**日期**：2026-11-02
**影响面**：M1/M2 的语料与抽取器输入；"长期知识库"到底是不是文档库；边界成文法（与 RAG/tools 的分界）；评测语料怎么造。

**背景**：主人要"长期知识库"。但"知识库"有两种完全不同的东西：

| 候选 | 吃什么 | 好处 | 风险/边界问题 |
|---|---|---|---|
| **A 只吃会话历史**（棋谱+日志） | 本机过往会话 | 边界最干净：全部有 provenance、可回溯、可失效；这就是"记忆" | 只是"我们做过什么"，不是"世界已知什么" |
| **B 会话 + 用户显式投喂的文档** | A + 用户主动 ingest 的文档（像 Hindsight 的 `ingest_document`） | 用户能指定"这个要记住" | 文档不是"会话历史"，属外部知识；需要单独标 source，且不能与 claim 混 |
| **C 会话 + 仓库内文档自动入库** | A + AGENTS/README/docs | 项目知识自动进来 | 自动扫描 = 上下文工程/RAG 的活；且文档会变，记忆会 stale |
| **D 会话 + 外部资料（网页/论文）** | 全部 | 最像"知识库" | 越界成 RAG；不可控来源、不可复现；与"记忆=历史"的定义冲突 |

**我的推荐**：**A 为主 + B 作为"用户显式投喂"的窄口**——理由：
1. 记忆的定义是"**发生过什么**"（有 seq 可回溯）；外部文档是"**别人写了什么**"，该由宿主的 read/grep 去读，不该复制进记忆（复制会 stale、会与原文冲突，且无法证伪）；
2. 但"用户明确说'把这个记下来'"是一个**事件**，可以入档（source=user-provided，独立标注），这不违反定义；
3. C/D 会把记忆变成 RAG，与本项目"不去重、不做向量库"的边界冲突；而且文档更新后记忆不会自动失效，必然产生 F3。

**主人裁定（原话）**：
> 「外部文档需要被 agent 过一遍才能算会话历史才能进入，按你推荐 AB。然后棋谱日志啥的都要带时间戳吧？不然的话模型没有时间概念，会把老旧的当成新的，也分不清覆盖关系。网络获取的知识页需要 agent 自己嚼碎一遍然后被压缩成 kifu 才能进入馆。」

**裁定（三条）**：

| # | 裁定 | 落点 |
|---|---|---|
| R6.1 | **A+B，且唯一入口 = 棋谱**：外部文档、网页、仓库文档都必须由 agent 在会话里读过/嚼碎，落进棋谱后才可能入馆；**不提供 `ingest_document` 旁路**，不自己抓网页、不自动扫仓库 | `方案.md` §3.4 |
| R6.2 | **时间戳是一等字段**：每条记忆带 `occurredAt`（事件发生时间，来自会话事件 `time` / 棋谱 `ts`）与 `recordedAt`（入馆时间）；**新旧按 `occurredAt` 判，不按入档顺序**；覆盖显式 `supersedes`；渲染显示绝对日期 | `方案.md` §4.9；闸 0；F10 |
| R6.3 | **没读过 = 没发生**：不被 agent 读过的内容永远进不来；这是有意的取舍 | §3.4 代价 |

**为什么**：① 只有经过会话，"发生过"才有 seq 可回溯；② 直读外部文档会 stale 且不可证伪，等于把 RAG 混进记忆；③ 时间戳缺失会让旧事实冒充新事实，覆盖关系无从谈起。

**版本**：v0.6 → v0.7。

## Q7 · 注入通道：每步、前 N 步，还是指针+按需？ ✅ 已裁定（2026-11-02，自裁）

**日期**：2026-11-02
**影响面**：M3 的形态、常驻 token 成本、与压缩热清单的叠加、以及"只在相关时跳转"能不能落地。

**背景**：记忆卡要和压缩热清单（约 500 tokens/步）并存。全量每步注入 = 成本翻倍；完全不注入 = 模型可能永远不去 read 记忆树（它没有"我缺什么"的信号，这是压缩仓 03 §5.1 的老结论）。

**候选**：

- **A 每步注入**：最及时；两份常驻，成本 ×2；且容易变成"注意力挤占"。
- **B 前 N 步注入**：冷启动给足，之后靠指针；中途转任务时可能错过。
- **C 指针 + 按需**：平时零注入，命中主题才跳（最符合"只在相关时跳转"）；但**冷启动没有钩子**——模型可能压根不知道有馆。
- **D 混合（我推荐）**：**首轮一行"馆存在 + INDEX 路径"的指针**（事实陈述，不是指令）+ **命中主题才展开**（≤5 条、带日期与证据）。成本：一行常驻 + 按需；既解决冷启动，又保持沉默。

**主人裁定（原话）**：
> 「按你推荐吧，以后这种明显有一个选项优于其他选项的，你应该自己决定吧？只有在目标方向上的问题你再来问我。」

**裁定**：**D**——首轮一行 INDEX 指针（事实陈述）+ 命中主题才展开（≤5 条、带日期与证据、失败教训优先）；未命中零注入。理由：A 成本翻倍、B 中途换任务会漏、C 冷启动无钩子；D 用一行换冷启动、用命中才展开保持沉默。

**版本**：v0.7 → v0.8。

## Q13 · 发布形态与服务对象：单机单用户 / 可分发 / 多用户？ ✅ 已裁定（2026-11-02）

**日期**：2026-11-02
**背景**：这决定用户层是"单例"还是"多租户"、隐私规则、打包方式、评测口径与发版纪律。

| 候选 | 含义 | 好处 | 代价 |
|---|---|---|---|
| **A 单机单用户、本地优先** | 只为这台机器上的你服务；不做多租户/同步 | 隐私最干净；用户层是单例，简单；与"无棋谱不入馆"一致 | 不能分享给别人；换机要手动搬 |

| **C 多用户/团队共享** | 一个馆服务多人 | 协作 | 隔离/权限/隐私复杂度大；与当前"本地 sidecar"冲突 |
| **D 先 A，M6 再评估 B（推荐）** | 先跑通自用，再决定是否发布 | 最稳；保留发布选项 | 发布晚 |

> 「当然是 A，后续只需要手动把记忆库搬到新机器就行了。记忆才是组成一个生命（哪怕是虚拟）的根本，搬走记忆库 + 系统提示词就是搬走智能体。」

**裁定**：

| # | 裁定 | 落点 |
