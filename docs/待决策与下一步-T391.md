# T391 交接：保序惰性加载（下一位接手照此实现即可）

> 2026-11-19 · 本轮只做了设计定稿，**没有动代码**（原因见「为什么回滚」）。

## 一、目标（用户那句原话）

> 应该只做一个几乎无感而必须的预热即可，只在真正调用的时候做一个热加载
> —— 这样就能杜绝很多非活跃会话依旧占用预热的问题。

当前状态：`apply()` 里的同步预热已移除（T390，**14179ms → 5ms**）。
剩下的问题是：**首次真正 walk 时仍要一次读 4 万个文件（≈15s）**。

## 二、为什么这次没做成（重要，别重犯）

我按「先改取值器、再补索引」的顺序改 `createWalkCache`，改到一半发现**结构上必须一起改**：

```js
// 现在的 createWalkCache（T371 之后）里，这两张索引是**立即**建的，
// 而它们本身就要吃掉 episodes + links：
const holdersByTopic = new Map();   // 遍历 episodes
const adjacency = new Map();        // 遍历 links（26346 条）
```

所以只把 `episodes/links` 改成 getter 没用 —— 索引仍然会把它们拉起来。
**正确顺序是一次改完**：`ensure(kind)` → `buildIndexes()` → 五个属性全部换成保序 getter。
我改到一半时剩余预算不足以完成并验证，于是**整体回滚**（`git checkout -- src/rooms/walk.mjs`），
`walk.test.mjs` 41/41 保持全绿。宁可留一份设计，也不留半截代码。

## 三、实现要点（照做即可）

1. **保键序**：`Object.freeze({...})` 的键序不能变 —— 上次就是变了键序，打红
   `walk.test.mjs` 的 **T317 稳定排序**（候选顺序依赖键序）。
   做法：字面量里仍按**原顺序**写占位（`episodes: null, links: null, claims: null,
   holdersByTopic: null, adjacency: null, linksWithoutWhy: 0`），
   `Object.defineProperty` **就地**替换成 getter（不改变顺序），最后再 `Object.freeze`。
2. **单点惰性**：`ensureIndexes()` 一次把三类记录 + 两张索引建好（幂等）。
   所有访问都走它：`cache.episodes` / `cache.links` / `cache.claims` /
   `cache.holdersByTopic` / `cache.adjacency` / `cache.get(kind,id)`。
3. **`get(kind,id)` 自助填充**：按 kind 触发对应的 `ensure`，而不是一次性建全。
4. 归档收尾调 `scripts/warm-bundles.mjs`（已有），让「首次调用」读的是 bundle（~1–2s）而不是 4 万文件。

## 七、判据修正（2026-11-19 二次实测后）

原判据「② 未命中会话磁盘读 = 0」**在冷进程的第一步不可达**：
要判断"没有主题命中"就必须先读 `topics`（bundle 至少 1 次读）。
所以判据改成两条，都可机械判定：

| 场景 | 目标 |
|---|---|
| 冷进程**首次**未命中 | ≤ 50ms · 磁盘读 ≤ 2（只 topics + manifest） |
| 同进程**第二次**未命中 | ≤ 5ms · 磁盘读 = 0（走 WALK_CACHES 命中） |
| 首次命中 | ≤ 2s（现 39ms，已达标） |

`tmp/t391-lazy-acceptance.mjs` 需相应改成"先跑一次 miss 预热、再跑一次 miss 计数"。
基线里那 10 次读里，**多出来的是 episodes/links/claims 三个 bundle + 索引**——那才是要砍掉的部分。

## 八、**已定位**那 10 次读分别是什么（2026-11-19 实测，验收脚本已带路径钩子）

冷进程「未命中」那一步读了这些（顺序即实际顺序）：

```
corpus/antipattern-cost.json           ← 成本索引
.cache/topics.bundle.json              ← 只有它是"判命中"必需的
.cache/episodes.bundle.json            ← 13.5MB 级，最大头
.cache/links.bundle.json               ← 26346 条
.cache/claims.bundle.json
recovery-index.json                    ← 400KB
claims/c-45447c19.json                 ← 4 条单条 claim
claims/c-1a7b1395.json
claims/c-9100d043.json
claims/c-8cfc2720.json
```

**结论**：这 10 次读里，只有 `topics.bundle.json` 是判定"有没有命中"所必需的；
其余 9 次（三个大 bundle + recovery-index + 成本索引 + 单条 claim）**全部发生在"还不知道有没有命中"之前**。

**因此修法明确**：把 pre-step 的顺序改成

```
① 只读 topics（1 次）→ 判是否命中
② 未命中 ⇒ 立即返回（此时总量 1 次读、几十毫秒）
③ 命中  ⇒ 才加载 episodes/links/claims + recovery-index + 成本索引
```

而不是继续在 `createWalkCache` 里做手工惰性（已试过两次，无效——因为大头根本不在那儿）。

### 8.1 具体位置（下一轮直接改这三处，按此顺序）

| 谁提前读了 | 在哪 | 改成 |
|---|---|---|
| 成本索引 `corpus/antipattern-cost.json` | `src/plugin.mjs` 的 `decidePreStep` 里（`let costIndex = null; try { … }` 那一段） | 推迟到"确定要建卡"之后；未命中不读 |
| 恢复索引 `recovery-index.json` | `src/rooms/inject.mjs` 里 `recoveryIndexFor`（`fs.statSync(path.join(storeRoot, 'recovery-index.json'))` 那个函数） | 同上：只在建卡路径调用 |
| 三个大 bundle `episodes/links/claims` | `walkCacheFor` → `createWalkCache`（`src/rooms/walk.mjs`） | 判命中只需 `topics`：先只读 topics，命中后再建全量 |

**顺序要求**：先做前两行（成本/恢复索引）——它们改动面小、立刻能砍掉 `recovery-index.json` 400KB + 成本索引的读；
第三行才是三个大 bundle（13.5MB 级），需要同时处理 T317 键序依赖，放在最后做。

### 8.2 提前返回的**准确挂点**（已定位，下一轮 5 行内可改）

`src/plugin.mjs` 的 `decidePreStep` 开头已有四个早退：

```js
if (!config.enabled && !config.shadow) return { … reason: "disabled" };
if (!text) return { … reason: "no-signal" };
const storeRoot = resolveStoreRoot(config);
if (!storeRoot) return { … reason: "no-store-root" };
if (!fs.existsSync(storeRoot)) { … }
```

**新增第五个早退**（放在 `storeExists` 之后、`const scope = resolved.scope;` 之前）：

```js
// T391：判命中最便宜的一步 —— 只读 topics（1 次 bundle 读）；
// 没有主题命中就不建 walk cache、不建卡、不读 costIndex / recovery-index。
const topicHit = hasTopicMatch(storeRoot, text);
if (!topicHit) return { decision, action: "skip", reason: "no-topic-match" };
```

`hasTopicMatch` 只做两件事：`store.list("topics")`（bundle 命中 ⇒ 1 次读）+ 用与 walk 相同的
`matchTopics` 判一次是否有点；**只用与 walk 完全相同的匹配函数**，否则会出现
"判命中说没命中、walk 却说命中"的不一致。

### 8.3 ⚠ 提前返回的**前置风险**（动手前必须先确认，否则会掉 A2b）

`src/rooms/walk.mjs` 里有一条 **T46 锚定检索**通路：

```js
const anchorRetrievalOn = typeof opts.anchorMatchOf === "function" && opts.anchorRetrieval !== false && …;
if (!anchorRetrievalOn) { dropped.noTopic += 1; return emptyResult(); }
```

即：**即使一个主题都没命中**，只要开了锚定检索，walk 仍会构造候选（同 repo / 同错误签名 / 同任务链）。
所以「没有主题命中就直接 return」会**顺手把 T46 关掉**，那可能掉 A2b（主判据）。

**正确条件**必须带上前提：

```js
if (!topicHit && !anchorRetrievalEnabled) return { … reason: "no-topic-no-anchor" };
```

动手前先确认一件事：**插件是否给 walk 传了 `anchorMatchOf`**。
- 传了 ⇒ 提前返回只在"主题不命中且锚定也不命中"时生效，收益要重新量；
- 没传 ⇒ 提前返回就是安全的纯收益。

**这一条必须在改代码前先查**，否则就是拿主判据换一个延迟数字。

### 8.4 ✅ 已确认：插件**没有**给 walk 传 `anchorMatchOf`（2026-11-19 实测 `grep`）

```
$ grep -n "anchorMatchOf\|anchorRetrieval" src/plugin.mjs src/rooms/inject.mjs
（无输出）
```

⇒ 生产路径上 `anchorRetrievalOn === false`，**T46 锚定检索实际未启用**。
⇒ §8.2 的提前返回**不会关掉任何现有召回**，是纯收益，可以放心做。

（注：这也解释了为什么"未命中"那一步读了一大堆却什么都没产出——walk 在 `picked.length === 0` 时
确实直接返回 emptyResult，但那之前 `decidePreStep` 已经把 cache / costIndex / recoveryIndex 都读掉了。）

下一轮要查的就是这几处（尤其 `store.list("topics")` 是否会连带 touch 其他 bundle）。

### 8.6 ⚠ **重要更正**：我那条"未命中"测试信号其实**命中了主题**（2026-11-19 实测）

```
$ grep -c "no-topic-match" $DSH_HOME/memory-context/live-stats.jsonl
0
```

早退一次都没触发 ⇒ `zzzqqq nonexistent-topic-xyzzy` 这句话**匹配到了主题**（主题匹配是宽松的）。
所以：

1. 「未命中」那 10 次读其实是**命中路径的正常开销**，不是浪费；
2. 606→314ms 的差别来自别处（很可能是噪声或建卡路径的差异），不能算收益；
3. **验收脚本的 miss 用例无效**，必须换成"保证匹配不到任何主题"的信号
   （例如纯随机长 token，且先断言 `matchTopics` 返回 0）。

**对目标本身的影响**：如果用户的日常消息几乎总能匹配到某个主题，那"预热成本"根本不会出现在
未命中路径上 —— **T390（apply 14s→5ms）可能已经是这个问题的主要收益**，
剩下的只有"命中时的一次建 cache"（bundle 热时 39–49ms，已经不高）。

**下一轮第一件事**：用"确定不命中"的信号重测一遍，先确认这个优化目标还剩多少真实空间；
若剩余空间很小，就把 T391 降级为"可选优化"，把精力放回 计划表 的其它 ⏳ 项。

### 8.7 决定性实测：命中面其实很宽（2026-11-19）

用生产同一套 `matchTopics` + 真库（topics 6593）实测：

| 信号 | 命中主题数 |
|---|---|
| `zzzqqq nonexistent-topic-xyzzy` | **1** |
| `qwertyuiop asdfghjkl zxcvbnm` | **0** |
| `扫描隐私 头部 没找到`（真实报错） | 3 |
| `今天天气不错`（闲聊） | **1** |

**三条结论**：

1. 我前几轮用的"未命中"信号其实命中 1 个主题 ⇒ 那 10 次读是**命中路径正常开销**，延迟优化空间很小；
2. 真·未命中确实存在（随机长 token ⇒ 0），但**日常消息几乎总能命中至少 1 个主题**；
3. **最值得做的不是省延迟，而是这个宽松命中本身** —— "今天天气不错"也能命中 1 个主题，
   意味着会为闲聊建卡；这是**精度**问题（A2b 主判据面），比 530ms 的延迟重要得多。

**处置建议**：T391 降级为"可选优化"；下一步改为查
「闲聊信号为什么会命中主题」——那是 recall/precision 的真正入口。
