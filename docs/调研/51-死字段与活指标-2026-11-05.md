## 一、ESLint：什么算"被使用"（判据的原始形态）

- [外] **"使用"被精确地定义成四种读**：变量 `foo` 算被使用，当且仅当
  "It is **called** (`foo()`) or **constructed** (`new foo()`) / It is **read** (`let bar = foo`) /
  It is **passed into a function as an argument** (`doSomething(foo)`) / It is **read inside of a function
  that is passed to another function**"。
- [外] **只写不算用**："A variable is **not** considered to be used if it is **only ever declared** (`let foo = 5`)
  or **assigned to** (`foo = 7`)." 文档给的例子直接写着"**Write-only variables are not considered as used**"。
- [外] **自读自改也不算**："A **read for a modification of itself** is not considered as used"
  （`let z = 0; z = z + 1;` 仍是死变量）。这条特别重要——**很多"指标"就是自增给自己看的**。
- [外] **故意保留必须显式声明**：非模块环境里可用 `/* exported variableName */` 标注"这是给外面用的"，
  否则按未使用报错；其余逃生口是 `varsIgnorePattern` / `argsIgnorePattern` 等**命名约定**。
  即：**"死"是默认判定，"活"要靠声明**。
- [外] **连"抑制指令"本身都要被审计**：配置项 `linterOptions.reportUnusedDisableDirectives`
  与 `reportUnusedInlineConfigs` 会**报告那些从未生效过的 disable/enable 注释**——"你关掉的东西其实没被触发过"。

## 二、Go deadcode：可达性 + 判断力（为什么不能只看静态）

- [外] **死 = 从入口不可达**："loads a Go program from source then uses **Rapid Type Analysis (RTA)** to build a
  call graph of all the functions **reachable from the program's main function**. Any functions that are
  **not reachable** are reported as dead code, grouped by package." 只有 main 包是起点。
- [外] **反向问题也要能答**：`-whylive=function` 会"explain **why** the named function is **not** dead by showing
  an **arbitrary shortest path to it from one of the main functions**"——即"活着"必须有可指出的**调用路径**。
- [外] **有些"死"是必需的**：marker 接口方法"technically unreachable, **removing them would break the interface
  implementation**. Hence, the tool **excludes them** from the report"；生成文件默认也不报（`-generated` 可选）。
- [外] **静态结论不等于可删**："just because a function is reported as dead **does not mean it is unconditionally
  safe to delete it**"（死函数可能被另一个死函数引用、死方法可能满足某个从未被调用的接口）——
  "**Some judgement is required.**"
- [外] **结论只对一种配置成立**："The analysis is valid only for a single **GOOS/GOARCH/-tags** configuration,
  so **a function reported as dead may be live in a different configuration**."——判定必须**声明适用范围**。
- [外] **`-test` 是个探针**："Tests sometimes make use of functions that would otherwise appear to be dead code,
  and **public API functions reported as dead with `-test` indicate possible gaps in your test coverage**."

## 三、三条件判据（最终形态）

一个字段/度量"活着"，当且仅当**三条同时成立**：

| 条件 | 定义 | 缺它的名字 |
|---|---|---|
| **L1 被读** | 有人在**读**它（不是只写、不是自增自改、不是被序列化透传） | **死字段 / 死代码** |
| **L2 会变** | 在**真实语料**上它的取值不是恒定（值域 > 1） | **恒定字段**（与死字段等价：读它得不到信息） |
| **L3 改变决定** | 有人**据此分支 / 报警 / 门禁 / 排序**；仅仅被打进 JSON 或日志**不算** | **虚荣指标**（vanity metric） |

**三者的关系不是"三选一"，而是"三条必须全中"；但修法不同**：

- 缺 **L1** ⇒ **删**（或移出扫描面）；若要保留，必须像 ESLint 的 `/* exported */` 一样**显式声明**；
- 缺 **L2** ⇒ **删，或降级为常量 + 一句为什么**（恒定值不该占一个名字）；
- 缺 **L3** ⇒ 二选一：**接上消费者**（谁用它做决定），或**标 vanity 并从看板/门禁里摘掉**（不要让它假装是证据）。

**两条附加纪律**（来自 deadcode 的两条坑）：

- **判定要带范围**：一条字段可能只在某条路径/某个 scope 下活（Go 的 `GOOS/GOARCH`）⇒ 结论必须写"在 X 配置下"。
- **"死"不等于"可删"**：删除前要答"它是不是满足某个约定（marker）/ 被另一个死物引用 / 是公开面的一部分"。

## 四、四个案例逐条命中

| 案例 | L1 被读 | L2 会变 | L3 改变决定 | 判定 | 修法 |
|---|---|---|---|---|---|
| **`mergeStats.candidatesHit`**（T193 后 walk 不再把它当 hit 返回） | 有人读 | ❌ **恒 0** | — | **恒定字段** | **删**；或改成常量并注明"为何不再增长" |
| **`mergeRepresentativeOf`**（建索引、测了 192× 加速，生产零消费者） | ❌ 无人读（除测试） | ✅ | ❌ | **死字段 + 虚荣指标** | **删**；若确实要用，则**接上 walk 的快速路径 + 加基准防退化** |
| **`tmp/` 旧测试副本被 `node --test` 扫到**（8 条假红） | ❌ 没人"读"它们，只是被递归发现 | — | ❌ | **假绿/假红的来源** | 移出扫描面（test glob 白名单），并**加一条"扫描面"断言** |
| **A4 p50 用绝对相等判**（统计量撞固定容差） | ✅ | ✅ | ⚠ **决定本身错** | **指标对、判据错** | 改成**区间判据**（对数域 ±ε）或改成"单调性"判据 |

注意第四条的形态与前三条不同：**它不是"字段死了"，是"判据死了"**——一个会变、有人读的指标，
被一个不可能稳定的比较式判成了"必须精确相等"。这类最危险，因为它**周期性假红**，会训练人忽略告警。

## 五、可执行的检查思路（不要求实现）

1. **写读差集**（ESLint 判据）：对每个字段 `f`，取"赋值处"与"读取处"的差集；
   只有赋值、没有读 ⇒ 死字段候选。**排除**自增自改（`x.f = x.f + 1`）——ESLint 明确说这不算用。
2. **值域扫描**（L2）：用真实语料跑一遍，输出每个字段的取值集合；`|值域| == 1` ⇒ 恒定字段，直接列出来。
3. **消费点分级**（L3）：把"读"再分成——出现在 `if/return/throw/断言/告警/排序键` 里（算决定）
   vs 只出现在 `JSON.stringify` / 日志 / 报告表格里（**不算**，是透传）。
   这一步能自动抓出"所有 vanity metric"，因为它们的消费点全在序列化那侧。
4. **配置维度复跑**（deadcode 的教训）：同一字段在 `--shadow` / `--store` / 默认三种入口各扫一遍，
   值域有变化 ⇒ 标"配置相关"，判定必须带范围。
5. **保留必须留痕**：任何"我知道它是死的但要留着"的字段，要求一行 `why-live: <消费者或理由>`；
   没有这行 ⇒ 按死处理（对应 ESLint 的 `/* exported */` 与 deadcode 的 marker 例外）。
6. **审计抑制项**（`reportUnusedDisableDirectives` 的形状）：测试里的 `skip` / `todo` / 白名单，
   定期报"哪些抑制已经不再需要"——**没有被触发的豁免本身就是死代码**。

## 六、对照本仓（棋院）

`AGENTS.md` §2.4 的「**指标先有消费者**」正是 L3，但它只写了三分之一：
**它没说"恒定值也是死的"（L2），也没说"写读差集怎么查"（L1 的机械判法）**。
今晚四次踩坑分别落在三格里：`candidatesHit` 缺 L2、`mergeRepresentativeOf` 缺 L1 与 L3、
`tmp/` 副本是**扫描面**问题（连 L1 都不该被问）、p50 是**判据**问题（三条都满足但比较式错）。

**建议补进 §2.4 的两句**：

1. 「**恒定值等价于死字段**：真实语料上值域为 1 的字段，必须删掉或降级为常量并注明为什么。」
2. 「**判定必须带范围**：一条指标只在某条路径/某个 scope 下有意义的，结论里必须写清是哪一个。」

## 结论

判据收敛成一句：**一个字段活着 = 有人读它（L1）× 它会变（L2）× 它改变某个决定（L3）**；
三条里任何一条不成立，它不是"暂时没用"，而是**在向读它的人撒谎**。
而"死"不等于"可删"——**故意保留必须写下来**，否则下一个接手的人会把它当成证据。
