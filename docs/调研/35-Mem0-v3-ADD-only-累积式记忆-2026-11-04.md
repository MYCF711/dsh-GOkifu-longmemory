# Mem0 v3 记忆管线：工程上从 UPDATE/DELETE 转向 ADD-only 累积（2026-11-04 采集）

- 来源：厂商文档三页（Mintlify 托管，均已读原文，访问日期 **2026-11-04**）：
  [SDK 版本记录](https://docs.mem0.ai/changelog/sdk.md)、
  [v2→v3 迁移指南](https://docs.mem0.ai/migration/platform-v2-to-v3.md)、
  [How Mem0 Works](https://docs.mem0.ai/core-concepts/how-it-works.md)。
- [外] **带日期的工程事实**：Python SDK **v2.0.0（2026-04-14）** 标注为 "Major Release: Python SDK with V3
  memory pipeline, **ADD-only extraction**"；其中 **Breaking Changes** 一条原文：
  "`add()` returns ADD-only events: No more `UPDATE` or `DELETE` events. **Memories accumulate; nothing is
  overwritten**"（[SDK 版本记录](https://docs.mem0.ai/changelog/sdk.md)，访问 2026-11-04）。
- [外] **同一条目里的实现细节**：Single-Pass Extraction —— "Replaced 2-LLM-call pipeline with additive
  extraction using `ADDITIVE_EXTRACTION_PROMPT`"，新记忆通过 **`linked_memory_ids`** 累积；不再产生
  UPDATE/DELETE 事件。同一条目还列了 Hybrid Search（semantic + BM25 keyword + entity boost，**additive
  scoring**；`keyword_search()` 落进 15 个向量库适配器）、Entity Extraction & Linking（spaCy 抽取 + 第二个
  向量集合 `{collection}_entities` 做跨记忆关系检索，可选依赖 `pip install mem0ai[nlp]`）、
  Batch Operations（batch embedding / persist / entity linking 的 **8 阶段流水线**）、
  Message Persistence（SQLite 滚动窗口，**10 条消息/会话作用域**，仅供 LLM 上下文用）。
- [外] **同一条目里被删掉的东西**：External Graph Store Removed (OSS) —— `graph_memory.py`、
  `memgraph_memory.py`、`kuzu_memory.py`、`apache_age_memory.py`、`mem0/graphs/`（Neo4j / Memgraph / Kuzu /
  Apache AGE / Neptune 驱动）**删除约 4,000 行**；"Graph memory now runs natively as built-in entity linking"；
  `enable_graph` 从 Client SDK 移除。
- [外] **同一条目里的口径变化**：`search()` 的 `score` 变成 **combined multi-signal score**（semantic + BM25 +
  entity 信号 + temporal boost 融合成一个值），绝对数值与旧版余弦不可比；`top_k` 默认 **100 → 20**；
  `threshold` 默认 **0.1**（[SDK 版本记录](https://docs.mem0.ai/changelog/sdk.md)，访问 2026-11-04）。
- [外] **迁移指南的对照表**（Before → After，[迁移指南](https://docs.mem0.ai/migration/platform-v2-to-v3.md)，
  访问 2026-11-04。**该页未标注发布日期**，只能确定抓取日期）：Extraction 两轮 LLM（extract + merge）→
  **单轮 ADD-only（一次 LLM 调用）**；Memory mutations `ADD, UPDATE, DELETE` → **`ADD only`: nothing is
  overwritten or deleted**；agent 自己生成的事实（如"已订 3 月 3 日机票"）从"常被忽略"变为**一等公民**；
  Graph memory 从"外部图库（Neo4j 等）+ 手工配置"→ **内置、自动**；Retrieval 从"仅语义（向量）"→ **混合多信号**。
- [外] **迁移指南里对"累积"的三条解释**：信息变化时（例：用户从纽约搬到旧金山）"both facts are preserved
  with temporal context"；收益是能区分 "used to live in New York" 与 "now lives in San Francisco"、
  并且"contradictory but actually complementary" 的事实不再丢；以及对旧用法的提示原文——
  "If your application previously relied on UPDATE/DELETE behavior to keep memory counts low, the new
  algorithm **handles this at retrieval time instead**. Multi-signal retrieval ranks the most relevant,
  current information higher **without destroying historical context**."
- [外] 迁移指南另两处工程口径：temporal 信号"applied internally during ranking and **are not returned as
  extra client-facing fields**"；FAQ 里"要控体积就用 **expiration date 或 delete API**"，且新算法是默认、**不可
  opt-out**（只能联系支持）。
- [外] **厂商自报成绩**（同一迁移指南）：新算法 **91.6 on LoCoMo**、**93.4 on LongMemEval**，相对旧算法
  **+20 / +26**，同时"cutting extraction latency roughly in half"。这是**自报数字**，非独立复现。
- [外] **写入管线的四个步骤**（[How Mem0 Works](https://docs.mem0.ai/core-concepts/how-it-works.md)，
  访问 2026-11-04）：① **Context lookup**（先查相关旧记忆，避免把同一事实再存一遍）→ ② **Fact extraction**
  （LLM 抽偏好/决定/计划）→ ③ **Deduplication and embedding**（去掉冗余事实再嵌入）→ ④ **Entity extraction**
  （人/地/组织/概念，Platform 上成为 Graph Memory 的节点）。同页原文："The automatic extraction path is
  **additive**. If a user says, 'I moved from Austin to Seattle,' Mem0 can store the new fact without silently
  rewriting the old one. Use explicit `update` or `delete` operations when your application needs to correct
  or remove a memory."
- [外] **读侧的四个信号**（同页表格）：**Semantic**（向量相似度）、**Keyword**（词面匹配，适合名字/ID）、
  **Entity**（查询里的实体命中时给相关记忆加权）、**Temporal**（用写入时抽取的时间元数据对比查询的时间意图）。
  Platform 内置融合这些信号、entity 信号由内置 Graph Memory 支撑；**OSS 没有 graph memory**，只有实体重叠加权。
- [外] **存储分工**（同页）：SQL 存事实与元数据（source of truth）、向量库存嵌入、entity store 存实体
  （Platform 上兼作 Graph Memory）。另有一句产品向的提示：`infer=False` 时原样存原文，否则存"清洗+去重后的
  事实"。

## 对照本仓（棋院）

这是本轮最有价值的对照面：**我们在 2025 年的论文口径下是"异类"，在 2026 年的工程口径下变成了主流。**

| Mem0 v3（2026-04） | 棋院 | 判断 |
|---|---|---|
| `add()` 只发 ADD，**nothing is overwritten** | 只增不改：冲突只加 `supersededBy`，原件永不删 | ✅ **同构**。这条外部证据说明"只增不改"不是保守，是工程趋势 |
| 用 `linked_memory_ids` 把新记忆挂到相关旧记忆上 | 归档时同批建 `link`（shared-topic / same-error / same-file） | ✅ 同形；差异在**谁产生关系**：他们靠 LLM 抽取，我们靠机械规则 |
| 体积变大 → **在检索时排序**，不删历史 | 体积变大 → 注入侧**遮蔽 + 指针**，旧条不删只遮蔽 | ✅ 同一解法方向；我们把它做成机械规则（无需模型） |
| temporal 信号在**排序时**内部生效、不外露字段 | 渲染必带 `occurredAt`、新旧按 `occurredAt` 判 | ⚠ 取舍不同：他们把时间当**内部信号**，我们把时间当**可见事实**（可核） |
| 写入时 **Deduplication**（去冗余事实再嵌入） | 没有写时去重；同一事实重复入馆会产生重复 claim | ⚠ **这是我们的缺口**，但可机械补：同 `text + occurredAt` 哈希去重，不动旧条 |
| agent 生成的事实升级为一等公民 | 工具调用/agent 动作本来就是 episode 与边的来源 | ✅ 早已同向 |
| 删掉外部图库、改内置实体链接（约 4,000 行） | 我们自带图（topics/links），零外部依赖 | ✅ 同向，且我们更彻底（无外部存储） |
| 厂商自报 91.6 / 93.4 | 我们的冻结卷是自建小基准 | 口径不同，不可横比；只当**方向**证据 |
| 作用域靠调用方自觉：文档原话 "Always scope searches with filters such as `user_id`, `agent_id`, or `run_id`" | 作用域由 `scopeKey` 定义、**跨作用域在闸口机械拦下**（A5 目标 0） | ✅ 同向；差别是**纪律位置**：他们写在文档里靠调用方，我们写进闸里靠代码 |
| `search` 返回事实字符串，**由你的 app 决定是否放进 prompt** | 注入只给事实，且过十道闸 + 祈使句过滤后才进卡 | ✅ 同向；我们更严（他们不管调用方怎么用返回物） |
| 记忆是模型改写后的事实陈述，**没有逐字原文**；旧版已被覆盖 | 每条注入可追到 `ep + seq + quote`，原件永远在（A6 文字可核） | ⚠ 能力差别：他们换来更干净的记忆文本，我们换来**可回放的原文** |

**能借的两点（都能做成机械规则）**：

1. **写时去重（限"完全相同"）**：入馆前对 `(kind, text 归一, occurredAt)` 做哈希去重，
   重复的直接跳过、不产生新条目。这与"只增不改"不冲突——它不修改任何已有条目，只是**不再写入同一条**；
   而且它正是他们第 ③ 步在做的事。
2. **"体积在检索时解决"的口径**：把"记忆变多"当成**读侧排序/遮蔽问题**，而不是写侧删除问题；
   这条可以直接写进我们的容量策略——上限只作用于**注入**，不作用于**库**。

**明确不借的四点（附理由）**：

1. **LLM 单轮抽取（`ADDITIVE_EXTRACTION_PROMPT`）**：抽取要靠模型判断，与本仓"机械抽取、零模型调用"冲突；
   我们换来的是可复算与可回放。
2. **向量/混合检索与 reranker**：本仓明确不做向量检索；我们的"检索"是词面 + 类别 + 作用域 + 十道闸。
3. **用 `expiration date` / `delete API` 控体积**：等于让旧记忆消失，直接砍掉可回溯；
   我们宁可库越来越大，也不删原件（上限设在注入侧）。
4. **把时间只当内部排序信号**：本仓的红线是"每条注入必须带日期且可核"，
   时间对我们不是隐藏权重，而是**可被用户核对的字段**。

## 两条可复用结论

1. **"累积 + 关系"是同一个包**：Mem0 的 ADD-only 不是"只写不管"，它同时加了 `linked_memory_ids`（关系）
   与 temporal 信号（时间）。我们已经有 `links` 与 `occurredAt`——这恰好说明本仓的结构选择踩在正确的两条腿上；
   缺任何一条，"累积"都会退化成垃圾堆。
2. **去重是"累积式记忆"的必要配件，不是可选项**：他们放在**写侧**（dedup 再嵌入），我们放**读侧**（遮蔽）。
   写侧去重更省空间、读侧遮蔽更保历史；两者可以并存——只要写侧去重只针对"完全同一条"，不碰历史。

## 结论

无需改架构（`ADD-only + 关系 + 时间` 与我们一致）；可落地的是**一件小事**：
入馆前做"完全相同事实"的机械去重，避免重复条目把索引与检索撑肿。
更重要的是它给了本仓一个**外部依据**：把"只增不改"写成"与 2026 年主流工程实现同向"，
而不是"我们的保守选择"；同时把它读侧的代价（体积涨、排序压力）说清楚——那正是我们遮蔽策略在扛的活。
