# 什么时候不该再取出来：记忆的陈旧与过期（2026-11-06 采集）

- 来源：两份一手文档（均已读全文，访问日期 **2026-11-06**）：
  [RFC 5861 · HTTP Cache-Control Extensions for Stale Content](https://www.rfc-editor.org/rfc/rfc5861.html)（2010-05）、
  [Amazon DynamoDB · Using time to live (TTL)](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html)。
- **范围声明**：46 篇讲三值逻辑、48 篇讲派生数据、50 篇是判据总表、59 篇讲**不能改原件时怎么纠错**、60 篇讲**时间戳语义**；
  本篇只写**"什么时候一条记忆不该再被取出来"**——陈旧（stale）的判据、降权而非删除、以及 TTL 的坑。五篇不重复页面。

## 一、陈旧是例外，不是常态

- [外] **默认必须给最新的**（RFC 5861 引 RFC 2616）：HTTP 要求缓存"**respond to a request with the most up-to-date
  response held** … that is appropriate to the request"，"**although 'in carefully considered circumstances' a stale
  response is allowed to be returned**."
  ⇒ **陈旧响应是要论证的例外**，不是默认行为。
- [外] **`stale-if-error`：上游坏了才用旧的**：允许在遇到错误（"a 500 Internal Server Error, a network segment, or
  DNS failure"）时返回陈旧响应，"**rather than returning a 'hard' error. This improves availability**."
  ⇒ 陈旧数据的第一个合法用途：**降级可用性**（有总比没有好），但**只在错误路径上**。
- [外] **`stale-while-revalidate`：先给旧的、后台换新的**："allows a cache to **immediately return a stale response
  while it revalidates it in the background**, thereby **hiding latency**（both in the network and on the server）
  from clients."
  ⇒ 第二个合法用途：**用陈旧换延迟**，代价是**短暂不一致**（必须能被后台重验纠正）。

## 二、TTL 的四个坑（DynamoDB）

- [外] **过期 ≠ 立刻删除**："DynamoDB automatically deletes expired items **within a few days** of their expiration
  time." ⇒ 删除是**最终一致**的，中间存在"已过期但仍可读"的窗口。
- [外] **过期项仍可读可改，且可复活**："Items with valid, expired TTL attributes **might be deleted … at any
  time**"；"You can **still update the expired items that are pending deletion**"；若把 TTL 改成未来时间或移除该属性，
  "the item is **no longer considered expired** and the TTL process **does not delete it**."
  ⇒ **TTL 是可逆的**（只要还没被删）。
- [外] **读侧必须自己过滤**："Use **filter expressions to remove expired items** from Scan and Query results."
  ⇒ **存储层不保证你看不到过期项**——"取出来"这件事由读者负责。
- [外] **格式错 = 静默永不过期**："Items with a TTL attribute that is **not a Number type** are **ignored** by the
  TTL process." ⇒ 一个写错的 TTL 字段**不会报错**，只会让条目**永远活着**——这是最危险的失败形态（无告警）。
- [外] **并发要条件写**："While updating an expired item, we recommend that you use a **condition expression** to
  make sure the item has **not been subsequently deleted**." ⇒ 过期与删除是竞态。

## 三、什么样的记忆会过期（分类）

| 类型 | 本仓例子 | 过期源 | 有没有"可复算的验证面" |
|---|---|---|---|
| **环境依赖** | `pnpm dlx shadcn@latest add button` | 包版本、工具行为、registry | ✅ 有（重跑命令即可验） |
| **文件/代码事实** | "`src/x.mjs` 里有 `foo()`" | 文件被改/删/重命名 | ✅ 有（`file-exists` + 内容 hash） |
| **外部事实** | 某 API 端点、某默认值 | 上游变更 | ⚠ 弱（只能靠时间与重测） |
| **方法性教训** | "**fs 读前必读**"、"先备份再改" | **几乎不过期**（协议/纪律级） | ❌ 无（长期有效） |
| **偏好** | "用户要中文、要简短" | 用户改主意 | 靠 `supersedes`（59 篇） |

**一句话判据**：**有"可复算验证面"的会过期；没有验证面的（方法、原则）不过期**——
把方法性教训按环境依赖一样设短 TTL，是**误杀**；反过来，把 `@latest` 命令当永真，是**过期污染**。

## 四、"过期"该怎么判（三条判据，从硬到软）

| # | 判据 | 机械检查 | 性质 |
|---|---|---|---|
| **V1 `validUntil` 到期** | 显式时间戳，`now > validUntil` | 最弱但**可机械** | 兜底 |
| **V2 `preconditions` 失败** | `file-exists` / `cmd` / `version` / `scope` / `step-range` 任一失败 | **可复算、最强** | 硬判据 |
| **V3 距上次被印证的时间** | `now − lastVerifiedAt > TTL(kind)` | 软判据（分级 TTL） | 降权 |

**分级 TTL（按 kind 定，不按条拍）**：

- **环境依赖**：短（如 30 天）+ 每次被命中时**重跑验证**（V2 优先）；
- **文件/代码事实**：随 `file-exists`/hash 走（V2 一票否决）；
- **外部事实**：中（如 90 天），且**标注"需重测"**；
- **方法性教训**：**TTL = ∞**（V3 不适用）；
- **偏好**：靠 `supersedes`，不看时间。

## 五、可执行的降权判据（**只降权，不删除**）

```
stale = V1 到期 || V2 失败 || V3 超期
若 stale：weight *= staleFactor（如 0.5），state = "stale"（条件已变只给指针）
不删除、不改写；若有过期原因可写进 correction（59 篇）
```

- **读侧必须过滤**（DynamoDB 明说"use filter expressions"）：**不能指望存储层帮你挡**。
- **与 59 篇的三态分工**：`supersededBy` = 有更好后继；`invalidated` = 条目为假；**`stale` = 可能过时，降权**。
  三者混用会让"旧了"与"错了"长得一样。
- **可复活**（DynamoDB）：若 V2 重跑通过（命令仍可复现、文件仍在），把 `state` 改回 `observed` 并更新
  `lastVerifiedAt`——**TTL 是可逆的**。
- **格式错要告警**：TTL 字段类型/格式不对必须**报错**，不能像 DynamoDB 那样"ignored"（静默永不过期）。

## 六、对照本仓（棋院）

- **`pnpm dlx shadcn@latest add button`** ⇒ **环境依赖类**：V3 短 TTL + 命中时重跑（V2）；
  它"包版本一变就可能过期"，**不能当永真**。
- **`fs 读前必读`** ⇒ **方法性教训**：**TTL = ∞**。把它按时间降权就是误杀——它不依赖任何版本。
- **T191 的 `validUntil`** 已经写了"**过期只降权不删除**"，与 DynamoDB 的"过期 ≠ 立刻删"一致；
  **缺的是**：① 分级 TTL 表（按 `kind` 定，而不是每条手写 `validUntil`）；② `lastVerifiedAt` 字段（V3 的分母）；
  ③ 读侧过滤的**强制**（现在是"可选降权"，应当"必须过滤"）。
- **与 §2.3 的关系**：`occurredAt` 决定"新旧"，`validUntil`/`stale` 决定"还该不该取"——**两个问题，不能互相替代**
  （60 篇：时间戳是"何时发生"，不是"何时失效"）。

- RFC 5861 是**信息类**（Informational），不是标准轨；它只定义 `stale-if-error` / `stale-while-revalidate`，
  **没有**给 TTL 取值建议。
- **未确认**：`lastVerifiedAt` 现在是否已存在于 claim 契约（若没有，V3 无法机械算）；
  以及读侧过滤是否已经**强制**（若只是"降权"，过期项仍会占卡位）。

## 结论

判据三句话：**陈旧是例外**（默认给最新的，`stale-if-error` 只在错误路径、`stale-while-revalidate` 只在能后台重验时）；
**过期 ≠ 删除**（最终一致、可复活、读侧必须过滤）；
**有验证面的会过期、没验证面的不过期**（V2 硬判、V1 兜底、V3 降权）。
最后一句：**TTL 最危险的失败形态是"静默永不过期"**——一个写错的字段不会报错，只会让错的记忆一直被取出来。
