# 指针还在但指错：引用完整性、内容寻址与迁移期不变量（2026-11-05 采集）

- 来源：两份一手文档（均已读全文，访问日期 **2026-11-05**）：
  [PostgreSQL 18 · 5.5 Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)、
  [IPFS Docs · Content Identifiers (CIDs)](https://docs.ipfs.tech/concepts/content-addressing/)。
- **范围声明**：46 篇讲三值逻辑（未知怎么传播）、48 篇讲派生层成本、50 篇是判据总表、51 篇讲死字段；
  本篇只讲**"指针还在、但指向已经错了"**——引用完整性与内容寻址为何能挡住它，以及迁移期该断言什么。五篇不重复页面。

## 一、PostgreSQL：三个"看起来在检查、其实没检查"的洞

- [外] **外键 = 引用完整性（前提是被强制）**："A foreign key constraint specifies that the values in a column
  (or a group of columns) **must match the values appearing in some row of another table**. We say this maintains
  the **referential integrity** between two related tables." 举例：**"it is impossible to create orders with
  non-NULL `product_no` entries that do not appear in the `products` table"**。
- [外] **洞一：CHECK 遇 NULL 即通过**——"a check constraint is **satisfied if the check expression evaluates to
  true or the null value**. Since most expressions will evaluate to the null value if any operand is null,
  **they will not prevent null values** in the constrained columns."（要挡空值得另加 `NOT NULL`。）
- [外] **洞二：只在写时检查**——"PostgreSQL assumes that `CHECK` constraints' conditions are **immutable**…
  This assumption is what justifies **examining `CHECK` constraints only when rows are inserted or updated,
  and not at other times**." 后果写得很直白：若被引用的东西（如函数）后来变了，
  "**it will not notice** if there are rows in the table that now violate the `CHECK` constraint."
- [外] **洞三：检查可以被延迟**——"checking of foreign-key constraints **can also be deferred** to later in the
  transaction… the `NO ACTION` setting would allow other commands to '**fix**' the situation **before the
  constraint is checked**"；而 "`RESTRICT` is a **stricter** setting… **does not allow the check to be deferred**"。
  也就是说：**"暂时悬空"是合法的状态**，取决于你选的是哪一种。
- [外] **要持续一致就得自己立触发器**："If what you desire is a **one-time check**… rather than a
  **continuously-maintained consistency guarantee**, a custom **trigger** can be used to implement that."

## 二、IPFS：内容寻址为什么能挡住"指错"

- [外] **地址由内容决定**："It doesn't indicate **where** the content is stored, but it forms a kind of
  **address based on the content itself**."；两条硬性质："**Any difference in the content will produce a different
  CID**" 与 "The **same content** added to two different nodes using the same settings will produce **the same CID**"。
- [外] **同一份内容可以有不同 CID**（这是最容易被忽略的一条）：CID 取决于**内容 + 结构**——
  "**Chunk size** / **DAG layout** / **Codec** / **CID version** / **Hash algorithm**" 任何一项不同，CID 就不同。
  推论：**指针只在它被计算时的"结构约定"下有意义**；换了一套切分/布局，同一个指针会指向别的东西。
- [外] **CID 不等于校验和**："While a data block's CID is constructed using the cryptographic hash…, a CID contains
  **additional information**… that the hash does not"（multihash + multicodec + multibase）。
  所以"我算过 sha256 了"不等于"我有一个可寻址的指针"。

## 三、"真的可回溯"的三条机械判据

| # | 判据 | 机械检查方式 | 缺它的名字 |
|---|---|---|---|
| **P1 可解析** | 指针能解析到**唯一**对象，且落在该对象的合法范围内 | `episode` 在 `episodes/` 里存在；`seq` 在该局的 seq 区间内；`quote` 非空 | **悬空指针**（PG 的外键未强制） |
| **P2 可重算** | 指针携带的**内容摘要**能重算且与记录一致 | `sha256(normalize(quote))` == 记录里的 `quoteHash`；且 quote 是**该 seq 事件文本的逐字子串** | **可替换指针**（看起来对，指向别处） |
| **P3 可复核** | 任何人**独立**跑一遍得到同一结论，不依赖写库时的进程内存/临时索引 | 校验脚本只吃 sidecar + 会话日志 | **私有真值**（只有写库者能验证） |

三条**必须同时成立**：P1 少了就是悬空，P2 少了就是"指针格式对、内容错"，P3 少了就是"作者自证"。
PG 的那三个洞正好对应：CHECK 遇 NULL 通过 = **P2 缺**（空值也能过）；只在写时检查 = **P3 缺**（事后无人复核）。

## 四、迁移/合并前后**必须保持**的不变量（可断言清单）

1. **引用完整性**：每条 claim 的 `support[].episode` 在 episodes 里存在（悬空数 = 0）。
2. **范围合法**：每条 `support[].seq` 落在该 episode 的 seq 区间内（不是"某个全局序号"）。
3. **逐字可核**：`support[].quote` 是该 (ep, seq) 事件文本的**子串**（归一化空白后）。
4. **摘要一致**：`quoteHash` 与 quote 重算一致（有摘要就必须核；没有就要补）。
5. **只增不减**：claim 总数**不减**；新增条目的 `recordedAt` ≥ 迁移开始时间（不得倒填）。
6. **反指针完整**：被覆盖/合并的条目必有 `supersededBy`，且**目标存在**（与 1 同构，只是指向 claim 而非 episode）。
7. **幂等**：迁移脚本重放两次结果相同（同一 (ep, seq, hash) 不重复计数）。
8. **A6 单调**：迁移前后"missing"**不增加**（0 必须保持 0）。
9. **可回滚**：迁移前存在可独立恢复的快照（49 的教训：回滚不是撤销，但至少要有一条退路）。

## 五、对照本仓（棋院）

**本文写作时点的实测（仅此一节）**：合流写库把 39 个合并组写进真库，**claims 1340 → 1379**；
之后一张卡引用的 `(ep-62bcb7d2, seq 5736)` 与原事件**对不上**，A6 **missing 1**（长期为 0）；
**写库 09:56、出现 missing 13:54，同一个进程、同一份代码**。

- **命中洞一（P2 缺）**：我们核过"ep 存在、seq 是个数"，但**没有核"quote 是那个 seq 的原文"**——
  这正是 PG 的"CHECK 遇 NULL 通过"：指针字段空着/错着，断言照样为真。
- **命中洞二（P3 缺）**：写库之后**没有任何一次全量 re-check**（PG 说"will not notice"），
  所以污染从 09:56 活到 13:54 才被随机发现。
- **命中洞三（延迟检查）**：如果迁移是"先写、后补指针"，那它是合法通过检查的——**除非**声明为 `RESTRICT`
  式的**立即**检查（每条 claim 落盘前必须先解析通过）。
- **内容寻址给我们的那一课**：**同一份内容在不同结构约定下地址不同**。合流改写了 support 的**结构**
  （成员 → 合并组的代表），若指针仍按旧结构解释，它就会**安静地指向别的东西**——
  这不是"数据坏了"，是"地址的解释器换了"。

### 结论：回滚还是修不变量？

**判据（按顺序问）**：

1. **能不能证明原值？** 迁移前有不变量快照/日志 ⇒ 能；否则不能。
2. 能 ⇒ **回滚 + 立刻补不变量**（不回滚就补不变量也行，但回滚给了"干净的基线"）；
   不能 ⇒ **不回滚**（回滚会丢更多，且无法证明回滚后的状态），改为：
   **修不变量（P2/P3）+ 对受影响条目打 `state:"disputed"` + 记 correction**（L4 纪律）。
3. **无论哪条，P1–P3 与第四节的九条断言必须先落地**——否则下一次迁移会重演。

**优先级**：**先保不变量，再谈回滚**。因为**回滚本身也需要不变量来验证**（49 篇：回滚不是撤销）。

### 我们**没做**的那一步（最具体的一条）

**"指针格式正确" ≠ "指针指向正确"。** 我们做了 P1（存在性）与部分 P3（脚本可独立跑），
**缺的是 P2 的逐字比对**：`sha256(normalize(quote))` 与 `(ep, seq)` 事件原文的 **子串断言**。
补上它，今晚这类"指针还在但指错"会在**写库那一刻**就红，而不是四小时后被随机抽样撞见。

## 结论

三条判据一句话：**可解析（P1）× 可重算（P2）× 可复核（P3）**。
第四节的九条不变量是它们的可执行形态；而**内容寻址真正的价值不是"哈希防篡改"，
是"换了结构就必须换地址"**——它让"解释器变更"这件事无法被静默忽略。
今晚的 missing 1 不是数据丢失，是**我们允许了一个空位通过检查**。
