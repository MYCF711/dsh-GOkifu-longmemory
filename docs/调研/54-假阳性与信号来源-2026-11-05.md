## 一、机制：管道只报"最后一条命令"的账

- [外] **管道的退出码默认来自最后一条命令**（Bash 手册原文）："The exit status of a pipeline is the exit status
  of the **last command** in the pipeline, **unless the `pipefail` option is enabled**."
- [外] **`pipefail` 打开后的语义**（同段）："If `pipefail` is enabled, the pipeline's return status is the value of
  the **last (rightmost) command to exit with a non-zero status**, or zero if all commands exit successfully."
  另：管道里**每条命令各在自己的子 shell** 里跑，"The shell waits for all commands in the pipeline to complete"。
- [外] **`grep` 的退出码是"选到没有"，不是"被搜的东西成不成功"**（grep(1) EXIT STATUS）：
  "Normally the exit status is **0 if a line is selected**, **1 if no lines were selected**, and **2 if an error
  occurred**. However, if the `-q` … is used and a line is selected, the exit status is **0 even if an error
  occurred**."
- **合起来的后果**：`node --test … | grep "^ℹ (tests|pass|fail)"` 这条链的退出码**由 grep 决定**；
  只要 grep **选中了那行绿汇总**，整条链就返回 **0**——上游真失败（以及链尾的 `git checkout` 失败）
  **在退出码层面被彻底抹掉**。同时，`errorSnippet` 抓到的那段文字，**恰好就是 grep 选中的那一行**：
  于是"绿汇总"变成了"失败证据"。

## 二、"一条失败教训凭什么算失败"——三条判据与各自的坑

| # | 判据 | 它的坑 |
|---|---|---|
| **F1 退出码非零** | 最硬、最可机械核 | **管道会吞码**（除非 `pipefail`）；`\|\| true`、`-q`、`set +e` 都会把它变成 0；**只保留最后一条命令的码** |
| **F2 错误标记**（stderr / `Error:` 前缀 / 退出码括号） | 不依赖退出码，视觉可读 | **标记可能来自被选中的那一行**（我们的实例：`fail 0` 里也有 "fail" 这个词）；"含 fail 字样"**不是**标记 |
| **F3 人工标注/复核** | 冲突时的最高证据 | 标注者看到的常是**摘要**而不是原始输出 ⇒ 二次污染；且不可机械复算 |

**三条的正确关系**（这是本篇的核心判据）：

> **F1 是必要条件**：`exitCode !== 0` 才可能是失败。
> **F2 是定位条件**：错误标记必须来自**失败的那个进程**的 **stderr**（或它的非零行），而不是"链上任何一行含关键词"。
> **F3 只用于裁决**：F1 与 F2 冲突时（例如退出码非零但输出是绿的），用人判断；**不得**用 F3 覆盖 F1。

**推论**：`if (snippet) return snippet`（有无片段即判失败）是**三条全不满足**的判法——
它把"有一段被选中的输出"当成了"失败"，而这正是本次 7 条假阳性的生成式。

## 三、"信号来自哪一行"为什么与"有没有失败"同等重要

一条可采信的错误信号必须带**四元组**：

```
(exitCode, stream, originProcess, lineNumber)
```

- `exitCode`：**产生这次失败的进程**的退出码（不是整条管道的）；
- `stream`：`stderr` 优先（stdout 里的"失败"多半是摘要或回显）；
- `originProcess`：哪个命令/子进程产生的（管道里每条命令都是独立子 shell）；
- `lineNumber`：在**该进程输出**里的行号（用于复查）。

**我们的实例三元全错**：`exitCode = 0`（grep 的）、`stream = stdout`（grep 的输出）、
`originProcess = grep`（不是被测试的进程）——**四个字段里三个指向"不是失败"的那一侧**。
只看"snippet 非空"就会把它读成失败；只看四元组就会立刻判定"这不是错误信号"。

## 四、可执行的检查思路：怎么机械地找出"库里把成功当失败"

1. **绿汇总白名单扫描**：对每条 claim 的 `support[].quote` 跑一组"成功特征"正则——
   `^ℹ (tests|pass|fail) \d+`、`^# *tests \d+`、`\bpass \d+\b.*\bfail 0\b`、`^\s*\d+ (passing|failing)`、
   `All tests passed`。命中 ⇒ 标 `suspected-false-positive`（**只标不删**）。
2. **与退出码交叉核**：若该 support 能追到 `tool/result` 的 exit code，且 `exitCode === 0` 而该条被记成
   `failure` ⇒ 标 `contradiction`（47 篇的"矛盾单列"做法）。
3. **矛盾双方的指向**：把 claim 的 `kind: "antipattern"` 与 quote 的"成功特征"并置——
   **同一行文字同时被读成"成功"和"教训"** ⇒ 必然是采信逻辑错了，不是数据错了。
4. **三态输出**：`suspected / confirmed / cleared`（46 篇的纪律：未知不许吸收成通过）。
5. **修法不改历史**：旧条目按 `supersededBy` 标注 + 新条目不写；**不删**（只增不改）。

## 五、对照本仓（棋院，写作时点实测）

真库里有 **7 条** claim 把 `ℹ tests N ℹ pass N ℹ fail 0` 标成 `[antipattern]`（测试全绿被当成失败教训）。

- **生成链**：`node --test … | grep "^ℹ (tests|pass|fail)"` 后面还有 `git checkout …`；
  **真失败在链尾**，而退出码被 grep 拿走（**F1 被管道吞掉**），snippet 抓到的是 grep **选中**的绿汇总
  （**F2 的来源错了**）——两条判据同时失效，只剩下"有 snippet ⇒ 是失败"的默认。
- **代价三条**（与主人的观察一致）：
  ① **占卡位**：top-5 有限，7 条假教训挤掉真教训；
  ② **误导模型**：看到 `[antipattern]` 会以为有坑要避，而"坑"其实是"测试全绿"；
  ③ **污染指标**：这些条目与任务无关，却因含 `fail` 字样可能撞上 overlap 排序（53 篇的"归因"问题：
  排序键不该被关键词污染）。
- **最小修法**（三处，都不改历史）：
  a. `errorSnippet` 只在**该命令自己的退出码非零**时采信（F1 门）；
  b. snippet 取**失败进程的 stderr**（F2 的来源门），而不是"链上某条命令的 stdout"；
  c. 管道统一 `set -o pipefail`，或干脆不管道（先落文件再 grep）——让退出码回到**真正执行测试的那个进程**。
- **旧 7 条**：标 `supersededBy` 指向"该命令实际 exit code"的核验记录，**不删**（只增不改 + A6 可追）。

## 结论

判据三句话：**F1 退出码是必要条件（管道会吞，务必 `pipefail`）→ F2 标记必须来自失败进程的 stderr → F3 只裁决不覆盖**。
再加一条关于"出处"的：**错误信号要带 `(exitCode, stream, originProcess, lineNumber)` 四元组**——
因为本次事故里，"有没有失败"与"信号来自哪一行"是同一个问题的两半；
只回答前者，就会把 `fail 0` 读成失败。
