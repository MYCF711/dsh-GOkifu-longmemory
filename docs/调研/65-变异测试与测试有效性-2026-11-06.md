# 怎么证明测试真的在测东西：变异、tombstone 与绿测试的假象（2026-11-06 采集）

- 来源：一手文档（已读全文，访问日期 **2026-11-06**）：
  [PIT Mutation Testing](https://pitest.org/)。
- **范围声明**：44 篇讲验收方法论、50 篇是判据总表、56 篇讲**考卷本身坏了**、61 篇讲**负向对照**；
  本篇只写**"怎么证明一个测试真的在测东西"**——变异、tombstone、以及绿测试的五种假象。四篇不重复页面。

## 一、变异测试的定义：杀不死的变异 = 测试没测到

- [外] **五十一个字的定义**："Faults (or **mutations**) are **automatically seeded** into your code, then your tests
  are run. **If your tests fail then the mutation is killed**, if your tests pass then the mutation **lived**.
  The quality of your tests can be gauged from the **percentage of mutations killed**."
- [外] **换一种说法更直白**："PIT runs your unit tests against **automatically modified versions** of your
  application code. When the application code changes, it **should produce different results and cause the unit tests
  to fail**. **If a unit test does not fail in this situation, it may indicate an issue with the test suite.**"
- [外] **它是"标准"而不是"另一种覆盖率"**："mutation testing is the **gold standard** against which all other types
  of coverage are measured."
- [外] **怎么跑才划算**："The most effective way to use mutation testing is to run it **frequently** against **only
  the code that has been changed**"；集成后"can be run **locally by developers**, or **automatically against pull
  requests**"。
- [外] **副产品：找死代码**（Sky 引文）："it can also find **redundant code that when deleted still implements the
  intended functionality**" ⇒ **删掉还能过 = 这段代码是死的**（正是 tombstone 的反向用途）。

## 二、行覆盖率的三个盲区

- [外] **覆盖率只测"被执行"**："Traditional test coverage (i.e line, statement, branch, etc.) measures only **which
  code is executed** by your tests. It does **not** check that your tests are actually able to **detect faults** in
  the executed code. It is therefore only able to identify code that is definitely **not tested**."
  ⇒ 高覆盖率**只排除**"完全没跑过"，**不证明**"跑过就有意义"。
- [外] **最极端的形态：没有断言的测试**："The most extreme examples of the problem are **tests with no
  assertions**."
- [外] **更常见的形态：分支全跑但没断言**："Much more common is code that is only **partially tested** by its suite.
  A suite that only partially tests code can **still execute all its branches**."
  ⇒ **"分支覆盖 100%"与"断言强度 0"可以同时成立**。

## 三、"绿测试也可能是假的"五种形态

| # | 形态 | 症状 | 变异测试怎么抓 |
|---|---|---|---|
| **1 没断言** | 测试体只有调用（`expect` 缺失或没人用返回值） | 永远绿 | **所有变异都 live** ⇒ 分数 0 |
| **2 断言过松** | 只断言"不抛异常"、`toBeTruthy()`、`!= null` | 变异后仍 truthy | 语义变异 live（值错但不空） |
| **3 只测 happy path** | 只喂正常输入 | 边界永远不红 | **边界变异**（`<`→`<=`、`+1`、`>=`→`>`）live |
| **4 快照/字符串比较过宽** | 快照含无关字段、整串比较 | 改一个字段也绿 | 字段级变异 live（快照没被更新） |
| **5 环境/顺序依赖（flaky）** | 有时绿有时红 | 变异"被杀"但不确定 | **分数不可复算**（56 篇：不可靠信号会让真失败被忽略） |

**共同点**：这五种都**通过**了测试，但**没有一条**能回答"改坏了会不会红"。
变异测试的判据只有一个：**改坏了，必须红**。

## 四、tombstone test：删掉实现，测试必须红

**定义**（`AGENTS.md` §11 的房间契约）：**删掉实现文件，那一整个测试文件必须红。**

**落地三式**：
1. **移动实现**：`mv src/rooms/x.mjs /tmp/`（或 `git stash push -- <file>`），跑 `node --test test/x.test.mjs`，**必须报错**；
2. **只跑该文件**：用 `--test-name-pattern` / 直接指定文件，避免被别的测试掩盖；
3. **留证据**：把"红的输出"贴进 evidence（与"绿的输出"同等重要）。

**变异测试是 tombstone 的细粒度版**：tombstone 删**整个文件**（粗），变异改**一个字符**（细）。
两者是同一判据的两端：**坏的输入必须产生坏的结果**。

### 一个测试文件"真的在测东西"的最低四条

| # | 判据 | 机械检查 |
|---|---|---|
| **T1 有断言** | 至少一条断言，且断言的是**返回值/副作用**（不是"跑完了"） | 扫测试体：`assert*`/`expect` 出现次数 ≥ 1，且**有对返回值的比较** |
| **T2 删实现必红** | 删掉实现文件 ⇒ 该文件全红 | `mv` 后跑，退出码 ≠ 0 |
| **T3 改常量必红** | 改一个边界/常量（`<`→`<=`、`+1`、`>=`→`>`）⇒ 该文件红 | 至少做**一个**变异并确认红 |
| **T4 可复算** | 连续 N 次同结果（无 flaky） | 跑 N 次，结果一致（56 篇） |

**T1 是必要条件，T2/T3 是有效性证明，T4 是可信度证明**——四条**全过**才叫"这个测试在测东西"。

## 结论

判据三句话：**覆盖率只证明"跑过"，变异才证明"测到"**（PIT：`killed` / `lived`）；
**一个测试文件至少要过 T1 有断言 / T2 删实现必红 / T3 改常量必红 / T4 可复算**；
**绿测试的五种假象**（没断言 / 断言过松 / 只测 happy path / 快照过宽 / flaky）都指向同一件事——
**它们从没回答过"改坏了会不会红"**。
最后一句：**tombstone 的价值不在删掉代码那一刻，而在"每次有人改坏时它都会红"**——
所以它必须被**自动跑**，否则只是一段文档。
