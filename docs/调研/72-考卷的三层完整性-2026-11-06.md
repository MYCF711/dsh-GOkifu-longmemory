# 钉住那一刻的世界：快照与三层完整性（2026-11-06 采集）

- 来源：一手文档（已读全文，访问日期 **2026-11-06**）：
  [PostgreSQL 18 · 13.2 Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html)。
- **范围声明**：48 篇讲派生数据、66 篇讲幂等、71 篇讲 harness 债；
  本篇只写**"考卷的三层完整性"**（输入快照 / 判据契约 / 库快照），即"**把世界固定在某一刻**"。三篇不重复页面。

## 一、快照是"某一刻的视图"，不是"当前的值"

- [外] **快照的定义**（Read Committed）："a `SELECT` query **sees a snapshot of the database as of the instant the
  query begins to run**. It never sees either uncommitted data or changes committed by concurrent transactions
  **during the query's execution**."
- [外] **但同一事务里的两次查询可以不一样**："two successive `SELECT` commands **can see different data**, even
  though they are within a single transaction, if other transactions commit changes after the first `SELECT` starts
  and before the second `SELECT` starts."
  ⇒ **"同一个进程、同一份代码"不等于"同一个世界"**——正是我们"两次运行 `claimsCount` 相同但内容不同"的形态。
- [外] **Repeatable Read 才钉住"事务开始时"**："a query … sees a snapshot as of the **start of the first
  non-transaction-control statement in the transaction**"；"successive `SELECT` commands within a single transaction
  **see the same data**."
- [外] **不稳定的视图会导致内部矛盾**（Read Committed）："it is possible for an updating command to see an
  **inconsistent snapshot**: it can see the effects of concurrent updating commands on the same rows it is trying to
  update, **but it does not see effects of those commands on other rows**."
- [外] **只读也不保证一致**："**even a read-only transaction at this level may see a control record updated to show
  that a batch has been completed but not see one of the detail records** which is logically part of the batch,
  because it read an earlier revision of the control record."
  ⇒ **"我只读，所以看到的一致"是错的**——只读事务照样能拼出互相矛盾的画面。

## 二、快照隔离 ≠ 可串行化（这就是"差 12"的类）

- [外] **Repeatable Read 就是 Snapshot Isolation**："The Repeatable Read isolation level is implemented using a
  technique known in academic database literature … as **Snapshot Isolation**."
- [外] **它仍允许序列化异常**：Serializable "works exactly the same as Repeatable Read **except** that it also
  **monitors for conditions which could make execution … inconsistent with all possible serial executions**"，
  触发即 **serialization failure**（SQLSTATE `40001`）。
- [外] **具体例子**：A 算 `SUM(value) WHERE class=1` 得 30 并写入 `class=2`；B 同时算 `class=2` 得 300 并写入
  `class=1`；两者都提交在 Repeatable Read 下合法，"but **since there is no serial order of execution consistent
  with the result**"，Serializable 会回滚其中一个。
  ⇒ **"两次跑都对"不等于"能同时成立"**：快照隔离保证**各自一致**，不保证**整体可串行**。

## 三、考卷的三层完整性（每层钉一样东西）

| 层 | 钉什么 | 机械形式 | 缺它会怎样 |
|---|---|---|---|
| **L1 输入快照** | 判据的**输入**（`at` / 题集 / 阈值） | 输入 JSON 的 `sha256` | 分数不可复算（本仓 T315） |
| **L2 判据契约** | 判定规则本身（J1–J6、作用域、容差） | 契约文件的 `sha256` + 版本号 | 换实现差 45 vs 55（T314/T316） |
| **L3 库快照** | **被测量的数据内容**（不是条数！） | `storeHash` = 所有条目内容排序后的 `sha256` | 1578 条但内容不同（T320） |

**`claimsCount` 一致 ≠ 内容一致**：条数是**基数**，不是**身份**（52 篇；57 篇的三层校验同理）。
**L3 必须用"内容哈希"**：对每条 claim 的规范化 JSON 求 hash、排序、再求总 hash——**顺序无关、内容敏感**。

## 四、"库快照"的三种钉法

| 钉法 | 形式 | 代价 | 适用 |
|---|---|---|---|
| **内容哈希（推荐）** | `storeHash = sha256(sorted(sha256(normalize(entry))))` | 便宜、可写进报告 | **考卷/回归**（默认） |
| **整份拷贝** | `cp -a store store@T` | 贵、占盘 | 复现事故现场 |
| **差异** | 只存 `base + delta` | 便宜但需重放 | append-only 库（本仓形态） |

**推荐组合**：`storeHash` 进报告（可快速比对）+ 事故时**整份拷贝**（可精确重放）+ 平时 `base+delta`（省空间）。

## 五、可复现考卷最少要钉住的（五条）

```
P1 at：判据的"决策时刻"（seq / 时间）
P2 signalHash：信号源的哈希（T318）
P3 storeHash：库内容的哈希（T320 的最终根因）
P4 judgeVer：判据契约版本（J1–J6）
P5 seed/order：任何随机与排序的显式化（66 篇：顺序固定）
```
**P1–P5 全钉 ⇒ 结论可复算；缺一条 ⇒ 那个数字只能叫"观察"。**
本仓事故序列正是**逐层补钉**的过程：`at` → `signal` → **库内容**——每次补一层，差异就缩小一次。

## 六、对照本仓（棋院）

| 步 | 缺的层 | 现象 |
|---|---|---|
| T314 | **L2 判据** | 独立实现 45 vs 主 55 |
| T315 | **L1 输入** | 钉住 `at` 后仍差 12 |
| T316 | L2 契约 | J1–J6 后降到 3 |
| T317 | L1/L3 | 稳定排序后仍 3（根因是信号漂移） |
| T318 | **L1 signal** | `signalHash` 同源后 22 → 0 |
| T320 | **L3 库内容** | 最终根因：库内容两次不同 |

**教训一句话**：**每一层缺失都会被下一层"看起来对"所掩盖**——
条数对（基数）、代码同（实现）、进程同（时间）都不等于**世界同**。
**建议**：把 `(at, signalHash, storeHash, judgeVer, seed)` 写成考卷报告的**固定头**，缺任一项即 `unverified`（46 篇三态）。

## 结论

判据三句话：**快照 = 某一刻的视图**（同一进程两次查询可看到不同世界）；
**快照隔离 ≠ 可串行化**（各自一致 ≠ 整体一致）；**只读也不保证一致**。
所以考卷必须钉住三层：**输入（at）× 判据（judgeVer）× 库（storeHash）**——
**`claimsCount` 相同不算钉住，只有内容哈希才算。**
