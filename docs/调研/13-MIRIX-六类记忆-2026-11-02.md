# MIRIX：六类记忆 + 多代理协调（2026-11-02 采集）

- 来源：[arXiv:2507.07957](https://arxiv.org/abs/2507.07957)（2025-07-10，cs.CL）。
- [外] 批评现状：多数系统是「扁平、范围狭窄」的记忆组件，无法个性化、抽象、可靠召回。
- [外] 提出六类记忆：
  1. **Core**（核心：用户/身份类稳定信息）
  2. **Episodic**（会话/事件）
  3. **Semantic**（事实/知识）
  4. **Procedural**（流程/做法）
  5. **Resource Memory**（资源，含多模态）
  6. **Knowledge Vault**（知识库/档案）
- [外] 多代理框架动态控制**更新与检索**；支持视觉/多模态记忆（截图）。
- [外] 自报：ScreenshotVQA 比 RAG 基线准确率高 35%、存储需求降 99.9%；LoCoMo 85.4%（SOTA）。附打包应用（实时截屏建库、可视化、本地存储）。

## 与我们对照

| MIRIX 类型 | 我们 | 判断 |
|---|---|---|
| Core | `u:` 用户层 claim（偏好/规则） | ✅ 同构（但我们要求同域证据才展示，见 Q18） |
| Episodic | `episode`（一局棋谱） | ✅ |
| Semantic | `claim(kind=fact/rule/semantic)` | ✅ |
| Procedural | `joseki`（定式，每招溯源）+ `preference` | ✅ 同构，且我们多了"定式准入门槛" |
| Resource Memory | 主题 `file/tool/repo/dependency` + 相关边 | ✅ 部分同构（不含多模态） |
| Knowledge Vault | **没有独立层**（我们不建人可读知识库） | 有意不做：面向模型，不做知识页 |
| 多代理协调更新/检索 | 多成员裁决（L2）+ 聚合器落账 | ✅ 同构（我们把"写权"限定在聚合器） |
| 多模态 | 不做 | 边界外 |

## 结论

MIRIX 的六类分法可以拿来**校准我们的 kind 词表**（agent 不该只有"fact"），但它的多模态与可视化应用是产品取向差异，
不进入本项目。若要借鉴，唯一有价值的是 **Procedural 与 Semantic 的显式区分**——我们已有（joseki vs claim），
但渲染时没有分档提示，可考虑在卡片排序里把定式候选明确排在失败教训之后（当前排序已如此，保持即可）。
