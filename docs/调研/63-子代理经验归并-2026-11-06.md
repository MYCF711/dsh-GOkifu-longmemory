# 子代理的经验归谁：多智能体的记忆归并（2026-11-06 采集）

- 来源：一手文档（已读全文，访问日期 **2026-11-06**）：
  [Microsoft AutoGen · Memory and RAG](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/memory.html)。
- **范围声明**：48 篇讲派生数据成本、50 篇是判据总表、52 篇讲溯源链污染；
  本篇只写**"子代理的经验归谁、怎么归并"**——记忆协议、归并键、归并率口径。三篇不重复页面。

## 一、AutoGen 的答案：记忆是**可插拔的 store**，不是 agent 内建

- [外] **记忆的五个方法**（`Memory` 协议）：`add`（加条目）、`query`（检索）、
  **`update_context`（"mutate an agent's internal `model_context` by adding the retrieved information"）**、
  `clear`、`close`。
  ⇒ **关键**：存着 ≠ 生效；**只有进了 `model_context` 才算"这个 agent 记得"**。
- [外] **每次查询都留痕**：示例里检索会产出一条 **`MemoryQueryEvent`**（`source='assistant_agent'`，内容是被取回的记忆条目）。
  ⇒ 记忆的来源**可审计**（哪一次查询、取了哪几条）——这正是"归谁"的观测面。
- [外] **`ListMemory` 的取舍写得很直白**："maintains memories in **chronological order**, appending the **most
  recent** memories to the model's context"；"designed to be **straightforward and predictable**, making it
  **easy to understand and debug**." ⇒ 归并策略宁可**简单可预测**，不要"聪明"。
- [外] **agent 的调用约定 = 只传新消息**："Agents are expected to be **stateful** and this method is expected to be
  **called with new messages, not complete history**." ⇒ 这是**归并的边界**：父子之间传的是**增量**，不是全量历史。
- [外] **该不该有子代理，文档给了判据**："Teams are for **complex tasks that require collaboration and diverse
  expertise**. However, they also demand **more scaffolding to steer** compared to single agents… **start with a
  single agent for simpler tasks**, and transition to a multi-agent team when a single agent **proves inadequate**."

## 二、"归并 vs 独立成记忆"的三条机械判据

| # | 判据 | 检查 | 不过关的含义 |
|---|---|---|---|
| **M1 工作分解** | 子代理的任务是否是父任务**可分解的一部分**（父局能指出"我要它做这件事"）？ | 在父局的 `tool/call` 里能找到派单 | 它是**独立项目**，不是父局的一部分 |
| **M2 可验证** | 子代理的失败/产出能否**指回**父局的某个 action/seq？ | `(parentEpisode, subEpisode, seq)` 可解析 | 归并了也**追溯不了**，等于污染（52 篇） |
| **M3 scope 一致** | 父子 `scopeKey` 是否相同？ | 字符串比较 | **不同 scope ⇒ 不归并**（跨 scope 是越界，不是归并） |

**三条全过 ⇒ 归并；M1 不过 ⇒ 独立成记忆；M3 不过 ⇒ 独立 + 标 `cross-scope`**（不是"归并失败"）。

## 三、归并的键与去重

**键 = `(parentEpisode, subEpisode, seq)` 三层**，缺一不可：

- `parentEpisode`：**归到谁**（父局是经验的归属者）；
- `subEpisode`：**来自哪**（子局是证据的出处）；
- `seq`：**哪一条**（事件级唯一）。

**去重**：同 `(subEpisode, seq)` 只记一次（幂等）；同 seq 但 quote 不同 ⇒ **保留先到 + 标 `disputed`**（46 篇三态）。

> 反例（我们踩过的）：把**归并键当成"路径字符串"**。路径是**实现细节**（换个目录、换个挂载点就变），
> 不是**身份**（52 篇：身份应是 `(ep, seq)`）。

## 四、"归并率"怎么测（三个读数，缺一不可）

```
mergeRate        = 已进入父局的子代理失败条数 / 子代理失败总条数
orphanFailures   = 子代理失败里，父局**找不到**对应 support 的条数
crossScopeSkipped= 因父子 scope 不同而**本就不该**归并的条数
```

- **分母**：所有 `delegationDepth > 0` 的 episode 的 failure 边数；
- **分子**：在父局 `claims[].support` 里能找到对应 `(subEpisode, seq)` 的条数；
- **恒等式**：`分母 = 归并 + orphan + crossScopeSkipped`——**对不上就说明口径有洞**。

**为什么必须单列 `crossScopeSkipped`**：否则"没归并"（缺陷）与"不该归并"（正确行为）会混成一个数，
于是**归并率既不能证明也没法改进**（本次 10% 就有这个风险）。

## 五、对照本仓（棋院，写作时点实测）

```
子代理局 726 · 带失败 530 · 失败总数 2939
旧归并率 10.00%（且只在"路径字符串完全一致"时才归并）
⇒ 约 2600+ 条子代理失败没有进入父局 claim
T293/T294 修复后：归并率 98.49%，且已接进归档管线（每次归档自动归并）
```

- **旧实现的错**：归并键用了**路径字符串**——路径是**实现细节**，换个目录就归并失败。
  按第二节 **M2**，它连"可验证"都不过：`(subEpisode, seq)` 一直是对的，但代码没用它。
- **剩余 1.51%** 必须按第四节拆开：是 `orphanFailures`（真缺陷）还是 `crossScopeSkipped`（正确跳过）。
  **不拆开就等于把 1.51% 的两种含义混成一个数**。
- **AutoGen 那条"只传新消息"**正好解释了我们的修法为什么对：归并不需要把子局的完整历史塞进父局，
  只需要**把子局的失败按 `(subEpisode, seq)` 挂上去**——增量挂载，不是历史拷贝。
- **"先单 agent"**（AutoGen）也提醒：子代理的价值是**可分解的协作**；若某类子代理从不需要父局知道结果，
  那是 M1 不过，应该**独立成记忆**而不是硬归并。

## 结论

判据三句话：**三条全过才归并**（M1 可分解 × M2 可追溯 × M3 同 scope）；
**归并键是 `(parent, sub, seq)` 三层，不是路径字符串**；
**归并率必须三读数**（mergeRate / orphan / crossScopeSkipped，恒等式要闭合）。
最后一句：**子代理干的是父局的一部分活，但"归谁"由父局的派单决定，不由路径决定**——
路径会变，`(ep, seq)` 不会。
