# 派生数据该不该存在：物化视图的成本与"现算"（2026-11-05 采集）

- 来源：两份一手文档（均已读全文，访问日期 **2026-11-05**）：
  [PostgreSQL 18 · REFRESH MATERIALIZED VIEW](https://www.postgresql.org/docs/current/sql-refreshmaterializedview.html)、
  [Azure Architecture Center · Materialized View pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)
  （页面标注 "Last updated on 2026-09-25"）。
- **范围声明**：47 篇讲**低频能力该继续投/降期权/删**（生命周期判断），本篇讲**"多一层派生数据"本身的成本结构**——
  维护代价、失效窗口、什么时候该退化成现算。两篇相邻但不同面，无重复页面。

## 一、PostgreSQL：刷新是"整体替换 + 锁 + 唯一索引门槛"

- [外] **刷新是破坏性的整体替换**："`REFRESH MATERIALIZED VIEW` **completely replaces the contents** of a
  materialized view… **The old contents are discarded.**" 且需要 `MAINTAIN` 权限。
- [外] **不加 `CONCURRENTLY` 就会挡读**："Without this option a refresh which affects a lot of rows will tend to use
  fewer resources and complete more quickly, but **could block other connections which are trying to read** from
  the materialized view."
- [外] **`CONCURRENTLY` 有硬门槛**：必须"at least one **`UNIQUE` index** on the materialized view which uses only
  column names and includes all rows; that is, **it must not be an expression index or include a `WHERE` clause**"；
  且"**only one `REFRESH` at a time** may run against any one materialized view"；并且"can only be used when the
  materialized view is **already populated**"。
- [外] **`WITH NO DATA` 会留下不可扫描的视图**："If `WITH NO DATA` is specified no new data is generated and the
  materialized view is left in an **unscannable state**."（且与 `CONCURRENTLY` 互斥。）
- [外] **刷新不保证保持顺序**：即使在定义里有 `ORDER BY`，"`REFRESH MATERIALIZED VIEW` does not guarantee to
  preserve that ordering"——派生层会丢掉源数据的一部分性质。

## 二、Azure：派生层是"可丢弃的缓存"，成本在失效信号

- [外] **合法性前提：可完全重建**："A key point is that a materialized view and the data it contains are
  **completely disposable** because they can be **entirely rebuilt** from the source data stores."
  查询方"treat the projection as **read-only**"，且"it's a specialized **cache**"。
- [外] **失效信号丢了会静默供旧数据**："If the activation signal that triggers view regeneration is lost or
  delayed — for example, a missed change-feed event or a failed scheduled task — **the view silently serves stale
  results**. Monitor refresh recency and **alert when the view age exceeds the acceptable staleness window**."
- [外] **刷新成本随源数据量与转换复杂度增长**："Regenerating a view consumes compute resources **proportional to
  the volume of source data and the complexity of the transformations**… the compute cost of refresh can be a
  significant cost driver." 事件驱动刷新若源数据变化很快，"can lead to **excessive overhead**"。
- [外] **覆盖的查询越多，存储成本越难接受**："Materialized views tend to be **specifically tailored to one or a
  small number of queries**. If many queries are used, materialized views can result in **unacceptable storage
  capacity requirements and storage cost**."
- [外] **重建失败时要选策略**："if the refresh process itself fails midway… determine whether the workload should
  serve the previous complete view, a partially updated view, or no view at all"；最稳妥是"**atomic publication or
  versioned replacement**"——旧版继续服务，新版建好并验证后再切换。
- [外] **三种情况不建议用**（原文 "This pattern might not be suitable when"）：① "**The source data is simple and
  easy to query**"；② 源数据变化很快或无需视图即可访问（"avoid the processing overhead of creating views"）；
  ③ "**Consistency is a high priority**"（视图可能不总与源数据一致）。
- [外] **派生层也要被当成可部署物管理**："Treat view definitions as deployable artifacts managed through source
  control and CI/CD… Without lifecycle management, view definitions can **drift between environments**"——
  即派生层自带一份"定义漂移"风险。

## 对照本仓（棋院）

**本文写作时点的实测（仅此一节）**：合流的去重收益上限 **5.5% 卡片长度**；
合并节点 **39 个**、成员 **96 个**；维护面 = **3 个模块 + 十道闸里的 2 道**（`budgetShare = 5.5%` 即"维护成本超过它就不该存在"）。

### 判据（三条出路，各自的可测条件）

| 出路 | 可测条件（全部满足才成立） |
|---|---|
| **落库保留**（作为一等派生数据） | ① 读路径**高频**使用（每次注入都要它）；② 单次重算成本 **> 阈值**（例如 > 秒级或 > 预算的 10%）；③ 收益/成本比 **> 1**（`budgetShare` 能覆盖维护面）；④ 有**失效信号**且能监控陈旧度 |
| **退化成现算**（报告/读时算，不落库） | ① 收益真实但**小**（不能覆盖维护面）；② 重算**便宜且确定**（同一输入同输出、秒级以内）；③ 源数据**简单易查**（Azure 的第一条"不适合"判据，正好是我们） |
| **删** | ① 收益为 **0** 或机制被证伪；② 或即便退化成现算，仍需要**额外的闸/契约**才能维护（成本 > 0 却无收益） |

### 代入我们的数字

- 收益上限 **5.5%** 卡片长度 ⇒ 三条"落库"条件里，③**收益/成本比 > 1 不成立**：
  为 5.5% 的收益养 **3 个模块 + 2 道闸**，明显是负的；① 也**不成立**（不是每次注入都用得上，39 个节点只覆盖 96 个成员）；
- 但 ① 重算便宜成立（合并是确定性函数，从 store 重算很快）、② 源数据易查成立（sidecar 里 topic/claim 直取）、
  ③ 收益**非零**且机制 12/12 正确 ⇒ "删"的三个条件**都不成立**。

**结论：退化成现算（不进库、不进闸）。**
具体说：把"合并"从**持久派生实体**降级为**离线报告里的现算视图**——报告输入 store 快照、输出"若折叠能省多少行/token、
哪些组会命中"，不写回 sidecar、不参与注入决策。

### 保留的最低维护形态（如果选择"保留"而非删除）

1. **只活在报告里**：`scripts/` 下一条命令，从 store 快照现算；产物是**带生成时间戳与 store 版本的 JSON/MD**，
   不是 sidecar 里的一等条目（Azure 的"completely disposable"）。
2. **闸退出关键路径**：十道闸里那 2 道改为**报告内断言**——失败只让报告变红，**不阻断注入**（阻断能力要另立预算）。
3. **不做失效链路**：正因为没有"视图新鲜度"要维护，就不需要事件信号、不需要陈旧度告警（Azure 列的最大风险项直接消失）。
4. **留下重新落库的触发条件**（写死，避免拍脑袋）：当报告显示"折叠收益 ≥ 10% 卡片长度"**且**连续多轮稳定成立时，
   才重新评估落库；届时按 Azure 的 **atomic publication / versioned replacement** 建新版再切换。
5. **契约措辞**：把 `mergedInto` 明确定义为**可现算的派生映射**（允许缓存，但缓存可随时丢弃、必须能从 store 重建）——
   这条比实现更重要：**不能从源重建的派生层不是派生层，是第二份真相**。

### 能借的 / 不借的

- ✅ **借**：Azure 的"完全可丢弃 + 可整体重建"作为**合法性前提**；"失效信号丢失 ⇒ 静默发旧数据"作为**风险清单**；
  "源数据简单易查 ⇒ 不该建视图"作为**退出判据**；"版本化替换/原子发布"作为将来落库时的**切换协议**；
  PostgreSQL 的 `CONCURRENTLY` 门槛（**唯一索引 + 一次一个 + 表已填充**）作为"派生层要付的机械代价"的证据。
- ⛔ **不借**：把派生层当**缓存之外的真相**（我们不做双写、不改源）；也不借"事件驱动刷新"（我们没有事件流，
  且它正是 Azure 点名的 `excessive overhead` 来源）。

## 两条可复用结论

1. **派生层的真实成本不在存储，而在"失效与一致性"**：Azure 把最大风险写成"信号丢了就静默供旧数据"。
   收益只有 5.5% 时，为它养一条失效链路（信号 + 陈旧度告警 + 重建失败策略）显然不划算——
   **现算把这条链路整体消掉**，这是"退化成现算"最硬的论点。
2. **"可丢弃"是派生层的定义性属性**：能整体重建 ⇒ 可以任意降级为报告；不能 ⇒ 它就是第二份真相。
   判据里因此可以写一条极简的：**这条派生数据现在删掉，能不能在无人记得它的情况下从源重建？** 不能 ⇒ 不该存在。

## 结论

**退化成现算**（离线报告里算，不落库、不进闸、不建失效链路）。
它不是"删"——5.5% 是真的、机制是对的；也不是"保留落库"——3 个模块 + 2 道闸换 5.5% 的上限收益，账算不平。
最省事的落点：一条报告命令 + 一条契约措辞（`mergedInto` 是可重建的派生映射），
其余复杂度（闸、信号、陈旧度）全部随"不落库"一起消失。
