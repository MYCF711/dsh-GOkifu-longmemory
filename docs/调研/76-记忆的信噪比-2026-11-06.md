# 多少噪声算太多：阈值、稳态与清理形态（2026-11-06 采集）

- 来源：一手文档（已读全文，访问日期 **2026-11-06**）：
  [PostgreSQL 18 · 24.1 Routine Vacuuming](https://www.postgresql.org/docs/current/routine-vacuuming.html)。
- **范围声明**：61 篇负向对照、67 篇信息密度、69 篇为什么记失败、73 篇怎么写教训；
  本篇只写**"多少噪声算太多、怎么清"**——阈值公式、稳态目标、清理形态。四篇不重复页面。

## 一、噪声不会被立即删除，只会被"标记可用"

- [外] **旧版本不立刻消失**："an `UPDATE` or `DELETE` of a row **does not immediately remove the old version** …
  the row version **must not be deleted while it is still potentially visible** to other transactions."
  ⇒ 记忆库的"只增不改"与 MVCC 同构：**错误条目会一直占空间**，直到被"回收"。
- [外] **标准的回收只做"标记可复用"**："The standard form of `VACUUM` **removes dead row versions** … and
  **marks the space available for future reuse**. However, it **will not return the space to the operating system**."
- [外] **彻底重写要付独占代价**：`VACUUM FULL`"**actively compacts** tables by writing a complete new version …
  **requires an `ACCESS EXCLUSIVE` lock** … **can take a long time**"。
  ⇒ **清库有两种形态**：便宜的"标记遮蔽"（读侧不再注入）与昂贵的"整库重写"。

## 二、"多少算太多"是一个**公式**，不是感觉

- [外] **阈值公式（原文）**：
  `vacuum threshold = Minimum(vacuum max threshold, vacuum base threshold + vacuum scale factor * number of tuples)`
  ⇒ **绝对下限 + 随规模增长的相对项 + 上限**——三件套让阈值**随库变大而自适应**。
- [外] **但目标不是最小体积**："the idea is **not to keep tables at their minimum size**, but to maintain
  **steady-state usage of disk space**: each table occupies space equivalent to its minimum size **plus however much
  space gets used up between vacuum runs**."
  ⇒ **追求 0 噪声是错的**；正确目标是**稳态**。
- [外] **固定周期会失效**："if a table has an **unexpected spike** in update activity, it may get **bloated** to the
  point that `VACUUM FULL` is really necessary. Using the autovacuum daemon **alleviates** this problem, since the
  daemon schedules vacuuming **dynamically in response to update activity**."
  ⇒ **按活动量触发**，而不是"每月清一次"。

## 三、不清的后果有**预警线**

- [外] **累积到临界会灾难性**：XID 回绕"would suffer … **catastrophic data loss**"；必须"vacuum every table …
  at least once every two billion transactions"。
- [外] **提前 4000 万事务发警告**："the system will begin to emit **warning messages** … 'database must be vacuumed
  within 39,985,967 transactions'"；低于 300 万时**直接拒绝写**。
  ⇒ **噪声率也需要一条"预警线"与一条"拒写线"**：到预警线报警、到红线停止注入。

## 四、"噪声"的四种定义（本仓口径）

| # | 定义 | 机械检查 | 本仓分辨率 |
|---|---|---|---|
| **N1 不是真失败** | 没有错误原文（E1） | `errorSnippet` 为空或非该次失败 | A1 门已排 **53.76%** |
| **N2 无依赖链** | 说不出"谁因此不可用"（X3） | X3 缺失 | 511 条中仅 **279（54.60%）** 有；重跑后 **58.90%** |
| **N3 无恢复条件** | 没有可执行恢复步骤（X4） | 缺 E3 | 仅 **3.98%** 可机械找到 |
| **N4 无失效条件** | 不可被反驳（X5） | 缺 E4 | 覆盖 **0%** |

**噪声率定义（推荐）**：
`noiseRate = (缺 N1 或 N2 的条目) / 总条目`——只算**硬缺**（真失败 + 依赖链），
不算 N3/N4（那是**质量债**，不是噪声）。

## 五、"多少算太多"的判据（三档阈值）

| 档 | 条件 | 动作 |
|---|---|---|
| **绿** | `noiseRate ≤ 10%` | 稳态，只按公式触发清理 |
| **黄（预警）** | `10% < noiseRate ≤ 30%` | **报警 + 停止新增采集**，先修抽取规则（75 篇） |
| **红（拒用）** | `noiseRate > 30%` | **停止注入**该类别，整类重跑抽取（"VACUUM FULL"） |

**为什么是 30%**：这是**本仓自定**门槛（PG 的 40M/3M 是它的单位，不是我们的）；
依据是"噪声条目会挤占卡位"（67 篇：注意力预算），三成噪声意味着**top-5 里平均 1.5 条是假的**。

## 六、一条记忆留在库里的门槛（四条）

```
R1 有真失败（N1 通过）
R2 有依赖链（N2 通过；缺 → state="observed"，不进注入）
R3 有恢复条件（N3；缺 → 降权，仍保留）
R4 有失效条件（N4；缺 → 只作参考面，不作主证据）
```
**R1 与 R2 是"留库"门票**（缺则**遮蔽**，不删）；R3/R4 决定**排序位置**，不决定去留。

## 七、对照本仓（棋院，写作时点实测）

- **1105 条** → A1 门（N1）排除 **53.76%** → 剩 **511 条** → 其中 **279（54.60%）有 X3**；
  重跑抽取后 **58.90%**，**210 条是永久损失**（原件里根本没有目标字段，75 篇 L1 判死）。
- 按第四节：`noiseRate`（缺 N1 或 N2）≈ **1 − 0.589 × 0.4624 ≈ 73%**（粗略量级）⇒ **红档**。

  ① **停止注入**该类（不进卡位）；
  ② **重跑抽取**修 N2（原件有的可修）；

  ④ **不追求 0 噪声**（第二节：稳态目标），先把 R1/R2 补到 ≥90%。

## 结论

判据三句话：**噪声不会被删，只会被标记**（标准回收只做"可复用"）；
**"多少算太多"是公式不是感觉**（基数+比例+上限，且**目标是稳态而非清零**）；
**清理分两档**（遮蔽/降权 vs 重跑抽取）。
最后一句：**报警线比清理更重要**——
PG 会在灾难前 4000 万事务就开始喊；我们的 `noiseRate` 也需要一条**提前喊**的线，否则等发现时已经全是噪声。
