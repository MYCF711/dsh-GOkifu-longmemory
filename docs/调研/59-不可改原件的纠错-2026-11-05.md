# 不能改原件时怎么纠错：反向、重放与更正记录（2026-11-05 采集）

  [Martin Fowler · Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)（2005-12-12）、
  [git-revert(1)](https://man7.org/linux/man-pages/man1/git-revert.1.html)（Git 2.55.0 手册）。
- **范围声明**：48 篇讲派生数据成本、50 篇是判据总表、52 篇讲溯源链污染、57 篇讲校验三层次；
  本篇只写**"原件错了但不能改，怎么纠"**——反向事件、重放、更正记录、以及 `supersededBy` 与 `invalidated` 的分工。四篇不重复页面。

## 一、Event Sourcing：纠错的正统做法是"反向 + 重放"

- [外] **ES 的定义**："Event Sourcing ensures that **all changes to application state are stored as a sequence of
  events**."；由此得到三个设施：**Complete Rebuild**（"We can discard the application state completely and rebuild
  it by re-running the events"）、**Temporal Query**（"determine the application state **at any point in time**"，
  甚至可以有多条时间线，类似版本控制的分支）、**Event Replay**（"If we find a past event was **incorrect**, we can
  compute the consequences by **reversing it and later events and then replaying the new event and later events**"）。
- [外] **反向要"存差"或"存前值"**："Reversal is the most straightforward when the event is cast in the form of a
  **difference**." 例子：`add $10` 可逆；`set account to $110` **不可逆**——"I don't have enough information to
  **recreate the past value**"。若事件不是差值形式，"the event should **ensure it stores everything needed for
  reversal**"。
- [外] **reversal 不是必需品**："all the capabilities of reversing events can be done instead by **reverting to a
  past snapshot and replaying the event stream**. As a result, **reversal is never absolutely needed for
  functionality**."——它只影响**效率**（"reversing a few events is much more efficient than … forward play on a lot
  of events"）。
- [外] **Bug 修复的标准姿势 = 改逻辑 + 重放**："Bug fixes occur when you look at past processing and realize it was
  incorrect. **For internal stuff this is really easy to fix, all you need to do is make the fix and reprocess the
  events.** Your application state is now fixed to what it should have been."
  ⇒ **不碰历史，重算派生**——这正是"只增不改"下的正解。
- [外] **副作用会毁掉重放**："if these events cause **update messages to be sent to external systems**, then things
  will **go wrong** because those external systems **don't know the difference between real processing and replays**."
  解法：**Gateway 在 replay 模式下关掉外发**（"the domain logic should never care about the context"）。
- [外] **双时态是深水区**："This may lead into **bi-temporal behavior**: 'reverse this event according to the rules
  for Aug 1 that we had on Oct 1 and replace it according to the rules for Aug 1 that we have now'. Clearly this
  stuff can get **very messy** — **don't go down this path unless you really need to**."

## 二、git-revert：纠错是"追加一次反向提交"，不是"改掉那次提交"

- [外] **定义**："Given one or more existing commits, revert the changes that the related patches introduce, and
  **record some new commits that record them**."——**历史只追加**。
- [外] **"改原件"的代价被写进警告**：`git revert` 要求工作树干净；想丢弃未提交更改要用 `git reset --hard` /
  `git restore --source`，而"**Take care with these alternatives as both will discard uncommitted changes**"。
  ⇒ 改原件 = **不可逆地丢东西**。
- [外] **合并产物必须指定主线**：`-m <parent-number>`——"Usually you **cannot revert a merge** because **you do not
  know which side of the merge should be considered the mainline**."（我们的 553 处重指正是**合并/迁移产物**。）
- [外] **revert 一个 merge 是不可逆的语义决定**："Reverting a merge commit **declares that you will never want the
  tree changes brought in by the merge**. As a result, **later merges will only bring in tree changes introduced by
  commits that are not ancestors of the previously reverted merge**."
- [外] **必须写理由，且反复 revert 会腐化**："it is **strongly recommended to explain why** the original commit is
  being reverted"；"repeatedly reverting reverts will result in increasingly **unwieldy subject lines**, for example
  *Reapply \"Reapply \"<original-subject>\"\"*."——**更正记录本身也会腐化**，要合并/重写说明。

## 三、`supersededBy` 与 `invalidated` 的分工（机械判据）

| 维度 | **加 `supersededBy`** | **标 `invalidated`** |
|---|---|---|
| 语义 | **旧值被新值替代**（有更好的后继） | **本身是错的**（无后继，或后继未知） |
| 典型触发 | 判据更新、口径升级、版本演进 | 假阳性、指针指错、数据损坏 |
| 读侧动作 | 优先读**后继**；旧条保留可追，**不进注入** | **过滤掉**（不进卡位/看板），但**保留可追** |
| 谁产生 | 新的正确条目（supersede 是"进步"） | 一条**更正记录**（谁、何时、为什么、依据） |
| 可撤销性 | 可撤回（后继也可再被 supersede） | 需要 correction 事件（不是改状态就完） |
| 本仓例子 | 55 篇的判据更新、6 篇的新结论 | **7 条假阳性 claim**、**651 处 `occurredAt` 错**、52 篇的悬空 `mergedInto` |

**一句话**：**`supersededBy` 记录"进步"，`invalidated` 记录"错误"**。
把两者混用（我们现在的做法），会让**版本演进**与**数据坏了**在库里长得一样——**读侧就无法决定该不该信**。

## 四、"原件错误但不可改"时的读侧动作 + 决策树

**读侧四种动作**（按代价从低到高）：**过滤**（不读它）→ **降权**（读但排后）→ **标注**（读但带警告）→ **重抽取**（从源重算）。

| 步 | 问题 | 动作 |
|---|---|---|
| 1 | 错误在**派生层**（可从源重算）？ | **重抽取**（Fowler：改逻辑 + `reprocess`），**不动原件** |
| 2 | 错误在**指针**（`seq`/`edgeId` 指错，但目标唯一可定）？ | **加 correction 记录**（`seqRewrittenFrom` + 重算 `occurredAt`），原字段保留 |
| 3 | 错误是**条目本身为假**（假阳性）？ | **标 `invalidated` + 读侧过滤**（**不降权**——假的不该占卡位） |
| 4 | 错误**无法判定真假**（缺证据）？ | 标 **`disputed`** + 读侧**降权**（46 篇三态） |
| 5 | 错误**来源不明**？ | 留 `unverified`，**不吸收成通过**，进报告 |
| 6 | 错误**影响外部副作用**？ | 先把 Gateway 的**外发关掉**再重放（Fowler 的 replay 保护） |

**三条铁律**：① **原件永不删**（只标不改）；② **纠错本身也是条目**，可被再次 supersede（否则更正记录无法被更正）；
③ **重放必须无副作用**，否则"重算"会把错误再发一遍。

## 五、对照本仓（棋院，写作时点实测）

- **553 处 `support.seq` 被重指**（其中 **651/1418 处 `occurredAt` 没同步**）⇒ 决策树 **第 2 条**：
  这是**指针错**，不是内容假 ⇒ 加 **correction 记录**（`seqRewrittenFrom` + 由规则重算日期），
  但**更好的做法是第 1 条**——归档管线**重跑**（Fowler 的 `reprocess`），因为 `occurredAt` 完全可从 `seq` 重算。
- **7 条"测试全绿被当失败"的假阳性 claim** ⇒ 决策树 **第 3 条**：**标 `invalidated` + 读侧过滤**。
  注意**不是降权**：它们占 top-5 卡位、污染 overlap 排序，只要还在候选里就是**纯损耗**（53 篇的归因问题）。
- **现在的做法只有 `supersededBy`**（AGENTS §2.3）⇒ 建议补两个字段：
  `invalidated: { by, at, why, evidence }` 与 `correction: { from, to, why }`，
  并把**读侧规则**写进契约：**`invalidated` 一律不进注入；`supersededBy` 只读后继；`disputed` 降权**。

## 结论

判据三句话：**纠错=追加（revert/replay），不是改写（reset）**；**`supersededBy` 记进步，`invalidated` 记错误**，
两者混用会让读侧无法决定信不信；**能重算的就重算（reprocess），不能重算的才标状态**。
最后一句来自 git 的手册：**改原件的代价是"丢弃未提交的更改"**——
在"只增不改"的库里，这条代价被消掉了，但换来的是**每一条错误都要靠更正记录去抵消**，
所以**更正记录本身必须能被更正**（否则库会慢慢被"Reapply \"Reapply …\""淹没）。
