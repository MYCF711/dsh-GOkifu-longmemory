# 交付不等于使用：8,000 局 SWE-bench 上"记忆被用了吗"的使用点评测（2026-11-08 采集）

- 来源：[arXiv:2611.01718](https://arxiv.org/abs/2611.01718)（**Delivered, Not Used: Evaluating Agent Memory at Its Point of Use**；
  作者 **Changran Xu / Zeju Li / Qiang Xu**，The Chinese University of Hong Kong, Department of Computer Science and Engineering；
  v1 2026-11-01 09:09:43 UTC（无 v2）；正文 [HTML](https://arxiv.org/html/2611.01718) 已读 §1–§5 与附录 A.1–A.5、A.6 的部分小节，访问日期 **2026-11-08**）。
- **范围声明**：`docs/调研/00` 的 01–91 已覆盖 Mem0 / Letta / Zep / Cognee / AWS AgentCore / Memobase 等系统与大量判据篇（33–91）；本篇评测的三个系统是 **MemGovern / Mem0 2.2.1 / TencentDB Agent Memory**（Mem0 已有多篇系统篇；MemGovern 与 TencentDB 是**首次出现**）。
  本篇是**第一篇"交付—使用—效果"三段式的使用点评测**（不提出新记忆系统，只测"投递出去的记忆有没有被 agent 用、用了之后发生了什么"），
  与 #42「存了却取不到（检索瓶颈）」互补：#42 拆的是 **candidates → surfaced → used** 的检索段，本篇把末端 **used → effect（有益/有害）** 补上，并给出 8,000 局的实测量级。
- **一句话结论**：[外] **任务成功率看不出记忆有没有被用**——三个记忆系统四种配置的 resolve rate 与无记忆基线相差 **≤ 0.40 个百分点、所有 95% 区间都含 0**；但同一批轨迹里 **71.5–98.6% 的投递条目不相关、51.3–79.7% 的相关条目从未被使用**；**23.2% 的"有益使用"局最终仍失败，31.3% 的"有害使用"局最终反而成功**。作者的主张：评测要从"检索"走到"使用"。

## 一、它问的问题（为什么值得看）

- [外] **现有评测只到"交付"为止**：任务成功率、检索质量、成本都**不能说明** agent 是否用了投递的记忆、以及用了之后发生了什么。
  作者原话："Task success, retrieval quality, and cost do not show whether an LLM agent used a delivered memory or what followed from that use."
- [外] **只看结果会把"记忆效应"整个吞掉**：结果相同不代表记忆相同作用——**有益的记忆可能出现在失败局里，有害的记忆可能出现在成功局里**；
  当记忆系统打不过无记忆基线时（作者引用 VibeMemBench 12 组对照里 11 组如此），也说不清是"冗余、被忽略、还是某步有用某步有害"。
- [外] **评测单元改成"一次记忆投递在上下文中的使用"**（memory delivery in context）：把「投递条目 + agent 当时已能看到的上下文 + 之后采取的动作 + 动作的后果」捆成一个可判单元。

## 二、方法：五信号 + 固定规则（可机械复核的骨架）

- [外] **上下文与信用窗口**：一次投递 `d` 把若干条目放进模型输入；`B_d` = 不含该投递文本的**先前上下文**（agent 已经能看到的东西）；
  信用窗口 `W_d(m)` 从消费步开始、到后续若干步为止；条目若被截断，还要记录 exposed text（full / clipped / unknown）。
- [外] **五个信号**（Table 1，逐条给理由、未定的记 `null`）：

  | 轴 | 信号 | 取值 | 问的问题 |
  |---|---|---|---|
  | 信息质量 | **Relevance** | true / false | 暴露的文本是否适用于**当前任务或子目标**？（注意它要求"共享机制/适用程序"，见 §三） |
  | 信息质量 | **Accuracy** | corroborated / uncontradicted / contradicted | 证据是**证实**还是**反驳**了条目所声称的事？**未被证实 ≠ 被反驳**（单列 `uncontradicted`） |
  | 信息质量 | **Novelty** | novel / confirming / redundant / undetermined | 相对 `B_d`，内容是**新的 / 补上未决假设的 / 重复既有信息的**？ |
  | 使用 | **Influence** | acted on / selected / referenced / none / undetermined | 条目在信用窗口里**实际影响**了什么？（acted on = 被执行动作使用；selected = 只是被检索到） |
  | 后果 | **Observed effect** | improved / no effect / harmed / undetermined | 归因到条目的动作，到局末看是**改善 / 无差别 / 有害**？ |

- [外] **固定规则聚合，不让裁判"自由发挥"**：`acted on + improved/no effect/harmed` ⇒ `used / unproductive / misused / unclear`；
  `selected/referenced/none` ⇒ `selected / noted / ignored`；span 级 triage 用**固定优先级** `negative > positive > unresolved > neutral`——
  **harm 优先**（一条有害条目不能被同 span 的有益条目掩盖）。
- [外] **entry-share profile**：triage 只反映"最严重的那个条目"，不反映构成；所以再加 **"span 内满足某轴的条目占比"** 的均值（一条有用的 span 和十条都有的 span 不再同分）。
- [外] **程序化证据检查**：裁判必须**完整读**任务、先前上下文索引、消费步及其前一步；`acted on` 必须给锚点且落在信用窗口内；
  引用步必须整步读完（search 摘要不计 coverage）；不合格答案可带违规反馈重答，超出预算则记 error span。
- [外] **实验规模**：SWE-bench Verified **全部 500 题**（12 个 Python 仓库）、4 个配置 × 4 次运行 = **8,000 个记忆局**（另有 4 次无记忆基线）；
  agent = **mini-SWE-agent 2.4.6**（gpt-6-luna，medium reasoning）；记忆系统 = **MemGovern**（固定经验卡库）/ **Mem0 2.2.1**（L 与 L+G 两种 scope）/ **TencentDB Agent Memory**；
  裁判 = **DeepSeek-V4.1-Flash-1017**（temperature 0、medium thinking，每 span 最多 250 次调用）。

## 三、它最硬的两条发现（都能直接对上我们的痛点）

### 3.1 结果层几乎完全分不开，使用层差十倍

- [外] **resolve rate**：MemGovern 73.4±0.6、Mem0(L+G) 72.7±0.7、Mem0(L) 72.8±0.6、TencentDB 72.7±0.8、**无记忆 73.0±1.5**；
  与基线的差最大 **+0.40pp**，**每个 95% 区间都含 0**；而基线自身四次运行就在 71.8–75.0% 之间波动。
- [外] **成本**：相对基线，每局成本 **MemGovern +8.8%**、Mem0 +37.7% / +38.1%、**TencentDB +293.2%**。
- [外] **使用层却分得开**：MemGovern 平均相关条目占比 **15.08%**，Mem0 只有 **1.42–1.43%**；TencentDB 28.48%（其中 persona 块贡献 18.0pp，其余 15.9%）；
  MemGovern 的 token 效率 **50.50 条有益条目/百万投递 token**，是其它配置 **3.08–4.92** 的十倍以上；但 MemGovern 的有害占比也最高（**0.36%** vs 0.01–0.03%）。
- [外] **两个共性瓶颈**：① **71.5–98.6%** 的 span 条目平均**不相关**；② **51.3–79.7%** 的相关条目**从未被使用**（没被执行、选择或引用）。
  结果：agent 平均只 acted on **0.40–4.08%** 的条目；有益条目只到达 **3.65–7.05%** 的局。
- [外] **714 条 acted-on 条目**的构成：**421 有益 / 16 有害 / 64 无差别 / 213 未定（29.8%）**——"被用了"不等于"用对了"。

### 3.2 结果会掩盖方向：有益也可能失败，有害也可能成功

- [外] **89/383（23.2%）** 有"有益使用"的局**最终失败**；**5/16（31.3%）** 有"有害使用"的局**最终成功**。
- [外] **67.9%（260/383）** 的有益使用发生在"基线四次都解得出"的题上；而在"基线四次都解不出"的题上，**73/79** 的有益使用局仍然失败——**局部有帮助 ≠ 总分变化**。
- [外] 反过来：记忆相对基线的胜负（+17.3–20.4 题 / −15.3–21.4 题）**和基线自身两次运行之间的差（18.1 题/方向）同量级**；
  71 个"记忆才有、基线没有"的成功里只有 **6** 个含有益使用；87 个"记忆才失败"里只有 **1** 个含有害使用——**大多数输赢根本没有 acted-on 条目**。

## 四、与我们最相关的一条判据原文（坑类/工具族的外部依据）

- [外] **Relevance 的定义**（§3.4 原文）：
  > "Sharing a topic, file, or function is insufficient; information drawn from another situation must state a **shared mechanism** or an **applicable procedure**."
  （只共享主题、文件或函数**不够**；从另一个情境抽取的信息必须给出**共享的机制**或**可适用的程序**。）
- [外] **Novelty 的定义**：相对 agent 当时已能看到的上下文——`redundant` = **重复既有信息**；作者实测重述很惊人：
  TencentDB **88.4%** 的投递是重述、Mem0 **78.2%**；Mem0 里"**仍在 agent 上下文中的条目的副本**"占投递 token 的 **68.1%**。
- [外] **重述不是免费的**：它占上下文预算、可能挤掉有用内容；作者把"预览/索引"算作**选择**（709 条 MemGovern 预览 + 1,500 条 TencentDB catalog/index/preview 引出了更完整的阅读），
  真正供给有益条目的是**完整卡片/任务召回/完整 skill**（分别 96.4% / 75.8% / 86.0% 的有益条目，只占 12.5% / 13.0% / 2.0% 的投递 token）。

## 五、没读到 / 不能确认的部分（如实标注）

1. **代码/数据未找到公开仓库**：正文与附录没有给出 MemUse 的代码或数据 release 链接（只给了被引系统的链接），**无法核对实现**。
2. **裁判与人的一致率未测**：作者在附录明确写 "**Agreement with human judgments has not been measured in this evaluation.**"——五信号全部由 LLM 裁判给，**没有人类金标校准**。
3. **裁判能看到 gold patch**：附录 A.5.3 说每个 evidence package **包含任务的 gold patch 作参考**（排除 harness outcome）——这可能抬高 relevance/accuracy 的判定质量，也意味着**不能直接搬到没有标准答案的生产环境**。
4. **只在一个基准上**：SWE-bench Verified（500 题、12 个 Python 仓库、单一 agent 框架与模型），**没有跨领域/跨语言/跨 agent 的复现**；论文没有单列"Limitations"章节。
5. **我只读到附录 A.1–A.5 与 A.6 的部分**：A.6 的逐配置明细表（Table 7–12）与 A.2 的信号绑定细节**未逐格核对**；正文表格数字以 HTML 版为准。
6. **"投递"的记录方式依赖 observer 重建**（TencentDB 是 proxy 注入、Mem0/MemGovern 是 host/agent 调用），不同系统的"投递"边界不完全同构，作者也承认这是记录/评估口径问题。

## 六、对照本仓（棋院）

| **交付 ≠ 使用 ≠ 效果**（五信号） | 我们的 T9 ablation 主要看 A/B 两臂的**结果差**；`evidence/M7-*` 与 #42 才有 candidates→surfaced→used 三段 | ✅ **可借**：T9 必须加"投递/被用/有益/有害"计数；**resolve 差 ≈ 0 不能推出"记忆没用"** |

| **Novelty 是独立轴**（redundant/重复投递） | 我们的 `abstain.reason` 四类：cross-scope / stale / low-confidence / no-relevant-claim；**没有 redundant** | ✅ **可借**：加第 5 类 `redundant`（claim 与当前上下文/本局已注入行重复）——**"重述"不是"不相关"，但不该占注入预算** |

| 裁判用 LLM 五信号 | 本仓 §2.3 **禁止模型评分参与晋升/排序/存留** | ⛔ **不借评分**；只借**信号分类法**与**机械计数**（delivered/acted-on/beneficial/harmful） |

## 七、能借的三点（都能做成机械规则）

1. **四段计数**：`delivered`（条目进入模型输入）→ `acted on`（被后续动作使用，可机械锚定到工具调用/编辑）→ `beneficial / harmful`（对最终结果或局部可验证状态的贡献，按 T9 判分口径）。
   每局记录、每臂汇总；**结果差与使用率一起报**。这是对 #42 三段的自然延伸，不需要任何模型评分。
2. **相关性判据升级为"共享机制 / 适用程序"**：claim 增加一个**可机械核对的 `mechanism` 指针**（例如共享的坑类 id、共享文件 basename + 同一错误签名、同一工具族的同一失败模式）；
   桥（`fileBasenames` / 工具族 / 坑类）只在**机制字段对上**时触发；只共享名字/主题的对继续当 hard negative。T1 的 `hard` 层正好可以用来回归这条。
3. **`redundant` 独立轴**：把"与当前上下文/本局已注入行重复"的条目单列为 `redundant`（静默丢弃、不计入 abstain 误杀），并单报 **restatement share**（重复投递 token / 总投递 token）。论文的 68.1% 说明这条能省下大量预算。

## 八、明确不借的三点（附理由）

1. **不把 agentic judge 作为常设指标或决策依据**：五信号全部由 LLM 裁判给、**与人判一致率未测**、且要读 gold patch——违反本仓"计数不是打分、禁止模型评分参与晋升/排序/存留"，也不可复算。
2. **不把论文的绝对数值外推到棋院**：8,000 局 SWE-bench、mini-SWE-agent + gpt-6-luna、三个特定记忆系统——**只能借机制与量级，不能借"15.08% vs 1.42%"这样的具体比例**。
3. **不把"投递量/召回率"当"记忆价值"**：论文自己的数据说明投递多不等于有用（TencentDB 投递最多、成本 +293%，但只有部分条目有益）；我们的验收也不能用"注入条数"当收益。

## 九、对本项目的可执行建议（T9 / T12 / T13 可直接排期）

1. **T9 ablation 报告加四段表**（最小改动）：每对 A/B 样本增加 `delivered / actedOn / beneficial / harmful` 四列（机械计数 + T9 的判分），报告同时给"结果差"与"使用率差"。
   若结果差 ≈ 0 而使用率有差 ⇒ 结论写"**记忆被用了但没改变结果**"，不写"记忆没用"（这正是论文 4.2/4.3 的读法）。
2. **`abstain.reason` 加第 5 类 `redundant`**：当 claim 文本与当前上下文或本局已注入行高重合（可用现有 `bigramOverlapCount` + 行级指纹）⇒ `redundant`，**静默丢弃、不计入误杀**；同时输出 `restatementShare`。
3. **T11/T12 误杀率拆两档**：把"误杀"拆成 **误杀-有用**（relevant 且有证据会被 acted on/beneficial）与 **误杀-无用**（relevant 但未被用）。
   现有 17 条"可核误杀"用新口径重跑一遍，再决定 `abstain` 该不该继续收紧（论文说 51.3–79.7% relevant 条目本就不会被用，收紧的收益可能被高估）。
4. **T13 的 hard 负例回归加一列 `mechanismShared`**：给 50 条 hard 负例标三态（共享机制 / 只共享名字 / 无共享），用它验证"只共享 topic/file/function"的对在 `hasPitClassBridge` 下**不得被救回**——这是论文 relevance 定义给我们的直接回归。
