# 过程性记忆的生产化：只从「验证过的成功」编译，用成熟度与试验喂信任（2026-11-08 采集）

- 来源：[arXiv:2611.01386](https://arxiv.org/abs/2611.01386)（**Learning by Doing: Autonomously Compiling and Curating Agent Skills from Verified Traces**；
  作者 **Daniel Chalef / Peter Evans / Pavlo Paliychuk / Mehul Patel / Preston Rasmussen / Jack Ryan**（**Zep AI**）；
  v1 **2026-11-01 00:47 UTC**（无 v2；25 页、9 图、14 表）；正文 [HTML](https://arxiv.org/html/2611.01386) 已读 §1、§3、§5、§6、§7、§8、§9，访问日期 **2026-11-08**）。
- **范围声明**：`docs/调研/00` 的 01–92 已覆盖 Mem0 / Letta / Zep 的时序知识图（#27）、Cognee / AWS AgentCore / Memobase、MemUse 的使用点评测（#92）等。
  本篇是 **Zep 2026 年的生产服务 Zep Agent Skills**：不是语义/情景记忆，而是**过程性记忆**（procedural memory）——「何时用、步骤是什么、何时停」；
  也是本库第一篇讲「**如何从轨迹里编译、验证、准入一条过程**」的工程实践篇。#27 讲 Zep 的时序图（valid/invalid time），与本篇不重复。
- **一句话结论**：[外] 过程性记忆可以做成一条生产流水线：**只从强验证的成功编译**（`only successful attempt families with strong verification can support a new Skill`）→ 每一步都**引用到具体事件**、由可信代码校验 → **准入闸**（验证/适用性/冲突/评测）→ **成熟度**（provisional / corroborated / established，信任 = 成功率 95% Wilson 下界）→ 检索按**适用性过滤**、相关性不能越过过滤。三个基准 26/26 个格子为正、**+4.5 到 +18.8 个百分点**；但增益集中在**老师解过的题**（τ3：老师四试全过的题 +17.0，老师从未过的题 +0.6），**迁移未被证明**。

## 一、它问的问题（为什么不用微调、不用对话记录）

- [外] **每一轮都从同一权重、同一提示出发**：成功的运行不会改变下一次运行，同一个问题要重解、同样的错会重犯。
- [外] 三条路各有代价：**微调**要训练轮次、绑定单一模型、难检查难撤销，流程一变就要重训；**检索历史对话（情景记忆）**便宜，但转录很长、带着某一次实例的具体值、还可能带出后来用户不该看的数据；**过程性记忆**是第三条路（Voyager、Agent Workflow Memory、ExpeL、ACE 都证明「从经验学到的过程」能提高成功率）。
- [外] **Agent Skills 格式已经是开放标准**：一个文件夹 + `SKILL.md` + frontmatter（name/description）+ 可选文件；Claude Code / Claude Cowork / OpenAI Codex 用**渐进披露**加载（先看名字与描述，适用时才读正文）。Anthropic 2025-12 公布，2026-10 捐给 Linux 基金会 AAIF。
- [外] 格式只管**打包与加载**，不管**怎么学、怎么验、怎么版本化、怎么治理**——「在多数部署里每条 Skill 都是人写的」。Zep Agent Skills 要回答的是后半段，且是生产要求：只从验证过的尝试学、每个字段能溯源、新版本不能悄悄替换能用的版本、不把一个用户的实例数据带到另一个、删除源要移除其影响、任意框架/模型都能用。

## 二、方法：一条「验证 → 编译 → 准入 → 成熟度」的流水线

### 2.1 Trace 与验证强度（谁说的不算，谁验的才算）

- [外] 每条任务尝试记成 **Trace**：有序事件（模型轮次、工具调用、工具结果）+ 一个 outcome（**agent 自报的结果与验证结果分开存**：`An agent can report success for a task that failed`）。
- [外] **验证强度由提交验证的调用方身份决定**，不接受调用方自己声明的强度：agent 只能提交「自报」验证；工具/外部系统必须先被**注册为该命名空间的 verifier**，并声明它能断言的强度；人要有验证权限；从 Braintrust / LangSmith 这类观察/评测平台导入的分数，映射成 outcome 需要人设阈值，注册为 verifier 后算**强验证**。
- [外] **重试继承父 Trace 的 attempt family**：编译按 **attempt family** 计数——**一次失败 + 它的成功重试只算一次支撑**（`A failure and its successful retry therefore count once as support`）。这条直接决定「支撑」不被重试次数灌水。
- [外] **摘要不是证据**：Trace 关闭后由 LLM 写摘要（目标、结果、方法、有效/无效步骤、错误、**恢复**、工具），每条 claim 必须引用事件，**可信代码把对不上事件的 claim 删掉**；摘要只用于**选材**，支撑仍要回到事件。

### 2.2 Skill 的契约：适用性 与 过程 分离

- [外] 每条 Skill 版本存成**结构化契约**（不是只有一个 Markdown）：**适用性字段** = 何时用 / 何时不用 / 前置条件 / 适用工具与环境；**过程字段** = 有序步骤、决策点、**预期观察**、输出、完成判据、**停止条件**、**失败模式及其恢复（failure modes with their recovery）**。
- [外] 字段是**类型化**的，编译器可以一次只改一部分；允许空字段（新 Skill 可能还没有失败模式）。对外渲染成两种 Markdown：**给人看的全量版**（每个被引用字段标证据）与**给 agent 看的 SKILL.md**（无证据标记、省略空字段）。
- [外] 理由：单存 Markdown 带不了访问控制、证据链接、版本历史、使用结果，检索也没法按字段过滤。

### 2.3 编译：两个 LLM 角色 + 可信代码 + 「引用或留存」

- [外] **Reflector 提五种操作**：新增、**局部 patch**（只改新证据支持的字段，其余保持——全文重写会丢细节，ACE 的报告）、合并相关 Skill、**报告冲突**、不动。每条 claim 引用支撑事件。
- [外] **Curator 给每条 claim 判 supported / unsupported**，再决定操作；**冲突会把受影响 Skill 从检索里移除**，直到冲突解决；**不支持的 claim 只废掉它对应的那处改动**；Curator 会拿候选与现有 Skill 比较，**避免弱的重写替换能用的版本**。
- [外] **可信代码校验**：结构、引用能否匹配到可读事件；**修引用不改 claim、不加证据**（所以修完还要重新校验支撑）。新 Skill 必须**超出单一实例的值**：替换掉实例的标识符/名字；只有一个 attempt family 支撑时，检查更严（过程不许保留源事件的标识符，适用性必须落在证据的工具/环境内）。
- [外] **失败尝试只作对照，不能支撑过程步骤**（`Failed attempts cannot support a procedure step`）——失败可以引用为「失败模式」，但不是成功步骤的依据。
- [外] **Cite-or-retain 规则**：一次运行后，**失败的源、未验证的源、以及被已准入改动引用过的成功源**都会被消费；**成功但没被任何已准入改动引用的源会留存**，给后续运行用；一直不被用到才消费。这样证据可被后续运行重新查看，又不会无限堆积。
- [外] **结果历史**：每次提案的最终结果（准入 / 扫描器拒 / Curator 拒 / 人拒 / 评测失败 / 模型调用失败）按任务族记录，作为**不可信上下文**喂给 Reflector（只帮它避开被拒的改法，不能当支撑）。

### 2.4 准入、成熟度、信任（本仓最该抄的一段）

- [外] **准入闸**：验证、适用性、冲突、所需评测，四项都过才自动准入；**自动 / 人工**两种审批模式；可以限定只有某些任务族自动准入、某些工具的 Skill 必须人工批；**审批必须来自已认证的人**（API 凭证不能批）；跨命名空间共享也要人批。
- [外] **成熟度三档**：

  | 档 | 条件 |
  |---|---|
  | `provisional` | **1 个 attempt family** 支撑 |
  | `corroborated` | **≥2 个 attempt family** 支撑 |
  | `established` | **信任值**达到配置阈值 |

- [外] **信任 = 成功率 95% Wilson 区间的下界**；**trial** 的定义很严：一次完整或部分使用、且结果是**强验证**的成功/失败才算，放弃的尝试、结果未知的、只有 agent 自报的都不算。**验证过的失败会降低 Skill 的排序**；定时维护会**退役** agent 不用的 provisional Skill；检索不返回退役版本。
- [外] **检索**：先按**适用性过滤**（只留活跃、可读、字段匹配的），`候选 / 退役 / 未解决冲突`一律排除，**相关性不能越过这些过滤**；再按描述符的**词面得分 × search weight** 排序（search weight 只改顺序，**不能让不合格的 Skill 变可见**）；**两步渐进披露**：先返回描述符让 agent 选，再读正文。
- [外] **检索 ≠ 使用**：`Retrieval alone is not evidence that the agent used a Skill`；harness 记录 **Skill use**（版本 ↔ Trace），**只有两者的 outcome 一致、且 verifier 仍注册时**，use 才继承 Trace 的验证强度；强验证的 use 才是 trial。

## 三、结果（三个基准、26 个格子）

- [外] **主实验 = teacher-executor**：强模型（Claude Opus 5.5 最高 effort）每题跑一次 → 编译成 Skills → 弱模型（GPT-6 Luna / Claude Haiku 5.5 / DeepSeek V4.1 Flash，各 2–3 档 effort）**同题**跑「有 Skills / 无 Skills」两臂。
- [外] **规模**：τ3-bench banking **97 题 × 4 试 = 388 局/臂**；AppWorld **147 题 × 3 试 = 441 局/臂**；EnterpriseOps-Gym **625 题 × 3 试 = 1875 局/臂**。
- [外] **26/26 个格子配对差为正**，提升 **+4.5 到 +18.8 个百分点**：τ3 八格合并 **+8.6**（95% CI +5.5 到 +11.9）；EnterpriseOps-Gym **+8.4 到 +11.4**（九个区间全在 0 上）；AppWorld **+4.5 到 +18.8**（九格里八格区间在 0 上，Haiku low 那格含 0，因为无 Skills 已达 88.0%、天花板低）。
- [外] **增益来自内容，不是来自"多了个索引/工具"**：按老师是否解过分层——τ3 老师四试全过的 40 题 **+17.0**（+11.6 到 +22.3），老师从未过的 30 题 **+0.6**（−2.2 到 +4.0）；AppWorld 中「有自己 Trace 的 Skill」的 96 题 **+5.9 到 +22.2**，同场景但没有自己 Trace 的 48 题 **−1.4 到 +2.1**（GPT-6 Luna low 例外 +9.0）。作者明说两臂还有「更长的系统提示 + 多一个 read_skill 工具」两个差异，实验没有拆开。
- [外] **可靠性**：τ3 四试全过的题在 8 格里 7 格增加；AppWorld 场景通过率 9/9 格增加；EnterpriseOps-Gym 九格里**错误终态**与**缺信息停**都变少。
- [外] **成本**：长任务节省——τ3 **每个通过局 token 降 7.0% 到 44.6%**（8/8 格）；短任务吃亏——AppWorld 9 格里 7 格 token 增加（索引是固定开销）。
- [外] **迁移只有弱证据**：ALFWorld 用 Qwen3-8B 自己的 train 局编译，**valid_unseen 新房间 +32.6 点**（弱基线），失败减少 57%（RSD 37%）；EnterpriseOps-Gym 老师失败的题 +2.0 到 +5.6（八/九格区间过 0，但作者说分不清是「别的题的 Skill」还是「Skills 臂的其它差异」）。**主实验没设计迁移检验**，作者自己把它列进局限。
- [外] **负迁移的实例**：AppWorld 场景 `229360a` 的两个变体规则相反（`liked and downloaded` vs `liked or downloaded`），编译器只保留了一条，Skills 臂在该场景**两个格子输掉**；EnterpriseOps-Gym 每个格子 Skills **赢 73–94 题、输 14–32 题**（赢 = Skills 三试里过 ≥2、基线过 ≤1；输为反向）。

## 四、局限（作者自陈 + 我们的读法）

1. [外] **只从成功学**：`The compiler uses only strongly verified successes as support`，老师没解过的题就没有自己的 Skill，增益小或 0；作者把「从失败 Trace 里**已验证的子目标**编译」列为 future work（子目标可以来自 verifier 在任务中记录的检查点，或从同族 Trace 推断）。
2. [外] **迁移未证**：主实验是「重复已知任务」，不是「新任务」；要测迁移需要「共享过程、不同实例」的题。
3. [外] **Skills 臂是捆绑差异**：内容 + 更长的系统提示 + 多一个工具，三者未拆开。
4. [外] **编译器要模型**：Reflector/Curator/扫描器都是 LLM + 确定性检查的混合；我们没有这个预算，也不允许模型参与晋升/排序/存留（本仓 §2.3）。

## 六、对照本仓（棋院）

| 论文 | 棋院现状 | 判断 |
|---|---|---|
| **只从强验证的成功编译** → 覆盖率天然低 | 我们的恢复事实要求「失败 → 后来**同一命令/同一主体**成功」，真库覆盖 **37/1560 = 2.37%**（T30）；与论文同一个天花板：老师没解过的题没有 Skill | ✅ **同一个机制**：覆盖率低不是实现 bug，是「只认验证成功」的必然。**可借**：把「已验证的子目标」也算进来（见 §九-1） |
| **attempt family 计数**：失败 + 成功重试只算一次支撑 | 我们的 recovery 索引按 support 事件挂，**没有「尝试族」概念**；同一命令重试会多次支撑 | ✅ **可借**：支撑数按 attempt family 去重，否则「2 局支撑」会被重试灌水 |
| **Skill 契约 = 适用性 + 过程（含失败模式与恢复）** | 事实型卡只有「哪一局、跑了什么、报了什么错、日期」；`why`/`scope` 是散的，**没有适用性字段、没有预期观察、没有恢复字段的结构** | ✅ **可借**：事实型卡补三栏（适用 / 观察 / 恢复），仍然全是事实、不含祈使句——这可能是「事实型弱于指令式」的直接解释：事实卡缺的正是适用性与预期观察 |
| **成熟度 + Wilson 下界 + trial** | claim 有 `observed/candidate/semantic` 三态（按支撑局数），**没有按使用结果算的信任**；`counters` 只有 injections/lastInjectedAt | ✅ **可借**：加「使用试验」记录（见 §九-3），用 Wilson 下界做**排序/退役**信号，不做可见性 |
| **检索 ≠ 使用**（use 记录、验证强度继承） | 我们的日志有注入次数，**没有「被用上了没」**；T9 只证机制，真库效果待线上验证 | ✅ **可借**：use 记录是把「效果」从导入到验证的桥；与 #92 的 actedOn 同向 |
| **冲突让 Skill 退出检索** | 我们有 `supersedes`/`counter`/`disputed`，冲突按 `occurredAt` 判新旧 | ⚠ 部分同向：论文是「冲突未解决 ⇒ 不可检索」，我们是「disputed 仍可见」；是否收紧要按负迁移 ≤5% 的实测再定 |
| **只成功学 → 失败只作对照** | 我们的 antipattern 是失败教训，恢复事实挂在它上面 | ✅ **同向但更保守**：论文按「失败模式」字段保留失败；我们没有把失败当支撑 |
| **编译器用 LLM** | 本仓 §2.3 禁止模型评分参与晋升/排序/存留 | ⛔ **不借编译器**；只借证据纪律（引用到事件、可信代码校验、冲突不覆盖） |

## 七、能借的三点（都能做成机械规则）

1. **把「支撑」从事件数改成 attempt family 数**：同一命令的失败 + 成功重试算 1 次支撑；`支撑局数 ≥2` 的旧判据保持不变，但计数单位换成「尝试族」。这是纯机械改动，不需要模型。
2. **事实型卡补三栏（仍无祈使句）**：`适用`（scope / 文件 / 工具 / 版本，来自 claim 的 preconditions 与 validity）、`观察`（当初的退出码 / 错误签名 / 成功输出特征）、`恢复`（同族的已验证成功：命令 + 退出码 + 日期 + seq）。论文的契约把「失败模式及其恢复」列为过程字段，**我们只是把它从卡尾注释提升为结构字段**。
3. **「使用试验」记录**：卡被注入后，若后续工具调用命中 claim 的主体（同命令/同文件），记一条 trial：`recurred`（又踩了）/ `avoided`（绕开了）/ `unknown`；只把**强可核**的 avoided/recurred 计入，算 Wilson 下界做**排序/退役**信号（不改变可见性，符合「排序≠可见性」）。

## 八、明确不借的三点（附理由）

1. **不借 LLM 编译器（Reflector/Curator）**：本仓禁止模型参与晋升/排序/存留；我们的抽取必须是 `extractSignals` 那类机械规则。可以借的是它的**证据纪律**：每条 claim 引用事件、可信代码校验、不支持只废那一处改动。
2. **不借「自动准入 + 自动退役」的默认开**：论文默认 auto，因为 manual 会延迟到下轮；但我们的 claim 是读面可见性，自动退役会误杀「将来有用」的记忆（#90 冷却优于先审再存）。我们只借「成熟度」的分档语义，动作仍走冷却/降权。
3. **不借「删除源 ⇒ 立刻不可检索」**：我们原件永不删（只遮蔽可见性），这条前提不成立；但可以借「**引用已失效 ⇒ 该行降级为指针**」的形态（T3 已有指针档）。

## 九、对本项目的可执行建议（对应三个痛点）

1. **恢复事实覆盖率（2.37%）**：把 `extract-recovery.mjs` 的主体匹配从「同一命令」扩到「同一文件/同一工具族的**已验证成功**」，并与现有精确命令事实分档（`exact` / `same-file` / `same-tool`）分别计数；目标不是立刻把 2.37% 做高，而是**先量出每一档的天花板**（论文的教训：只成功学 ⇒ 老师没解过的题永远 0，别把结构性上限当 bug 修）。同时按 attempt family 去重支撑。
2. **事实型卡弱于指令式**：在卡片渲染里加 `适用` / `观察` / `恢复` 三栏（§七-2），先做 A/B：同一批合成坑，事实型 vs 事实型+三栏，用 T29 的 syntheticHit 判分（12 对/批，McNemar）。若三栏能把事实型从 25.0% 拉到接近指令式的 8.3%，就说明「事实型弱」是**缺字段**，不是「事实不如祈使」。
3. **真库效果待线上验证**：在注入日志里加 trial（§七-3），先只**记录不生效**跑一周，得到 `recurred/avoided/unknown` 的真实分布；再决定 Wilson 下界是否进排序。没有这一步，「机制已证、真库待验」会一直是空话——论文的 use 记录就是为了把「检索到了」和「真的被用了」分开。
