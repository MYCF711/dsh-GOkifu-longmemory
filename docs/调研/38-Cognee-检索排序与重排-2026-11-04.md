# Cognee 的检索排序层：importance_weight 与 truth-subspace reranking（2026-11-04 采集）

- 来源：厂商文档两页（均已读原文，访问日期 **2026-11-04**）：
  [Importance Weight](https://docs.cognee.ai/guides/importance-weight)、
  [Truth-Subspace Reranking](https://docs.cognee.ai/guides/truth-subspace-reranking)。
  文档索引：[docs.cognee.ai/llms.txt](https://docs.cognee.ai/llms.txt)（同批抓取，用于确认这两页在"Guides"节下）。
- [外] **importance_weight 是什么**：`remember(...)` 的一个浮点参数，"Boost or dampen stored memories in
  retrieval ranking"；取值 **0.0–1.0**，**默认 0.5**（不传即 0.5，存储值缺失也按 0.5 兜底）。
  （[Importance Weight](https://docs.cognee.ai/guides/importance-weight)，访问 2026-11-04）
- [外] **权重是"记忆的属性"，不是"查询的参数"**：文档原话——"The weight is stored on the ingested data record
  and carried onto everything derived from it — the chunks, their summaries, and the entities extracted from
  them — so it is a property of the memory rather than of the query."；且"This holds for every built-in
  chunker… a chunker you write yourself has to copy the weight onto its chunks explicitly."
- [外] **权重如何进入排序（两个检索器各一套）**：图检索把它折进 triplet 的**距离**——
  原文 "folds the weight into a triplet element's distance as **`(2 - importance_weight)`**: `1.0` leaves the
  distance untouched while `0.0` doubles it"；混合检索则"multiplies the ranking score by a factor derived from
  the weight"。
- [外] **另有两条（默认关闭的）信号能调整同一距离**：`feedback_weight`（**除非** `feedback_influence`
  高于默认值 `0`，否则被忽略）与"个人偏好权重"（只作用于用户打过分的元素）；
  文档明确"`importance_weight` is the one that always counts"。
- [外] **哪些检索类型吃这个权重**：`HYBRID_COMPLETION`、`GRAPH_COMPLETION`、`GRAPH_COMPLETION_COT`、
  `GRAPH_COMPLETION_CONTEXT_EXTENSION`、`GRAPH_COMPLETION_DECOMPOSITION`、`GRAPH_SUMMARY_COMPLETION`；
  **`RAG_COMPLETION` 与 `CHUNKS` 无效**（它们只按向量相似度排序）。另：不传 `query_type` 时 `recall()`
  会自动选类型，"may pick one that ignores the weight"。
- [外] **权重只做偏置、不做隐藏**：原文 "A low weight biases ranking; **it does not hide data**. Asking directly
  about the `0.3`-weighted fact still answers from it"。
- [外] **权重写入后不会被改写**："The weight is set at ingestion time… and **nothing rewrites it afterwards**.
  Ingesting the same text again does not change it either: the existing record keeps its stored weight and is
  skipped as already processed. To re-weight content, **`forget()` the item and ingest it again** at the new
  weight."；`improve()` 动的是**另一个字段** `feedback_weight`，"never changes the `importance_weight` you stored"。
- [外] **一个真实的坑（文档自己写的）**：共享的 `EntityType` 节点是"每次写入覆盖"的，所以
  "`person` / `place` 保留最后那次调用的 0.3"，"A type node's weight therefore reflects **ingestion order,
  not importance**"；另一处：`TextChunkerWithOverlap` / `CsvChunker` 在 PR #5231 之前写入的 chunk
  "carry the `0.5` default regardless of the weight you set"（升级只修之后写入的）。
- [外] **truth-subspace reranking 是什么**：**实验性、默认关闭**——"only runs when you build the subspace and
  pass `use_truth_weight=True`. With it off, retrieval behaves exactly as before."
  它把"一局会话学到的东西"变成影响未来排序的信号：一局被蒸馏进 `session_learnings` 之后，
  系统据这些教训建**一小撮锚向量**（"truth subspace"，**最多 k = 8 个确定性 centroid 槽**），
  把每个 chunk 投影上去、把得到的 **alignment 坐标**存到图节点上；查询时**混合检索器**读这些坐标，
  把 chunk 排序往"这局教它重视的方向"推。
- [外] **两个存储各管一半**（文档原表）：`TruthAnchor` 向量集合存"每条被采纳的教训"（它的嵌入就是一条
  "truth direction"）；chunk 节点上的 `truth_alignment` 属性存"每个 chunk 对每个锚的余弦"。
  二者都在**会话结束后离线构建**，查询时分别给出"查询的坐标"与"候选的坐标"。
- [外] **打分公式与中性原则**：rerank 分数是两边坐标的"一致度"，再按"查询本身与每个锚的对齐强度"加权；
  原文关键一句——"a chunk with **no stored coordinates is left untouched (neutral)**, so the feature can
  **never penalize un-scored content**."
- [外] **代价与边界**：坐标写在**图节点属性**上（"a cheap per-property write, **no re-embedding**"），
  查询时只对候选 chunk 做一次批量读取；MVP **只重排 hybrid 的 chunk lane**、entity 排序不受影响；
  文档强调它"**not yet validated by an automatic quality measurement**"，建议保持 opt-in、先在自己的数据上评估。
- [外] **与反馈回路的关系**：`feedback_weight` 是"按会话评分学到的**逐元素标量**"，
  走 `feedback_influence` 作用于图/triplet 检索器；`truth_alignment` 是"按蒸馏教训学到的**逐 chunk 几何信号**"，
  走 `use_truth_weight` 作用于 hybrid 的 chunk lane；两者都默认关闭/中性，且"stored on graph nodes the same way"。

## 对照本仓（棋院）

这块正好是"我们明确不做、但要弄清代价"的一层：**检索排序**。Cognee 给了两个可复用的**设计原则**，
和一堆我们不能借的**打分机制**。

| Cognee 排序层 | 棋院 | 判断 |
|---|---|---|
| 权重是**记忆的属性**（入库时定、随派生对象传播），不是查询参数 | 我们的 `df` / `失败数` / `支撑局数` 也是记忆的属性，且**可复算** | ✅ 同形；差别是他们存浮点，我们存计数 |
| 权重只**偏置排序**、**不隐藏数据**（低权重仍可被直接问到） | 我们用 `supersededBy` **遮蔽**旧条，但遮蔽不是删除 | ✅ 同向：排序与可见性是**两层**，不要混 |
| **未打分的对象保持中性、永不被惩罚** | 十道闸对缺字段的条目是"拒"还是"中性"，目前**逐条硬判** | ✅ **可直接借**：任何排序加成都不该让"没有证据"变成"有罪" |
| 权重写入后**不可改**；要改就 forget + 重入库 | 只增不改：冲突只加 `supersededBy`，**永不重写** | ⚠ 方向一致（都不回头改），但他们的"重入库"我们换成"新条目 + 覆盖指针" |
| `feedback_weight`（按评分学的标量）/ `truth_alignment`（按教训学的几何坐标） | 禁止模型评分与向量；排序只能用可机械统计的量 | ⛔ **不借**：连续分与嵌入坐标都不可复算，违反"计数不是打分" |
| 2 个检索器各有一套折权方式（距离 vs 乘因子） | 我们只有一条"词面 + 类别 + 作用域 + 闸"的路 | ⛔ 不借：多套打分器会让"为什么排前面"说不清（A6 要可核） |
| 共享的 `EntityType` 节点权重"反映写入顺序而非重要性" | 主题表按 `df` 全局算，不存在"最后写入者覆盖" | ✅ 我们的口径天然免疫这个坑（也说明：**共享节点的可变属性**是危险的） |
| rerank 只改顺序、只在 query time 生效（opt-in） | **自动注入 + 按需 `kifu_*` 工具并存**：两条路都在读侧 | ⚠ 若加排序，必须**两条路同一套规则**，否则自动注入那条会绕开排序 |

**能借的三点（都能做成机械规则，且不引入浮点分）**：

1. **"中性原则"写进闸**：任何将来加的排序/加成都必须满足"没有证据 ⇒ 中性"，不能让缺字段的条目
   在排序里被系统性压低；这和他们那句 "never penalize un-scored content" 是同一条纪律。
2. **"排序 ≠ 可见性"分层**：把"排在第几"与"要不要给"分成两层判定。我们现在遮蔽与排序混在渲染里，
   分层的收益是：遮蔽（`supersededBy`）始终先于排序执行，排序只能在**已经通过闸**的行里换位置
   （对应你要的"边界闸行级化"：闸逐行判、排序只在通过的行内进行）。
3. **权重必须是记忆的属性、且写入后不改**：我们的 `df` / `signals.failures` 就是这样；
   若将来给"教训"加机械权重（如 `失败次数/(失败+成功)`），也要遵守"入库时定、不回头改、可复算"。

**明确不借的四点（附理由）**：

1. **连续浮点权重（含默认 0.5）**：不可复算、不可解释，且默认值会让所有未标注条目共享一个"任意"的分；
   我们的替代是**计数**（支撑局数、反例数、注入次数）。
2. **反馈评分 / 真实子空间（embedding 锚 + 余弦坐标）**：本仓不做向量、不做评分；
   而且 truth-subspace 页自己说它"not yet validated by an automatic quality measurement"——连它自己都没验证。
3. **多检索器多套打分**：不同检索类型用不同公式，会让"为什么这条排第一"无法用一行文字回答，
   与 A6"文字可核"冲突。
4. **`forget()` + 重入库来改权重**：删除旧条再重写，等于放弃原件；我们改用"新条目 + `supersededBy`"。

## 两条可复用结论

1. **排序层最值得抄的不是公式，是三条纪律**：权重属于记忆、排序不隐藏数据、未打分者保持中性。
   这三条都能用计数实现，不需要向量，也不需要模型。
2. **"谁打的分"决定它能不能进本仓**：Cognee 的分来自用户评分与模型蒸馏；我们的分只能来自
   **归档时可机械复算的事实**。这条界线清楚，排序层就不会变成第二个不可解释的黑箱。

## 结论

无机制可照搬（连续分与向量都出边界）；可落地的是两条纪律化改造：
**闸行级化后排序只在通过的行内换位**、**中性原则（无证据不降权）**。
它同时给了我们一个反面坐标：一个成熟系统在排序上叠了四层信号（重要性、反馈、个人偏好、真值子空间），
而**每一层都靠"事后可调"活着**——这正是本仓用"只增不改 + 可复算计数"换掉的东西。
