  本篇只写**"同一段里有成功又有失败，怎么判"**——部分失败、依赖链、以及"能不能复用"。四篇不重复页面。

## 一、部分失败是系统的常态，不是异常

- [外] **默认行为是"一个错就放弃整条链"**："If there is an error (the exit status is nonzero), `make` **gives up
  on the current rule**, and **perhaps on all rules**."；一旦某目标失败，"it implies that the current target
  **cannot be correctly remade**, and **neither can any other that depends on it, directly or indirectly**"。
  ⇒ **"ok verify: OK … rebuild: FAIL" 里，`OK` 是上游、`FAIL` 是下游**——上游的成功**不能抵消**下游的失败。
- [外] **`-k` 是"明知整体必败仍继续"**："after an error in compiling one object file, '**make -k**' will continue
  compiling other object files **even though it already knows that linking them will be impossible**."
  ⇒ 所以混合输出**天然存在**：它是"**尽可能多地找出独立问题**"的产物（"find several independent problems so
  that you can correct them all before the next attempt"）。
- [外] **忽略错误 = 把错误当成功（但留日志）**：用 `-` 前缀或 `-i` 时，"`make` treats an error return **just like
  success**, except that it **prints out a message that tells you the status code** … and says that the error has
  been **ignored**."
  ⇒ **"退出码 0"可能只是"错误被忽略"**（54 篇 F1 的同型）。
- [外] **最阴险的形态：部分写入 + 时间戳新**："if it has changed the target file at all, **the file is corrupted
  and cannot be used** … Yet **the file's time stamp says that it is now up to date**, so **the next time `make`
  runs, it will not try to update that file**."（要 `.DELETE_ON_ERROR` 才删。）
  ⇒ **我们的"混合输出"正是这个**：部分成功让"下次不再重试"，**错误被永久固化**。

## 二、"混合输出"的四种形态

| # | 形态 | 例子 | 判定要点 |
|---|---|---|---|
| **M1 链式部分失败** | `ok verify: OK … rebuild: FAIL` | 上游成功、下游失败 | 看**依赖方向**：下游失败 ⇒ 整体失败 |
| **M2 部分测试通过** | `ℹ pass 5 ℹ fail 2` | 同一套里有红有绿 | **fail>0 即失败**；pass 数不抵消 |
| **M3 部分文件成功** | 3 个文件写成功、1 个失败 | 批处理半成功 | 看**是否有整体回滚**；无 ⇒ 状态不一致 |
| **M4 忽略型** | `-rm -f *.o` / `|| true` | 退出码 0 但打了错误 | **退出码不可信**（看 stderr 与 status code 打印） |

**共同点**：四种都**同时含成功与失败**，且**失败那一侧才是信息**（69 篇：反例的逻辑力）。

## 三、"它是不是一条可复用的教训"三判据

| # | 判据 | 机械检查 | 不过关 |
|---|---|---|---|
| **R1 失败主体明确** | 能指出**哪个目标/文件/测试**失败（不是"某处失败"） | 抽取 `FAIL <target>` / 文件路径 / 测试名 | 无法定位 ⇒ 不是教训 |
| **R2 失败占主导** | 该段的**最终结论**是失败（退出码/最后一行/汇总） | 退出码 ≠ 0 **或** 汇总行 `fail>0` | 只是噪声 ⇒ 不进卡 |
| **R3 依赖链可判** | 能说出"**它失败导致谁不可用**" | 有依赖边（上游/下游） | 无法归因 ⇒ 只作观察 |

**R1+R2 是"真失败"，R3 是"可复用"**：
`ok verify: OK … rebuild: FAIL` 满足 R1（`rebuild` 是主体）与 R2（末态失败），
**R3 需要写清"rebuild 失败 ⇒ 产物不可用"**——缺 R3 它就只是"一次构建失败"。

## 四、一段混合输出进 `antipattern` 的最低五条

```
X1 失败主体（R1）：目标/文件/测试名可指认
X2 失败证据（E1）：该主体的错误原文（不是别的行的 OK）
X3 依赖链（R3）：它失败导致什么不可用
X4 恢复条件（E3）：怎么重跑/怎么修
X5 失效条件（E4）：什么情况下这条不再成立
```
**五条全过才进卡**；缺 X3 ⇒ 存"观察"；缺 X1/X2 ⇒ 是噪声（73 篇的三类噪声）。

## 五、对照本仓（棋院）

- **A1 门排除了 53.76% 的噪声**，但过门的 **511 条**里仍有 `ok verify: OK … rebuild: FAIL` 这类混合输出。
- 按第三节：**R2 已满足**（末态失败）、**R1 部分满足**（能指出 `rebuild`）、**R3 普遍缺失**——
  **没人写"它失败导致什么不可用"**，所以它们**不是可复用的教训**，只是"某次构建失败"。
- 更严重的：按第一节第四条，**部分成功会让"下次不再重试"**（时间戳/退出码正常）——
  我们的库里**同一个坑重复出现**（如 `pnpm dlx` 类）正是这个机制。
- **最小修法**：
  ① 抽取决议"段内**最终结论**"（R2），而不是"有没有 FAIL 字样"；
  ② 要求 **X3 依赖链**必填（缺则 `state:"observed"`，不进注入排序）；
  ③ 对 M4（忽略型）**强制看 stderr + status code**，不信退出码（54 篇 F1）。

## 结论

判据三句话：**部分失败是常态**（`-k` 明知整体必败仍继续，为的是找全问题）；
**上游成功不抵消下游失败**（看依赖方向，不看有多少个 OK）；
**可复用 = R1 主体 × R2 末态 × R3 依赖链**。
最后一句：**最危险的不是"整段失败"，而是"部分成功"**——它让时间戳与退出码都正常，
于是**下一次不会再试**，错误就此固化。
