## 二、前 49 篇里**互相矛盾 / 张力**的结论（单列，这是本篇最有价值的部分）

- **C1：45 的"重载失败要回滚" vs 49 的"回滚语义在热重载前提下先天不成立"**
  45 借 nginx 的"校验失败 ⇒ roll back and continue with the old configuration"，暗示回滚是可靠的；
  49 借 CodeDeploy 的"回滚只撤销它知道的文件、不 reconcile 脚本副作用"，并给了"坏写入让回滚目标失效"的实例。
  **不是矛盾而是分层**：45 保证的是**文件层**（新配置没生效、旧配置仍在），49 说的是**运行时层**（进程已经热重载过了，
  回滚文件不会把内存里的状态退回去）。**结论**：回滚只能保证"文件没变"，要保证"进程回到原状"必须**避免热重载**本身。

- **C2：42 的"该投检索" vs 48 的"派生层不划算"**
  42 说检索是主战场（r=0.98），48 说派生数据的维护成本常常大于收益（我们的是 5.5% 上限）。
  **判别式**：看**收益落在哪个轴**——派生层若提升**检索质量**（命中率/精度），42 支持它；
  若只省 **token 长度**（我们的 5.5%），48 判它不值。**同一句"该不该建派生层"必须带上轴的名字**，否则两边都对、结论相反。

- **C3：44 的 Wilson **下界** vs 47 的 Wilson **上界****
  44 用**下界**（≥0.7 才算通过），47 用**上界**（<1% 才判低频转期权）——同一个区间两端，用途相反。
  **混用的后果**：用下界判"低频"会把小样本判成"能力差"；用上界判"通过"会把小样本判成"没问题"。
  **纪律**：**判定"够不够"用下界，判定"稀有到该弃用"用上界**，两者不得互换。

## 四、三条使用建议

1. **先查表，再查篇**：本表 16 条覆盖了"存了取不到 / 机制值不值 / 派生层该不该 / 未知怎么判 / 配置怎么改 / 验收怎么做"六类决定；
   表里没有的问题，回原篇；原篇也没有，说明**还没调研**——按 46 的纪律，那是 `unverified`，不是"没问题"。
2. **矛盾先看"轴"和"层"**：C1 是**文件层 vs 运行时层**，C2 是**检索质量轴 vs token 轴**，C3 是**区间两端**。
   遇到两条结论打架，先问"它们各自在说哪一层/哪个轴"，再决定采用哪条——**不要用平均折中**。
3. **"没采纳"清单就是下一轮的待办**：七条里前三条（配对比较、功效组数、十二问）是**风险最高**的——
   它们不改变已有结论，但决定"我们凭什么相信结论"。**判据的可信度不能低于判据本身。**
