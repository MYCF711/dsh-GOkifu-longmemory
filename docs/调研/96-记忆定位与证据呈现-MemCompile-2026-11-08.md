# 记忆的「定位」与「呈现」必须分开：来源归一 + 证据预算（2026-11-08 采集）

- 来源：[arXiv:2610.23313](https://arxiv.org/abs/2610.23313)（**From Memory Hits to Answerable Evidence: Query-Conditioned Memory Compilation for Long-Term Agent Memory**；
  作者 **Shangze Li / Yanyu Yao / Derong Xu / Zhi Zheng / Tong Xu**（**中国科学技术大学**，State Key Laboratory of Cognitive Intelligence）；
  v1 **2026-10-16**；代码仓库 [MINE-USTC/MemCompile](https://github.com/MINE-USTC/MemCompile)（实测 **HTTP 200**）；
  正文 [HTML](https://arxiv.org/html/2610.23313) 已读 §1–§5、Limitations、附录 A/B 部分，访问日期 **2026-11-08**）。
- **范围声明**：`docs/调研/00` 的 01–95 已覆盖 MemUse 的使用点评测（#92）、Zep Agent Skills 的过程编译（#93）、经验复用与负迁移（#94）、三层经验图（#95）等。
  本篇是**第一篇把「记忆定位（address）」与「证据呈现（evidence presentation）」拆成两个平面**的论文——正好对应我们 T43/T44/T45 的三条负结果：
  语义向量找「主题相似」不如机械判据（T43）、结构化精确锚定因集合饱和无提升（T44）、walk 重排 0 收益（T45）。
- **一句话结论**：[外] 召回命中（hit）不是证据：Top-20 里只有 **14.60 个不同来源**，**同源命中吃掉 27.02% 的预算**（影响 97.27% 的题）；把命中**归一到一个不可变的来源包**（SourcePacket）再按来源分配证据预算，在**来源召回固定 85.50%** 的前提下，**只换呈现方式**就能把 Judge 从 **57.01（单条代表 claim）→ 75.32（原始来源）→ 80.52（完整 claim 包）**——**呈现本身就是一等设计问题**，不是检索的附庸。

## 一、它问的问题：为什么「检索到了」不等于「答得出」

- [外] 长期记忆的失败常发生在**检索成功之后**：检索到的单位（claim/摘要/层级节点）**同时被拿去当"地址"和"给读者的证据"**，两个决策被耦合：地址要**紧凑、可区分、召回广**；读者证据要**保留限定条件、连接互补事实、避免冗余**。同一个单位身兼两职，只能接受固定折中。
- [外] 三个具体后果：① 原子 claim 好检索，但可能丢掉**因果关系与同源兄弟事实**；② 原始对话轮保留细节，但会带**寒暄与无关对话**；③ 层级节点是好的导航单位，但**粒度不对**。更糟的是：没有**来源级边界**时，多条 claim / 多个检索通道会**反复给同一个底层来源分配预算**。
- [外] 这还让归因变难：**分不清是"来源没找回来"还是"证据没呈现好"**。作者的主张：把两件事拆成 Address Plane 与 Evidence Plane。

## 二、方法：两平面 + 来源归一

### 2.1 来源包（SourcePacket）与地址平面

- [外] 每个原始对话轮 `p_i` 实例化为**不可变 SourcePacket**：speaker、session、交互时间、**原始内容**、**稳定标识**。
- [外] **Address Plane** 建**来源链接的紧凑描述符**，放进**有界 Cells**（capacity-aware），配合 BM25 与 dense 候选池——目标是**在固定上限下保住来源覆盖**，而不是把每条 claim 直接当证据。

### 2.2 来源归一（最该抄的一段）

- [外] 候选池里是**地址命中**，不是**不同证据**：多条 claim 可能在转述同一轮对话，同一 claim 也可能同时被 BM25 与多个 Cell 命中。
- [外] 归一：每条候选 `x_i` 通过 `ρ(x_i)=π_i` **解析到它所属的 SourcePacket**；同一 packet 的候选**合并**，包分数取 `max`（`s(p,q)=max_{x_i→p} r_i`）。
- [外] 关键语义：**「多个成功的地址命中 ⇒ 一个证据候选」，不是多个预算条目**。这一步把「检索键的多样性」与「证据的数量」解耦。

### 2.3 证据平面：互补调度 + 有界前沿 + 读侧呈现

- [外] **互补包调度**：闭池 listwise 调度器给候选打**不透明标签**（含对话 id、说话人、日期、来源内容），选 `K0=10` 个**互补** SourcePacket（先直答型、再关系/时间/比较/列举型）；返回**恰好 10 个不同标签**，标签再解析回 packet 身份——调度器只能**重排/筛选池内包**，不能引入新证据。
- [外] **保锚有界前沿**：`W_q = A_0(q) ∪ D_q`，reranker 排序后只在前 `KR=5` 个位置里**新增至多 `KΔ=2`** 个未选中的包（`E_q = A_0 ∪ Δ`）——**保留基线锚、限定证据变化**。
- [外] **读侧编译**：对每个 packet 渲染**该来源的全部保留 claim 组成的包**（`B_p`），带 packet 时间戳，按调度顺序拼接——即「**来源作用域的 claim 包**」，不是单条代表 claim，也不是原始全文重建。

## 三、结果（数字都来自正文/表）

- [外] **LoCoMo 主结果**：F1/BLEU/Recall/Judge = **55.94 / 48.65 / 85.50 / 80.52**，单跳、多跳、时间三类指标全部第一；相比最强基线，多跳与时间的 Judge 分别 **+8.69 / +7.79** 个百分点。
- [外] **成本**：相比 Mem0，Judge **+14.35** 且 token **少 51.7%**（26.72M vs 55.30M）；相比 AtomMem，token 只多 **8.8%**（26.72M vs 24.55M）却 Judge **+10.01**。LongMemEval-S 上时间推理 +24.1、单会话助理 +50 个百分点（vs Mem0）。
- [外] **命中 ≠ 覆盖（RQ3）**：Top-20 排名有 20 个 hit，但平均只有 **14.60 个不同来源**；**同源命中吃掉 27.02% 的名义预算**、影响 **97.27%** 的题。⇒ 加 hit / 加通道不会自动变成更广的证据覆盖。
- [外] **两种机制各管一段**：**普通文本去重几乎没有提升**；**来源归一**把每个命中解析到 SourcePacket 再分配预算，Gold Recall **+3.35pp**；**互补调度**再把释放出的容量分给"补缺"的来源，Gold Recall **51.91% → 80.84%（+28.93pp）**，而**不同来源数仍是 9.988、重复来源率（DBR）为 0**——归一防重复占位，调度决定谁来补位。
- [外] **呈现决定成败（RQ4，固定来源召回 85.50%）**：单条代表 claim **Judge 57.01 / F1 40.68**；原始 SourcePacket **75.32 / 53.00**；完整 claim 包 **80.52 / 55.94**——**同一批来源、只换读侧视图，Judge 差 23.5 分**。作者判词：激进压缩会丢掉"回答所需的关系、时间限定词"。
- [外] **消融**：完整系统 80.52 > BM25-only 77.53 > Cell-only 71.88 > dense cosine Top-10 + claim 包 **70.91** > 无调度无前沿 60.91。**稠密余弦直接取 Top-10** 明显不如编译管线——与 T43 的结论同向（语义相似不是"同一件事"）。

## 四、局限（作者自陈）

- [外] 只在**两个对话记忆基准**（LoCoMo、LongMemEval-S）与**闭源 LLM** 上评测；更广领域与开源模型复现是 future work。
- [外] 总 token 消耗仍可优化（作者自陈质量-成本权衡"有利"但非最优）。

## 七、能借的三点（都能做成机械规则）

1. **按来源预算**：把卡片/注入的 token 预算从「按 claim 行」改成「按 support episode 行」；同一 `(episode)` 的多条 claim 合并成一个证据块（claim 文本 + 日期 + 支撑引文摘要），避免同源占多行。验收指标：**不同来源数 / 总行数**、**同源预算占比**（对标 14.60/20 与 27.02%）。
2. **来源归一计数**：候选先解析到 `(episode, seq)` 再算「命中了几个证据」；同一来源的多个 claim/多通道命中只算 1 个证据候选。这是纯机械的 `Map` 操作，可单测。
3. **呈现与定位分开验收**：walk/排序（定位）与卡片渲染（呈现）分别测——A2b 的 strict 是渲染口径，先做「渲染实验」再动排序；同 recall 下换渲染才可能看到提升（论文的 57.01→80.52）。

## 八、明确不借的三点（附理由）

1. **不借 LLM listwise scheduler / dense reranker**：违反「禁止模型评分参与晋升/排序/存留」；而且它们的效果依赖闭源 LLM，我们无法复现。
2. **不借「完整 claim 包一定更好」的直接外推**：论文的包是**对话 claim**，我们的 claim 是**跨局提炼的教训**，粒度不同；token 预算也更紧（我们的卡是模型读的，不是 QA reader）。要先在本仓语料上测。
3. **不借「原始来源 > 压缩」当口号**：我们的产品前提就是**压缩成 claim**（原件保留在库里）；要借的是「读侧按来源组织」，不是「把原文倒进卡里」。

## 九、对本项目的可执行建议（对应三个痛点）

1. **检索的相关性 = 共享机制不是主题相似（T43 结论）**：把「地址」定义从 claim 文本相似度换成**来源/实体键**（support episode、同一 repo、同一错误签名、同一任务链——T44 已有三锚），并报「命中数 vs 不同来源数」；**不再投入 embedding 方向**（T43 已负结果，本篇 A7 再次同向）。
2. **证据归属**：给每条 claim 的渲染加**来源块**（`episode + seq + 日期 + 一句支撑引文`），并按**来源**而不是 claim 计预算；先做只读统计：当前 5 行里有多少来自同一局、同源占比是否接近论文的 27%。
3. **A2b 提升难**：把「渲染」当成独立实验面——固定同一批候选（同 recall），对比三种读侧视图：①单条 claim（现状）②claim + 来源块 ③同源 claim 包。用 A2b strict 判分，**先证呈现有效，再谈排序**（T45 已证明重排 0 收益，与本篇「呈现才是杠杆」一致）。
