# Cognee memify：去重的三条路（删除式合并 / 就地重写 / 冲突留档）（2026-11-05 采集）

- 来源：厂商文档三页（均已读原文，访问日期 **2026-11-05**）：
  [Entity Deduplication](https://docs.cognee.ai/guides/memify-entity-deduplication)、
  [Entity Consolidation](https://docs.cognee.ai/guides/memify-entity-consolidation)、
  [Resolve Conflicting Facts](https://docs.cognee.ai/guides/resolve-conflicts)。
  页面清单取自 [docs.cognee.ai/llms.txt](https://docs.cognee.ai/llms.txt)（同批抓取，用于确认这三页在 Guides 节下）。
- **范围声明**：本仓已有 09（Cognee 的 remember/recall/improve/forget 四操作）与 38（Cognee 的检索排序层）；
  本篇只写**去重/合并/冲突**这三页 Memify 机制，不重复前两篇的内容。
- [外] **路径一：删除式去重（`consolidate_entities_pipeline`）**。用途：同一实体被抽成多个名字
  （文档例子 `New York City` 与 `NYC`）导致边被拆散。文档原文警告：**"This pipeline is destructive.
  Duplicate `Entity` nodes are deleted from the graph and their name embeddings are deleted from the vector
  store. Run it with `dry_run=True` first and back up your graph and vector stores before running it for real."**
- [外] **它的判据是两个独立通道**（这点对本仓最有用）：
  ① `similarity_threshold`（**默认 0.85**，取值 `(0,1]`）——两个实体名**嵌入的余弦相似度**；
  ② `name_match`（**默认 true**）——"normalized names are identical, where normalizing means **lower-casing and
  stripping every non-alphanumeric character**"（所以 `U.S.A.` 命中 `USA`），且这一路 **"is not bounded by `top_k`"**。
  另有 `top_k`（默认 10，每个实体只看最近邻）、`allow_cross_type`（**默认 false**：只在**同一 EntityType** 内合并）、
  `protect_node_types`（永不合并的类型白名单）。
- [外] **合并后的语义（逐条都是可核的规则）**：
  - 每个簇坍缩成**一个 canonical 节点**，其余删除；canonical = **簇内连接度最高者**，
    平手依次按 **`created_at` 最早** → **归一化名字序**；
  - canonical **保留它原有的 graph id**，"so anything already pointing at it stays valid"；
  - 重复节点上的每条边**重指向** canonical 且**保持方向**；**会变成自环的边直接丢弃**；
  - canonical 的 `description` 变成簇内**去重后非空描述的并集**；
  - canonical 的 `belongs_to_set` 变成**所有成员标签的并集**（"a merge never narrows a node's dataset /
    node-set scoping"）；
  - 旧的重复节点 detach-delete（连带旧边），名字嵌入从 `Entity_name` 向量集合清除；
  - 每次运行（含 dry run）都写一份 **merge report**：`canonical_id` / `canonical_name` / `merged_from`。
- [外] **实现形状（"Under the hood"）**：两步——`detect_entity_duplicates`（读全部 Entity、嵌入其名字、
  按余弦 + 归一化名聚类；"Similarities are scanned in **row-blocks** and only each node's `top_k` nearest
  neighbors are inspected, so the **full N×N similarity matrix is never materialized**"）与
  `merge_entity_duplicates`（选 canonical、**一次批量调用**重指向边、写回并集、删节点与向量）。
  文档强调合并只用 `get_graph_data` / `add_edges` / `add_nodes` / `delete_nodes` + 向量引擎的 `delete_data_points`，
  "No per-edge delete primitive is required"——**后端无关**。
- [外] **路径二：就地重写（`consolidate_entity_descriptions_pipeline`，已弃用）**：三阶段——重写每个 Entity 描述
  （用它的邻居与边）、用**真实成员**重写每个 EntityType 的描述、给每个成员的 `is_a` 边写一行 `edge_text`。
  文档明说它 **"only rewrites text — it never creates or deletes nodes"**，并标注该 pipeline
  **deprecated**，建议改用 `improve()`（其 conflict review 默认开启，"leaves descriptions as extracted
  rather than rewriting them"）。
- [外] **路径二的预算参数是"防病态输入"的硬顶**（示例值，原文给的默认）：`entity_max_neighbor_lines` 20、
  `entity_max_neighbor_text_chars` 500、`entity_max_concurrent_calls` 10、`type_max_members_per_batch` 50、
  `type_max_named_members` 5（≤5 个成员才逐个点名）、`type_max_persisted_is_a_chars` 500、
  `type_tokens_per_is_a_line` 60；且**失败被隔离**：某实体重写失败就保留原描述（保证成员计数仍准），
  某类型失败则该类型不汇总、其它照常落盘。
- [外] **路径三：冲突留档 + 人来裁定（`list_conflicts` / `resolve_conflict`）**：
  两个来源对**不随时间变化的事实**给出不同说法（例："Acme was founded in Berlin." vs "…in Munich."）时，
  `improve(review_conflicts=True)` **只记录冲突、不选胜者**，状态为 `unresolved`；
  `resolve_conflict(conflict.id, dataset_id, selected_fact_id, reason)` 记录"我接受哪一条"，
  `selected_fact_id` 必须是该冲突 facts 之一，否则校验报错。
- [外] **关键一句（与"只增不改"同构）**：**"The other facts are not deleted: they stay in the graph as
  superseded. Recall applies the decision at query time, with no further `improve()` run: graph completion
  drops the rejected facts from its context and states the accepted one."**
  后续再跑 review **不会推翻**这次决定（"keeps it for as long as the selected fact exists"）；
  用另一条 fact 再调 `resolve_conflict` 才会替换。另有一个总开关：`EDGE_EVIDENCE_ENABLED`（默认 true），
  关掉则 conflict review 被跳过。

**没读到 / 不能确认的部分（如实标注）**：① 三页都是**厂商文档**、**无发布日期**，只能记抓取日期 2026-11-05；
② 除参数默认值外，**没有任何去重准确率/误并率数字**；③ `detect_entity_duplicates` 的聚类算法细节

## 对照本仓（棋院）

我们定的合流判据是：**同 kind+scope、≥2 口径命中（ASCII 词集 Jaccard≥0.6 / CJK 2-gram 交集≥4 /
错误类键+前 40 码点相同）、单口径禁止**。Cognee 这三页正好把"合流"拆成了三种截然不同的工程答案，
而且**每一种都能校准我们的一条规则**。

| Cognee | 棋院合流 | 判断 |
|---|---|---|
| **两个独立通道**：归一化名完全相等（`name_match`）**或** 嵌入余弦 ≥0.85 | ≥2 口径命中才合并，**单口径禁止** | ✅ **同一个保守方向**：他们也不敢只凭一路相似度就合并（名称归一是确定性通道，可替代嵌入通道的一半） |
| 归一化 = 小写 + 去所有非字母数字（`U.S.A.`→`USA`） | 我们的 ASCII 词集 Jaccard 是在**词级**比，不认识 `U.S.A.`/`USA` 这类标点差 | ✅ **可借**：入词集前先做"去非字母数字"归一，能消掉一批假阴性，且完全可复算 |
| `allow_cross_type` **默认 false**：只在同一 EntityType 内合并 | 我们同 kind 才合流（`kind` 相同 + `scope` 相同） | ✅ 同构；他们的"默认保守"正好是我们写死的行为 |
| `top_k` 默认 10、行块扫描不物化 N×N | 我们按 kind/scope 分桶后两两比 | ✅ 同向；我们的桶天然比他们的 top_k 更小，**不需要近似** |
| 合并后 canonical **保留原 id**，边重指向、自环丢弃 | 合流后的"大棋谱"要不要保留被并局的 id？ | ⚠ **可借"保 id"**：canonical 用**最早/最连接**的那条 id，被并的 id 只作为 `merged_from` 记录——这样外部引用不断 |
| canonical = **连接度最高 → created_at 最早 → 名字序** | 我们还没有"谁当代表"的规则 | ✅ **可借**（改成机械量：边数/提及数 → 最早 `occurredAt` → id 序），**不用模型** |
| 合并会**删除**重复节点与向量（destructive） | **只增不改、原件永不删** | ⛔ **不借**：删除等于放弃回放；我们只合并"视图"，不动归档原件 |
| 用 LLM 重写实体描述（consolidation） | 机械抽取、不调模型 | ⛔ 不借；且他们自己也把这条标 deprecate、改走"保留抽取原样"的 conflict review |
| 冲突**不删**、留作 superseded，**读时**丢弃被拒事实 | `supersededBy` + 读侧遮蔽 | ✅ **完全同构**——注意：这是他们**唯一**不删数据的合并路径，恰好也是我们唯一采纳的路径 |
| `resolve_conflict(selected_fact_id, reason)` 记录"谁选了哪条、为什么" | 我们有 `supersededBy` + `supersededAtSeq`，**没有 reason 字段** | ✅ **可借**：给覆盖边加一个**机械可核的来源**（哪条 panel/哪一局的裁定），而不是自由文本理由 |

**能借的四点（都能落成机械规则，不进模型判断）**：

1. **归一化前置**：词集比较前先"小写 + 去非字母数字"，`U.S.A.`/`USA`、`New-York`/`NewYork` 视为同词——
   这只改**判据的输入**，不改判据本身，且可复算。
2. **代表规则**：合流后的代表局 = **边数最多 → `occurredAt` 最早 → `id` 字典序**（Cognee 用连接度/created_at/名字序，
   我们换成自己的机械量），被并局记进 `merged_from`。
3. **保 id**：代表沿用被并局中**最早**那条的 id，外部指针（walk 结果、索引里的 `ep-…`）不断裂。
4. **冲突留档**：如果将来出现"两条 claim 互相矛盾且都不该删"，照他们 `resolve_conflict` 的形状记
   「被接受的是谁、依据是哪一局/哪一次纠错」——**只加一个指针字段**，不加自由文本理由。

**明确不借的四点（附理由）**：

1. **删除式合并**：`destructive` + 删向量，与本仓"原件永不删、A6 文字可核"直接冲突；
   他们自己也要求先 `dry_run` + 备份，说明这不是可逆操作。
2. **嵌入相似度判据**：本仓不做向量，且 0.85 这种阈值**不可复算**——同一对实体在不同模型/版本下会翻案。
3. **LLM 重写描述**：那是模型判断，且他们已把该 pipeline 标为 deprecated（转向"保留抽取原样"），
   等于外部也承认"重写不如留档"。
4. **跨类型合并**：我们连 kind 都要求相同，跨类型（如 `tool:` 与 `file:` 同名）一律不合流。

## 两条可复用结论

1. **"合流"最少有三种语义，必须选一种并写进契约**：删除式合并（Cognee dedup）、就地重写（Cognee consolidation）、
   留档 + 读时遮蔽（Cognee conflict resolve）。本仓选第三种；他们的 dedup 页恰好证明**前两种都要付删除或改写的代价**。
2. **多口径不是我们的洁癖**：Cognee 也要"名称归一 **或** 余弦相似度"两条通道才敢合并，且默认只在同类型内合并。
   我们把"≥2 口径命中"写成硬规则，方向一致、只是更严（要求同时命中而不是任一命中）。

## 结论

无需改判据形状（多口径 + 同 kind/scope + 不删原件）；可落地的是三件小事：
**比词集前先做"小写 + 去非字母数字"归一**、**给合流后的代表局一条机械代表规则并保留原 id**、
**给覆盖边加一个可核的来源指针**。
它同时给了我们一个外部依据：连"敢删节点"的系统，在**冲突**这条路上也选择了"不删、只留 superseded、读时才判"——
这正是本仓选的那条路。
