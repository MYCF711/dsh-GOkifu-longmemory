# 向后兼容与灰度：Feature Toggle 的四条纪律（我这两刀就是这么做的）

> **范围**：只写"**怎么安全地上一个会改变行为的改动**"这一面 —— Feature Toggle / latent code、Off 时保持旧行为、两种状态都要测、以及 toggle 的持有成本。
> 不重复 `55-默认关的价值`（为什么默认关）、`44-验收方法论`（怎么证一个改动有效）、`45-配置面陷阱`（配置怎么写）。
> 访问日期：**2026-11-07**。

## 为什么写这篇

这两刀我做了一个会改变行为的改动（`abstain` / `markerWithPolarity`），用了同一套手法：
**先纯函数（可单测）→ 可选参数（不传 ⇒ 原行为）→ 取不到输入 ⇒ 保守（不改行为）**。

结果**一条测试都没破**（1062 条全绿）。
**这套手法在 Martin Fowler 的 Feature Toggles 里都有名字** —— 这篇把它对上去。

## 一、一手文献（Pete Hodgson，Martin Fowler 网站《Feature Toggles》）

### [外 1] **Off 时保持旧行为**（这是最重要的约定）
> "a good convention is to **enable existing or legacy behavior when a Feature Flag is Off**
> and new or future behavior when it's On."
>
> — https://martinfowler.com/articles/feature-toggles.html （访问 2026-11-07）

**本仓的对应**：
```js
marker: options?.signalText
  ? markerWithPolarity(claim, detectPolarity(options.signalText, text))   // On：新行为
  : stateTokenOf(claim)                                                    // Off：**原行为**
```
**不传 `signalText`（= Off）⇒ 走 `stateTokenOf`（旧行为）** —— 所以**现有行为一行都不受影响**。

### [外 2] **两种状态都要测**
> "in order to validate all codepaths which may end up live in production we must perform test our artifact
> in **both** states: with the toggle flipped **On and flipped Off**."

**本仓的对应**：
- **On**：接线测试（"能不能关掉" + "能不能更频繁" ⇒ `opposite` ⇒ `[disputed]`）；
- **Off**：向后兼容测试（不传 `signalText` ⇒ 走 `stateTokenOf`，**原行为**）。

**只测 On（新行为）就会漏掉"我有没有把旧行为弄坏"。**

### [外 3] **latent code**（潜伏代码）—— "默认关"的正式名称
> "Release Toggles allow incomplete and un-tested codepaths to be shipped to production as
> **latent code which may never be turned on**."

**本仓的对应**：`abstainIrrelevant` **默认关** —— 代码**已经在库里**，但**不生效**。
**它不是"没做完"，而是"故意让它潜伏"**（判据还没校准到不误杀）。

### [外 4] **toggle 有持有成本，要主动去库存**
> "Savvy teams view their Feature Toggles as **inventory which comes with a carrying cost**,
> and work to **keep that inventory as low as possible**."

**本仓的对应**：每一个"默认关"的功能（Q18 / T267 / abstain）**都是一个 toggle**，
**都必须写清"重开条件"**，否则它们会**越积越多、没人敢删**。

## 二、本仓这四条是怎么落的（可核）

| 纪律 | 本仓的做法 | 证据 |
|---|---|---|
| **Off 保持旧行为** | 不传 `signalText` ⇒ `stateTokenOf(claim)` | 1062 条测试**没破一条** |
| **两种状态都测** | On（接线测试）+ Off（向后兼容测试） | `test/abstain.test.mjs` |
| **latent code** | `abstainIrrelevant` 默认关 | `src/plugin.mjs` |
| **toggle 持有成本** | 每个默认关的功能都写死**重开条件** | `abstain.mjs` / Q18 / T267 的注释 |

## 三、机械判据（以后做行为改动时照这个来）

### 判据 1：**先纯函数，再接线**
新行为先做成**可单测的纯函数**（不碰渲染/注入路径），**测绿了再接线**。
**不要在没读懂的路径上直接改行为。**

### 判据 2：**可选参数，Off ⇒ 旧行为**
新行为用**可选参数/开关**引入；**不传（Off）⇒ 走原来的代码路径**。
**这一条保证"现有行为一行都不变"。**

### 判据 3：**取不到输入 ⇒ 保守**
**缺输入/判据不可用 ⇒ 不改行为**（不拒绝、不改标记、不报错）。
**宁可"没生效"，也不能"误生效"。**

### 判据 4：**两种状态都测**
- **On**：新行为按预期工作；
- **Off**：**旧行为没有被弄坏**（这是最容易漏的一条）。

### 判据 5：**默认关的功能必须写"重开条件"**
每个 latent code 的 toggle 都要写清：**满足什么条件才允许打开**。
**没有重开条件的 toggle = 永远没人敢删的库存。**

## 四、我这两刀的具体教训

**推迟了两次的"渲染接线"，最后只做了一件小事**：读懂 `entryFromClaim(hit, claim, options)` 的签名，
**加一个可选参数 `signalText`** —— **一条测试都没破**。

**"不敢改"和"不能改"是两回事**：
- 不敢改 = 没读懂路径，怕弄坏；
- **读懂签名之后，接线其实很小**（一个可选参数）。

**而"Off 保持旧行为"这条约定，是让"接线很小"成立的前提** —— 因为**不传就什么都不变**。

## 六、一句话

**"新功能上线"和"新功能上线但旧行为一行不变"，靠的就是这一条约定：Off 时，走原来的路。**
