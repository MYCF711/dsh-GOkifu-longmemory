## 一、爆炸半径是一个可配置的旋钮（CodeDeploy 的三种预置）

- [外] **"一次推多少"是显式配置**（EC2/本地平台，靠 "**minimum healthy hosts**" 与可选的
  "minimum healthy hosts per zone" 表达）：`CodeDeployDefault.AllAtOnce`（尽量一次全推——"**The overall
  deployment succeeds if deployment to even a single instance is successful.**"）、
  `CodeDeployDefault.HalfAtATime`（一次最多一半）、`CodeDeployDefault.OneAtATime`（**一次一台**，
  "the overall deployment **fails as soon as** the application revision fails to be deployed to any but the last instance"）。
- [外] **流量按百分比与时间窗分批**（ECS / Lambda 平台）：`Canary10Percent5Minutes`（先切 **10%**，其余 90%
  在 **5 分钟**后——同系列还有 10/15/30 分钟）、`Linear10PercentEvery1Minutes`（每 1 分钟切 10%），
  以及 `AllAtOnce`。即**爆炸半径 = 初始百分比 × 观察窗口**，两者都可调。
- [外] **不指定就用默认**："If you don't specify a deployment configuration, CodeDeploy uses the
  `CodeDeployDefault.OneAtATime` deployment configuration."——**默认最保守**这一点本身就是设计决策。

## 二、回滚不是撤销：它是"把上一版当成新一次发布"

- [外] **回滚 = 重新部署，不是恢复**："CodeDeploy rolls back deployments by **redeploying a previously deployed
  revision**… These rolled-back deployments are **technically new deployments, with new deployment IDs, rather than
  restored versions** of a previous deployment."
- [外] **自动回滚的触发条件是"失败 + 监控阈值"**："automatically roll back when a deployment fails **or when a
  monitoring threshold you specify is met**"，此时"the **last known good** version"被部署。
  手动回滚的动机也写得很直白：应用进入 "**unknown state**" 时，"Rather than spending a lot of time troubleshooting,
  you can redeploy the application to a **known working state**"。
- [外] **回滚只能撤销"它自己装过的东西"**：回滚前，CodeDeploy 依据 cleanup 文件
  （`…/deployment-instructions/<group>-cleanup`）删除"**all files that were last successfully installed**"；
  而"CodeDeploy will **not try to revert or otherwise reconcile any actions taken by any scripts** in previous
  deployments"——**脚本的副作用不在回滚范围内**，要自己写逻辑清理。
- [外] **一次坏写入可以让回滚变得不可能**（文档给了三段部署的实例）：部署 1 用 `RETAIN` 保留了若干文件 →
  部署 2 用 `OVERWRITE` 失败并**删掉了那些保留文件** → 部署 3 回滚到"最后已知良好版本"时，
  "the files that you wanted to retain in deployment 1 were **deleted before deployment 2 failed and cannot be
  retrieved** by AWS CodeDeploy"。即：**回滚的目标版本可以存在，但它依赖的状态已被失败的那次改动破坏**。
- [外] **还有一条易漏的**："If you remove an instance from a deployment group, CodeDeploy **does not uninstall**
  anything that might have already been installed on that instance."——**移除 ≠ 清理**。

## 对照本仓（棋院）

**场景**：一份"给主人的一键脚本"要改 `cordis.patch.yml`；按项目铁律，**运行中改它会整树热重载，
可能让 host `exit(1)`**（2026-10-30 真实事故）。也就是说：**一条命令 = 整个宿主 + 当前所有会话的爆炸半径**。

### 十二问（可直接拿去审脚本）

| # | 问题 | 外部依据 | 我们做了吗 |

### 如果不做会怎样（最坏结果 + 概率量级）

- **最坏**：脚本在写入中途被中断或写坏了 YAML ⇒ 热重载 ⇒ host `exit(1)` ⇒ **所有会话同时中断**，
  而 `exit(1)` 之后**没有任何东西能证明崩溃前那版配置是好的**（第 3、6 条都不成立）。
- **更坏的一种**（CodeDeploy 的三段部署教训）：坏配置**删掉了回滚要用的状态**，于是"回滚到上一版"这个动作
  **本身也不成立**——文件回去了，但运行时已经不是一个可回到的状态。
- **概率量级**：不是"极低"——这条路已经**实现过一次**；也不是"必然"——只在**运行中写入**时触发。
  可用一句话判据：**只要"运行中写 patch 文件"这件事由脚本自动做，就是在拿全部会话赌一次热重载。**

### 上线门槛（gate，机械可判）

**四条铁闸，缺一条就不许脚本自动执行**（只能输出"给人手动执行的步骤 + 回滚命令"）：

1. **写前校验**（第 4 条）：YAML 语法 + 语义（同一 name 唯一、`disabled`/`enabled` 二选一）**先跑**，
   不过就不写。
2. **原子写 + 独立备份**（第 3、5 条）：tmp → rename；备份文件**不依赖脚本**即可恢复（路径写进输出）。
3. **回滚语义写清**（第 6 条）：明确"回滚 = 恢复文件 + 重启（由人执行）"，并说明**副作用不自动撤销**。
4. **爆炸半径声明**（第 7、8 条）：在脚本输出第一行写明"本命令将热重载整个宿主，最坏结果是 `exit(1)`"，
   且**默认不自动执行**——按 CodeDeploy 的"默认最保守"原则，默认走 `OneAtATime` 式的"先给人看"。

**能借的**：爆炸半径旋钮（把"一次改多少"变成参数）、"默认最保守"、自动回滚的**双触发条件**（失败 + 监控阈值）、
"last known good"的措辞、"回滚 = 新一次部署"的心智模型（回滚也要被记录、被审计）。
**不借的**：`AllAtOnce` 式的"一次成功即整体成功"（对我们是灾难）、以及"移除即清理"的假设（我们连"移除"都没有）。

## 两条可复用结论

1. **回滚不是一个动作，而是一个能力**：它需要①目标版本存在 ②它依赖的状态未被破坏 ③副作用可被撤销。
   CodeDeploy 的三段部署例子证明：**只要 ② 被破坏，回滚就是幻觉**——所以我们必须在**写之前**就保证能回到原状，
   而不是写完再想怎么回。
2. **爆炸半径必须显式，默认必须最保守**：CodeDeploy 不给配置时用 `OneAtATime`。反推：任何"默认全量"的工具
   都在**默认状态下**承担最大风险；对单宿主系统，这个默认等于"一次改坏全部"。

## 结论

按十二问对照：**第 2、4、6、7、10 条没做，第 3、5、12 条待确认**，只有第 11 条（可观测）做到了。
结论不是"把脚本写得更小心"，而是**把它降级为"给人执行的步骤"**：脚本只做写前校验 + 备份 + 打印回滚命令，
**不自动改 patch、不触发热重载**——因为回滚语义（第 6 条）在"运行中改配置"这个前提下**先天不成立**。
