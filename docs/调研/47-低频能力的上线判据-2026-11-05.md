# 低频能力怎么处置：临时态、软弃用与"期权"（2026-11-05 采集）

- 来源：三份一手规范（均已读全文，访问日期 **2026-11-05**）：
  [The TC39 Process](https://tc39.es/process-document/)、
  [PEP 411 – Provisional packages](https://peps.python.org/pep-0411/)、
  [PEP 387 – Backwards Compatibility Policy](https://peps.python.org/pep-0387/)。
- **范围声明**：44 篇讲**验收方法论**（功效、聚类、裁判偏差）、46 篇讲**未知如何传播**（三值逻辑）；
  本篇只讲**"能力正确但几乎不触发"时该继续投、降级保留、还是删**——即"低频能力的产品生命周期"，与那两篇不重复。

## 一、TC39：把"可能永远不进标准"写进流程

- [外] **Stage 2 的官方措辞就承认失败可能**："The committee expects the feature to be developed and eventually
  included in the standard, **but due to reasons that may not be apparent at this stage, the feature may never be
  included in the standard.**"
- [外] **Stage 2.7 是"停止投入、等证据"的显式阶段**："The solution is complete and **no further work is possible
  without feedback from tests, implementations, or usage**. No changes to the proposal will be requested by the
  committee aside from those elicited through testing, implementation, or usage experience."
  入口条件是"完整规范文本 + 评审人签字"，**不是**"已经有用"。
- [外] **Stage 3 才是"够格实现"**："The proposal has been recommended for implementation"——其入口要求
  "**sufficient testing and appropriate pre-implementation experience**"；
  而 Stage 3 的含义被明确成"design work is complete and further refinement will require **implementation
  experience, significant usage, and external feedback**"。
- [外] **可以退回与撤回**："a proposal champion may request **regressing a proposal to an earlier stage, or
  withdrawing it altogether**"，但"**Consensus of the committee is necessary**"，且"must include a rationale
  explaining why it is appropriate"；即使共识失败，也要求"record a good description of **why** a proposal did
  not advance"。

## 二、PEP 387：软弃用 = "保留但不投"

- [外] **soft deprecation 的定义（几乎就是"期权"）**：用于"an API which **should no longer be used to write new
  code, but it remains safe to continue using it in existing code**"；"The API **remains documented and tested, but
  will not be developed further (no enhancement)**"。
- [外] **软弃用不排删除**："the main difference between a 'soft' and a (regular) 'hard' deprecation is that
  **the soft deprecation does not imply scheduling the removal**"；且软弃用**不抛警告**，只写在文档里。
- [外] **硬弃用的时序与例外**：要等警告出现在"至少两个 minor 版本"（或更旧的 major 一个 minor）之后，
  文档**倾向于等 5 年**再移除；但如果"expected maintenance overhead and security risk … is small"，
  "**it can stay indefinitely**"；steering council 可为例外缩短期限，典型理由是"features **no one could
  reasonably be depending on**"。

## 三、PEP 411 的**事后自评**：为稀有状态设计的机制，自己也可能低频

- [外] **provisional 状态**：包可以"to be included and marked as 'provisional'"，明确"**no promises are made
  with regards to the stability of the package's API**"，极端情况下"may even be removed … **without a
  deprecation period**"；毕业条件是积累反馈，不毕业的两种理由是"不稳定/无人维护"与"发现了更好的替代"。
- [外] **但这套机制被自己否决了**（状态已标记 Superseded，正文顶部 Note）："A decade after this PEP was written,
  experience has shown this is a **rarely used feature** in managing the standard library. It has also **not helped
  prevent people from relying too heavily on provisional modules**, such that changes can still cause significant
  breakage in the community."
  也就是说：**一个专门为"不确定是否该长期存在"设计的状态，最终因为"很少被使用"而退役**。

## 对照本仓（棋院）

**本文写作时点的实测（仅此一节，非版本或测试数字）**：合流机制 **12/12 成立**（只要输入同时命中同组 ≥2 个成员，
100% 省行）；真库随机 **0/1000** 次抽样触发；**Wilson 95% 上界 0.38%**。

### 判据（三道闸，机械可判）

| 闸 | 问什么 | 判据 | 本仓代入 |
|---|---|---|---|
| **G1 正确性** | 机制本身有没有反例？ | 有反例 ⇒ 修；无反例 ⇒ 进 G2 | **12/12 无已知反例** ⇒ 过 |
| **G2 触发面可放大性** | 存在**不改语义**、只改召回/展开路径的改动吗？成本是否 ≤ 一轮工作量？ | 有且便宜 ⇒ **做一次有时间箱的实验**；无或昂贵 ⇒ 进 G3 | **有**（见下）⇒ **做实验** |
| **G3 期权判定** | 实验后触发率仍极低，且保留成本可接受？ | 触发率 Wilson 上界 < 1% 且保留成本（代码路径/闸/每轮验收）可接受 ⇒ **软弃用（期权）**；否则 ⇒ **删** | 待实验后判 |

**结论：不是"删"，是"先做一次有界的修触发面实验"，再决定是否转期权。**
理由：G1 已过（机制正确、收益真实），G2 有便宜可做的项——在这两条成立时直接转期权，等于把"没试过放大"当成"放大不了"。

### 触发面该怎么改（具体，不泛泛）

现状的触发条件是**两个事件同时发生**：① 卡片命中某个成员；② 同一张卡里还命中**同组的另一个成员**（≥2 才折叠）。
0/1000 说明第二个事件几乎不发生。三条具体改法，按成本从低到高：

1. **把"≥2 命中"改成"≥1 命中 + 代表展开"**：命中任一成员 ⇒ 冒泡到代表（用现成的 `mergedInto` 反指针），
   代表行展开 1 条成员指针。触发概率从 P(≥2 同组同卡) 变成 **P(≥1 成员被命中)**——这是**量级**差别，不是几个百分点。
   语义不变：折叠仍只发生在读侧，成员仍在库里。
2. **把"精确命中代表 id"改成"命中成员即代表可见"**：现在大多数路径是按 id 精确匹配，代表 id 很少被直接命中；
   加一条"成员 → 代表"的**反向索引**即可（这条索引本身就是 `mergedInto` 的用途，目前没被用上）。
3. **把频率从抽样估计变成运行时计数**：每张卡记 `mergeCandidatesHit` / `mergeCollapsed` 两个计数。
   现在 0/1000 是**离线抽样**的估计（上界 0.38%），加了计数器才能回答"到底是 0 还是 0.1%"，
   也才能在实验后给出**配对**的前后对比（44 篇的纪律）。

### 实验的退出条件（写死，避免无限投入）

- 时间箱：一轮（做完上述 1–2 项 + 计数器）。
- 判据：改造后**触发率**（运行时计数口径）若仍 < 1%，转 **soft-deprecated 期权**——
  代码保留、文档标注"不再投入、不排删除"（PEP 387 的软弃用语义），并且**不再进入每轮验收的关键路径**；
- 若≥1%，则从"实验"转为"常规能力"，并把触发率纳入监控。

### 能借的 / 不借的

- ✅ **借**：TC39 的"Stage 2.7 = 停止投入等证据"（我们的"时间箱实验"就是它的缩小版）；
  PEP 387 的 **soft deprecation**（保留 + 不投入 + 不排删除，三者缺一不可）；
  PEP 411 的**事后自评姿态**——一个机制退役时要说清"它为什么没被用起来"，而不是悄悄留着。
- ⛔ **不借**：TC39 的"多阶段共识"全套（我们是单机单用户，没有委员会，别把流程做成官僚）；
  以及"provisional 状态"本身——PEP 411 的自评已经证明**为稀有状态专门造一个状态**往往低产，
  我们只需要"软弃用"这一种状态。

## 两条可复用结论

1. **"机制成立"与"值得投"是两个正交判断**：正确性用反例检验（G1），价值用**触发面可放大性**检验（G2）。
   把两者混在一起，就会出现两种误判——要么因为"频率低"删掉一个正确的机制，要么因为"机制对"无限投入一个几乎不触发的路径。
2. **低频能力有三种合法归宿，而不是两种**：继续投（有可放大触发面的证据）、**软弃用/期权**（保留、不投、不排删除）、删。
   PEP 411 的自评补了第四条教训：**连"为不确定能力设计的机制"自己也可能低频**——所以状态要少，判据要硬。

## 结论

按三道闸代入：**G1 过（12/12）→ G2 有便宜可做的触发面改动 → 做一次时间箱实验；实验后仍 < 1% 才转期权，永不轻言删。**
最可能见效的一条是"命中任一成员即冒泡到代表（≥1 命中即展开）"——它把触发从"两件事同时发生"降到"一件"，
而这正是 `mergedInto` 反指针本来就该承担的职责。
