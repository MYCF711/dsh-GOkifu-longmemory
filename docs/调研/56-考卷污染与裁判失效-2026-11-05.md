## 一、xfail：一个判据可以"永远等不到通过"

- [外] **xfail 的语义是"我预期它会失败"**：`pytest.mark.xfail` 用于"a test for a feature not yet implemented,
  or a bug not yet fixed"；当它**通过**时是 **XPASS**（"unexpectedly passing"）。
- [外] **XPASS 默认不失败**——这是尺子过期的藏身处："Both `XFAIL` and `XPASS` **don't fail the test suite by
  default**. You can change this by setting the `strict` keyword-only parameter to `True`…
  This will make `XPASS` … **fail the test suite**."（也可用 `xfail_strict = true` 全局打开。）
  ⇒ **没有 `strict`，一个"已经被修好"的东西会静静躺在失败清单里**，没人被通知。
- [外] **判据必须与失败形态同形**：`raises=` 参数指定"只有这类异常算预期失败"——
  "Then the test will be reported as **a regular failure** if it fails with an exception **not mentioned** in `raises`."
  即：**失败的理由不匹配，就不是 xfail，是真失败**。
- [外] **`--runxfail` 可以把尺子暂时摘掉重测**："force the running and reporting of an `xfail` marked test
  **as if it weren't marked at all**"——用于回答"如果我不预设它会失败，它到底怎样"。

## 二、不可靠的信号会让**真失败**被忽略

- [外] **flaky 的代价不是误报，是信任崩塌**（原文）："If the test result is **not a reliable signal** – that a test
  failure means the code change broke the test – **developers can become mistrustful of the test results, which can
  lead to overlooking genuine failures.** It is also a source of wasted time as developers must re-run test suites
  and investigate **spurious failures**."
  ⇒ **假阳性的真正代价是"以后真的没人看"**。
- [外] **"判据过严"被列为 flaky 的头号根因之一**："**Overly strict assertion** — Overly strict assertions can cause
  problems with **floating point comparison** as well as **timing issues**. `pytest.approx()` is useful here."
- [外] **长期"隔离"是危险动作**："`xfail` with `strict=False` can be used to mark a test so that its failure
  **does not cause the whole build to break**. This could be considered like a **manual quarantine**, and is
  **rather dangerous to use permanently**."
- [外] **处置路径是"删或重写"而非"养着"**："**Delete or rewrite the test** — If the functionality is covered by other
  tests, perhaps the test can be **removed**. If not, perhaps it can be **rewritten at a lower level** which will
  remove the flakiness or make its source more apparent."

## 三、三条机械判据（考卷健康度）

| # | 判据 | 机械口径 | 阈值处置 |
|---|---|---|---|
| **H1 尺子过期率** | `staleJudgeRate = 已被证明修好、但判据仍标失败的题 / 总题`（xfail 的 XPASS 就是这个） | `> 0` 必须处理 | 打开 `strict`（XPASS 变红）|
| **H2 形态同形** | 判据是否**指定了"哪一类失败算数"**（类比 `raises=`）？ | 判据对"语言/编码/格式"敏感 ⇒ 形态不同形 | 判据必须与任务同语言同形态，否则恒失败 |
| **H3 过严率** | `overStrictRate = 因精度/时序/格式差异而失败的题 / 总失败题` | `> 20%` ⇒ 判据过严 | 改用容差比较（`approx` 式）|
| **H4 覆盖面** | `stratumCoverage`（题型覆盖数/权重）、`easiestShare`（最容易那一类的占比） | `easiestShare > 50%` ⇒ 考卷被最容易的题主导 | 必须按题型分桶报 `worst-bucket` |

## 四、"尺子错了 vs 东西坏了"决策树

按顺序问，**任一步给出结论就停止**：

1. **反事实（决定性）**：构造一条**必然正确**的样本（如把原文**逐字复制**当答案）喂给判据。
   **判据仍判失败 ⇒ 判据坏**（东西不可能是坏的，因为输入就是它自己）。
2. **控制变量**：同一批对象分别用**旧判据**与**新判据**跑。结论**反转** ⇒ 判据敏感，坏的是尺子。
3. **抽样读原文**：随机取 10 条"失败"，人工读被引原文。若引文**确实存在** ⇒ 尺子错（定位到判据的输入字段）。
4. **独立复算**：换一个**独立**实现/语言/人重算同一批。结论**不一致** ⇒ 尺子坏；一致 ⇒ 东西坏。
5. **时序**：`坏读数` 与 `数据变更` 的先后。时序**不支持**"数据坏"时，仍需 1–4 才能定论（时序只排除不证明）。

> 我们的三次事故全部落在**第 1 步**：只要喂一条"逐字正确"的样本，判据就该通过；它没通过 ⇒ 尺子坏。

|---|---|---|---|

| 考卷要求"与任务原话 **≥2 判别词**重合"，但**任务原话是中文、claim 是英文报错** | **形态不同形**：判据对语言敏感，恒失败 | **H2**（`raises` 不匹配） | 尺子坏：**18 条**"已渲染进卡"被判未命中 |

三次的共同形状：**产品没错，测量工具错了**。而"信任崩塌"那条已经在发生——
假阳性一多，真的坏引用会被当噪声（flaky 页原文：**"overlooking genuine failures"**）。
**处置**（照 pytest 的四条）：① 给判据加"严格模式"（H1）② 判据与任务同语言同形态（H2）③ 过严处改容差（H3）
④ 修不动的**删或重写**，不要长期隔离（`strict=False` 被文档点名"rather dangerous to use permanently"）。

## 结论

判据三句话：**H1 尺子会过期（XPASS 必须变红）→ H2 判据必须与失败形态同形（`raises` 式）→ H3 过严要改容差**；
再加一条覆盖面：**H4 报 `worst-bucket` 与 `easiestShare`，不报 overall**。
判别只需第 1 步：**喂一条"逐字正确"的样本，判据还失败，那就是尺子坏了**——
因为一个**永远等不到通过**的判据，和没有判据是同一件事，只是它还会**让人不再相信真失败**。
