## 0. 一句话结论

**我们踩的坑，上游全都踩过，而且都已经在代码里改掉了 —— 差别是他们把「代价」写成了不变量，我们只把「质量」写成了判据。**

三个最硬的对齐点：

| 我们的坑 | 上游的结论（代码级） | 性质 |
|---|---|---|
| 每轮全量派生 + 全量替换（`deriveStore`/`replaceDerived`） | Graphiti 的 `add_episode` **只处理本 episode 的节点/边**，候选集限定在**同一对端点**（`_pair_search_filter`）；Mem0 现行只剩 `ADDITIVE_EXTRACTION_PROMPT`（"Your sole operation is ADD"） | 架构级 |
| 重复注入（A1.redundant；`aa0b0da9` 10/10 次） | Letta `rebuild_system_prompt`：**记忆串没变就跳过**；注释原话 "Updates to the memory header should *not* trigger a rebuild, since that will simply flood recall storage with excess messages" | 架构级 |
| 注入位置影响成本，我们从没量化 | Anthropic：缓存是**前缀累积哈希**，层级 `tools → system → messages`；**改早前内容 ⇒ 该层及其后全废**；只有"在尾部追加"能全命中 | 成本级 |

## 2. 优化项：P0（纯正向、零代价，可立即做）

### P0-1 注入改成「按 slot 幂等覆盖 + 内容 hash 判等」

- **官方/上游**：Letta `rebuild_system_prompt`（内容未变即 return）；Anthropic"只追加尾部"
- **我们**：`src/plugin.mjs` 的 pre-step 注入 + `src/rooms/inject.mjs` 的 `buildMemoryCard`
- **改法**：为每个注入 slot 记 `{slotId, contentHash, seq}`（**持久化到 sidecar**，不放内存）；`hash` 相同 ⇒ 不注入；不同 ⇒ 覆盖同 slot 而非追加新块
- **验收**：`node --test test/inject.test.mjs` 新增用例「同 session 第二次 pre-step 注入为空」；A1.redundant 维持 0；`aa0b0da9` 场景回归（end-seed 后重新 apply 仍 0 重复）
- **预期**：A1.redundant 从"未通电"变成**可测的 0**；每轮注入字符数下降
- **回滚**：单文件开关 `INJECT_SLOT_IDEMPOTENT=0`

### P0-2 去重键改成「内容身份」并持久化

- **上游**：Mem0 md5（太弱，只挡逐字）+ issue #7123 证明窗口去重不够；Graphiti 用 `uuid5(内容)` 寻址做幂等（Cognee 侧）
- **我们**：把去重键从内存 `injectedIds` 改为 `(scopeKey, episodeId, seq, claimId)` 落盘，随 store 版本号失效
- **验收**：模拟 `session/end-seed` 后重新 apply，断言 0 重复；`node scripts/patrol.mjs` A1=0
- **预期**：跨重启/跨 apply 去重生效

### P0-3 归档改「按 episode 增量」，取代全量 `replaceDerived`

- **上游**：Graphiti 8 步增量 + 端点对限定候选；Mem0 单条 `add()` 不重建整库
- **我们**：`src/rooms/persist.mjs` 的 `deriveStore` / `replaceDerived`
- **改法**：以 episode 为最小更新单位，只对「本轮新增/变更的 episode」重算它涉及的 topic/link/thread，其余沿用库内记录；删除只在 episode 真正消失时发生
- **验收**：`node --test test/archive.test.mjs test/archive-stale.test.mjs`；连跑两次第二次 `writes.*.written === 0`；稳态 `node scripts/archive.mjs --incremental` ≤30s
- **预期**：稳态 63s → **≤30s**；写入条数与"新增局数"成正比而非与库大小成正比
- **回滚**：保留 `KIFU_ARCHIVE_FULL_DERIVE=1` 走老路径

### P0-4 单一常量表 + 单一判据实现

- **上游**：Graphiti 顶部集中常量；LlamaIndex `token_limit` 单入口
- **我们**：`scripts/metrics-guard.mjs` 与 `scripts/ledger-check.mjs` 各有一份 A4 门槛（D7 改两次才生效）
- **改法**：新建 `src/rooms/limits.mjs`（唯一权威），两个脚本 import 它；注入/检索/walk 的魔法数字一并迁入
- **验收**：新增测试断言「两处读到的 A4 门槛是同一个常量对象」；`node --test test/ledger-tmp-guard.test.mjs`
- **预期**：再也不会出现"改一半就发版"

### P0-5 加一条「缓存成本」指标

- **上游**：Anthropic 的层级失效规则；官方 `context editing` 要求 `clear_at_least` 保证每次清理值回票价
- **我们**：只有 A4 时延，没有缓存命中率
- **改法**：记录每轮注入前后的 `prefixHash` 与注入字符数，落 sidecar；`metrics-guard` 新增 `A7.cacheBreak`（每轮前缀变化的次数 / 轮数）
- **验收**：`node scripts/metrics-guard.mjs` 输出 A7；阈值先只统计不判红（与"指标先有消费者"一致）
- **预期**：把"重复注入的代价"从隐性变成可测数字

## 6. 为什么这些坑我们仍然踩了（流程性根因）

1. **判据只覆盖"质量"，不覆盖"代价"**：A2b/A5/A6 全在测"召回对不对"，**没有一条门禁测增量性、幂等性、开销上界、缓存不失效**。于是架构退化不会变红，只会累积到 900 秒跑不完。
2. **优化从症状出发，不从架构清单出发**：本会话七次误判（冷缓存/bundle/matchTopics/零变更早退/derive 第一步/OOM/中间态读数）都是"先猜再改"，没有先对照上游的标准架构清单（分层/增量/去重键/失效语义/缓存位置）。
3. **阈值多份实现**：同一个门槛写在两个脚本里，改一处就以为改完了 —— D7 因此发了两轮才生效。
4. **"量"的方法没有固化**：线上库随时处于"上次没跑完"的混合态，我三次拿文件数当读数（16.3 万→3.5 万→2 万）。已固化为纪律：**派生量必须用 `--dry-run` 同语料对照**。
