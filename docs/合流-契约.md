# 合流契约（consolidation contract）

> **状态**：草案（T141，2026-11-04）。只写契约，不含实现。
> **上游依据**：`方案.md` §14（M9 方向：合流成大棋谱 + 局部视图）；`docs/数据契约.md` §9（claim 字段）、§12（既有"类级章节"巩固，本契约是它的推广，不是替代）。
> **读前须知**：本契约里的所有数字都标了 `[本]` 与读取时点；语料是活的，跨时点不可比。代码引用一律用「文件名 + 符号名」，不用行号。

---

## 0 · 一句话

**合流 = 在同一作用域、同一 kind 内，把"证据指向同一个坑/同一条事实"的 claim 收成一条新 claim（派生数据），成员原样保留、出处并集、正文逐字可回溯、冲突不合只连边。**

它不是"写一份摘要"，也不是"删掉重复条目"——库里的成员一个都不删，合并节点是从成员机械算出来的视图（与 `ensureClassClaims` 生成的类级章节同性质）。

---

## 1 · 范围：合什么、不合什么

### 1.1 可以合（S2 允许）

| 条件 | 说明 |
|---|---|
| 同一 `kind` | 只有 `antipattern` 参与 S2 的模糊合流；`fact` / `preference` 只做**精确重复**（见 §2.7） |
| 同一 `scopeKey` | 逐字节相等（大小写已由 `normalizeScopeKey` 归一，见 `src/rooms/inject.mjs`） |
| 同一证据（Tier 0），或 A/B/C 三口径中**≥2 个命中**（Tier 1） | 见 §2.3；单口径一律不合 |
| `preconditions` 的 `(check,value)` 集合完全相等 | 否则合并会**放宽适用范围**（例：一条"只在 file-exists 时成立"，一条"无此条件"） |
| `validity` 的 `(type,value)` 完全相等 | 否则是两条不同的事实断言 |
| 双方 `counter` 均为空 | 任一方有反例 ⇒ 不合，只连 `contradicts`（§3） |

### 1.2 不合，只连（永不合并）

| 情形 | 处理 | 依据 |
|---|---|---|
| **跨作用域**（`scopeKey` 不同） | 不合、不连（`corroborates` 也不建） | A5 铁律：跨工程混流是 Hindsight 的已知成本（`docs/对标-Hindsight.md` §1）；`crossScopeLeakRate` 必须为 0 |
| **不同 `kind`** | 不合；同一 `(scope, episode, seq)` 的 `fact` 与 `antipattern` 建 `derives` 边 | 两类断言语义不同：`fact` 断言"该路径/版本在 T 时刻如何"，`antipattern` 断言"这类失败是要避开的坑"。合并会把"事实"与"教训"混成一条不可判读的条目 |
| 任一方是 `class:*` 类级章节 | 不参与 S2（它已是聚合结果） | `docs/数据契约.md` §12；再合一次会与类章节叠加出第三层 |
| 任一方 `state` 为 `disputed` / `invalidated` / `stale` | 不合 | 反例优先（`方案.md` §5.2）；把 disputed 并入正常条目 = 洗掉反例 |
| 任一方 `support` 为空 | 不合（也不该存在） | 无源不入 |

> **反例会怎样**：若允许跨作用域合并，`DSH-GO` 里"git 不是仓库"的教训会与 `反代` 里同名文本合成一条，注入到任一工程时都带出另一工程的 `episode` 指针 —— 这正是 A5 要防的事故形态。

### 1.3 一个 claim 的 support 跨局怎么算

- **合并节点的 support = 各成员 support 的并集**，去重键 `(episode, seq, quote)` 三元组（与 `ensureClassClaims` 现有做法一致）。
- 保留每条 support 的 `threadId / nodeId / edgeId / occurredAt` 原样；不重写、不补全。
- **独立支撑局数** = 并集里不同 `episode` 的个数（不是 support 条数）。`方案.md` §5.1 的晋升阶梯按"局"算，不按"条"算。
- 合并**不能**把"同一局的两条证据"算成两局。数据佐证：某局一条用户消息里有几十句约束，全部落在同一个 `(episode, seq)` 上，但它们是**不同句子**；反过来，两条 claim 的 support 集合完全相同也**不**说明重复（见 §8.4）。
- 合并后 `counters.support` 仍写**条数**（保持 `docs/数据契约.md` §9 的字段语义），独立局数作为派生字段 `merge.supportEpisodes` 输出，不写回 `counters`。
- **跨局簇是"多局印证"，不是"重复"**：T145 体检里 **57 簇横跨 ≥2 个 episode**。这类合并不是在删信息，而是在把"同一个坑被 3 个不同会话各踩一次"记成一条带 3 局出处的教训；因此合并后 `merge.supportEpisodes ≥ 2` 必须成立，且并集里**每一个** `(episode, seq)` 都要原样保留（A6 不许退化，见 §4.2）。把它们按"重复"处理掉 = 丢掉多局印证，直接违反"反例优先/多局支撑"的晋升语义。

## 2 · 机械判据（可复算，零模型调用）

### 2.1 归一化阶梯 `normalizeForMerge(text)`

按顺序执行，**只做这些替换**：

| # | 规则 | 例 | 为什么 |
|---|---|---|---|
| 1 | 去 ANSI 控制序列 | `\u001b[31m` → 空格 | 工具输出常带颜色码，同一错误在不同终端下字节不同 |
| 2 | 路径 → `<path>` | `'D:\tmp\a.json'`、`/tmp/a.json` → `<path>` | 路径是最常见的易变部分；保留它会让"同一个坑"因目录不同而分裂 |
| 3 | 长十六进制 → `<hex>` | `bash-49fb11d400eb4696` → `bash-<hex>` | 作业 id / 提交号 / 临时哈希都是易变标识 |
| 4 | `d:d`（行:列）→ `<line:col>` | `main.go:407:25` → `main.go:<line:col>` | 编译/语法错误的位置会随代码行号漂移 |
| 5 | 日期时间 → `<ts>` | `Nov 4 06:42`、`2026-11-04T06:42:31Z` → `<ts>` | 日志前缀的时钟不是错误本身 |
| 6 | 去工具前缀 | `ok ` / `FAIL ` / `PASS ` / `FAILED ` 开头 | 同一错误在不同命令里带不同前后缀（实测存在 `ok cmd\…` 与 `cmd\…` 两种写法） |
| 7 | 压空白 + 转小写 + 截断 160 字 | — | 稳定相等判断；160 字的理由见 §2.6 |

**不做**的替换：不删数字（`exit code: 2` 有语义）、不删 CJK、不做同义词/停用词、不做词干还原。理由：删数字会把"exit 2 与 exit 1"合成一条；同义词/词干化需要词典，等于引入语义判断。

### 2.2 判等前处理：归一化阶梯（辅助，不是独立合并依据）

归一化**只用于缩短"同一口径内的判等"距离**，本身不构成一条合并判据（单独拿它当判据就是"单口径"，见 §2.3 的过合证据）。它喂给口径 C（错误类 + 前 40 码点）与 Tier 0 的"逐字相同"判定。

### 2.3 三个口径 + "≥2 口径同时命中"（核心判据）

| 口径 | 定义 | 为什么要它 |
|---|---|---|
| **A** 词面重叠 | ASCII 词集 Jaccard ≥ 0.6（小写、非字母数字切、英文词长 ≥4） | 抓"同一句英文错误、少量词不同"；对中文为主的句子几乎不生效 |
| **B** 中文重叠 | CJK 2-gram 交集 ≥ 4 | 抓"同一句中文约束/结论、换序或换虚词"；A 对中文无效，B 补位 |
| **C** 错误类 | `errorClassKey` 相同 **且** 前 40 码点相同（`errorClassKey` 取自 `src/rooms/claim.mjs` 的 `classifyErrorClass` / `errorKeyOf` 同源口径） | 抓"同一类错误 + 同一句开头"，不受长度影响 |

**合并判据：A、B、C 里至少 2 个同时命中。**

#### 为什么必须是 ≥2 个，而不是任意单个

真数据（T145 重复度体检，2026-11-04，只读）给出的三口径独立命中量：

| 口径 | 疑似重复对 | 涉及 claim | 簇 | 可合并条数 | 降幅 |
|---|---|---|---|---|---|
| A 单独 | 615 | 298（24.2%） | 98 | 200 | 16.2% |
| B 单独 | 36 | 43（3.5%） | 16 | 27 | 2.2% |
| C 单独 | 252 | 179（14.5%） | 61 | 118 | 9.6% |
| A∪B∪C（任一口径） | 817 | 400（32.5%） | 120 | 280 | 22.7% |
| **≥2 口径同时命中** | — | — | **43** | **64** | **5.2%** |

**单口径 = 过合，证据在 A 的构成里**：615 对里 **327 对只差数字/十六进制 id**（版本号 `<pkg-version>`、行号、job id），**只有 3 对是完全相同**。也就是说 A 单独作用时，它几乎只做了一件事——把"同一句话里的易变标识"抹平；这既会把真正不同的两个值（两个版本号、两个行号）并成一条，也会把"同一个坑的不同实例"与"不同坑的同一句式"混在一起。任一口径 ∪ 起来能吃下 22.7% 的库，这个量级本身就不是"去重"，而是"改写语义"。

**≥2 口径的真实产出是 43 簇 / 64 条 / 5.2%**，这才是本契约允许的**高精度种子**。它的含义是：两条 claim 必须同时满足"词面或中文高度重叠"**和**"错误类 + 开头一致"，才允许考虑合并——两个彼此独立的机械信号同时命中，才把假阳性压到可接受。

#### 合并档位（两档，其余一律不合）

| 档 | 条件 | 真数据规模 | 说明 |
|---|---|---|---|
| **Tier 0：同证据重复（无条件可合）** | 同 `kind` + 同 `scopeKey` + 所有成员的 support 都落在**同一个 `(episode, seq)`** + `validity` 相等 + `preconditions` 相等 + `counter` 全空 | **5 簇** | 一条证据被写成了多条 claim（历史遗留/重算残留）。它们没有"跨局印证"价值，合并零信息损失，是最安全的一档 |
| **Tier 1：≥2 口径命中（高精度种子）** | 同 `kind` + 同 `scopeKey` + A/B/C 至少 2 个命中 + `validity` 相等 + `preconditions` 相等 + `counter` 全空 + 非噪声 | **43 簇 / 64 条 / 5.2%** | 跨局/跨时间的"同一个坑"；合并后 support 累加（§1.3） |
| ❌ 禁止：只命中 1 个口径 | — | A 单独就有 98 簇 / 200 条 | 过合（见上：327/615 只差易变标识） |
| ❌ 禁止：A∪B∪C 任一命中即合 | — | 120 簇 / 280 条 / 22.7% | 同上，且会把不同错误类并到一起 |

**反例会怎样**：若按 A 单独合并，`version = "<pkg-version>"` 的多个版本会并成一条，正文只留最早的版本号，而"版本号本身"就是这条事实的全部信息（§8.3 已记录：此类 `fact` 的正文不含包名，版本号是唯一可核内容）——合并即制造假事实。

### 2.4 否决项（任一命中 ⇒ 不合）

| # | 否决 | 理由 |
|---|---|---|
| V1 | `scopeKey` 不同 | §1.2 |
| V2 | `kind` 不同 | §1.2 |
| V3 | `preconditions` 集合不同 | 合并会放宽适用条件；真数据里有 **11 簇**正是栽在这一项上 |
| V4 | `validity` 不同 | 两条事实断言不是同一个命题；真数据里有 **19 簇**栽在这一项上（版本号/文件路径本身就是正文，不能当「只差易变标识」合并） |
| V5 | 任一方 `counter` 非空 | 反例优先，冲突不合（§3）。T145 实测当前库 **0 簇**命中——这项现在是「空转的守卫」，但必须保留（一旦被反例触及，合并就是洗掉反例） |
| V6 | 任一方 `state ∈ {disputed, invalidated, stale}` | 同上；T145 实测 `disputed` **0 簇**，同样是空转守卫 |
| V7 | 任一方是 `class:*` | 已是聚合结果 |
| V8 | 有一方是输出噪声（§2.3 的噪声定义） | 噪声不进教训层；实测反模式池里约 10% 是命令输出而非教训 |
| V9 | 主题集非空且**交集为空** | §2.5 |

### 2.5 主题交集：本版是"否决项"，不是"合并依据"

- **现状**：`claim.threadIds` 在所有现存 claim 上都是空数组（`docs/数据契约.md` §9 写明"保留字段、无生产者"），所以"共享 ≥N 个 thread"这条判据在 claim 层**当前不可用**。硬把它写成合并依据，等于用一个恒为空的字段做判据——永远不成立或永远成立，都是假判据。
- **本契约的做法**：S2 合并**不要求**主题交集（避免假判据）；只在可选输入里接受 `topicsOf(claim)`（由 support 的 `episode` 反查 `episode.topics`），并把它当**否决项**：两边主题集都非空且交集为空 ⇒ 不合（V9）。阈值取 **≥1 个共享主题**即可，因为 claim 层没有 df 加权，多要求一个共享主题会误杀（同一坑的两次出现常常只有 1 个共同主题）。
- 真正的"按主题合流"留给 S3（大棋谱视图）：那里以 topic 为轴，`threadIds` 由 R06 产出，判据才成立。

### 2.6 时间窗

- **不设上限**：同一个坑可以隔几个月再现，按 `occurredAt` 距离设上限会把它拆成两条，正好违背"大棋谱"的初衷。
- **不设"证据不重叠"门槛**：两条 claim 的证据集若完全相同，它们不是"重复"而是"同一证据的两种断言"（§8.4 有 40 句反例），合并它们不产生任何新信息。
- 只保留一条时间规则：**合并节点的 `occurredAt = min(成员 occurredAt)`，`validFrom = occurredAt`，`validTo = null`**（合并本身不终结有效期；`validTo` 只由人纠错或核验失败写入，见 `applyAdjudications`）。
- **截断 160 字**的理由：`clip` 的现有上限是 200 字（`DEFAULT_CLAIM_OPTIONS.maxQuote`），归一正文只用于**判等/判重**，不用于展示；取 160 是让"长尾差异"（结尾附带的不同输出）不参与判等，又与 200 字展示上限留出余量。

### 2.7 哪些 kind 用哪条判据

| kind | Tier 0（同证据） | Tier 1（≥2 口径） | 说明 |
|---|---|---|---|
| `antipattern` | ✅ | ✅ A/B/C 至少 2 个 | 教训可以按「坑」合并；也是 Tier 1 的主战场（A/B/C 都是按错误正文定义的） |
| `fact` | ✅（且 `validity` 相同） | ❌ 不用 | 事实的主体是路径/版本，不是正文句子。实测按文本 Jaccard 0.9 会误并不同文件/不同包（§8.3） |
| `preference` | ✅ | ❌ 不用 | 每句用户约束都是独立的；实测 Jaccard 0.4 都无一对可合（§8.4）。Tier 1 对 preference 只会制造假合并 |
| `rule` / `pattern` | 暂不做 | ❌ | 无真实样本、无消费者，不立规则（AGENTS §2.4「指标先有消费者」同精神） |

> 注：`fact` / `preference` 的 Tier 0 只收「同一 `(episode, seq)` 写重了」的情况；它们的重复极小（实测精确重复 3 组），其余一律不合。

## 3 · 冲突：不合，改记 `contradicts` 边

矛盾判据全部机械，按顺序判，命中即停：

| # | 判据 | 判定 | 动作 |
|---|---|---|---|
| C1 | **反例冲突**：A 的 `counter` 里的 `(episode, seq)` 出现在 B 的 `support` 里（或反之） | 两条互相否定 | 不合；建 `claimEdge{kind:"contradicts", evidence:[两侧原文]}`；两条都保留（有 counter 的那条已是 `disputed`） |
| C2 | **否定极性相反**：归一正文在**剥掉否定词**（`不` / `不要` / `禁止` / `never` / `don't` / `avoid`）后相等，但一条带否定词、另一条不带 | 一条主张"要做"，一条主张"别做" | 不合；建 `contradicts`；两条并存 |
| C3 | **同主体、值互斥且非时序**：两条 `fact` 的 `validity.type` 相同、`validity.value` 不同，且 `occurredAt` 相差 < 1 小时、属于同一 episode | 同一时刻两个互斥值（多半是抽取噪声） | 不合；建 `contradicts`；交 R10 裁决，不自动选边 |
| C4 | **同一证据、相反结论**：两条 claim 的 support 完全等于对方的 counter（同一 `(episode, seq)` 既是 A 的证据又是 B 的反例） | 直接矛盾 | 不合；`contradicts`；两条都标 `disputed` 不可自动晋升 |

**明确不构成矛盾的**：

- `fact` 的 `validity.value` 随时间变化（例如同一包的两个版本字面量）——这是**时序覆盖**，不是冲突；处理方式是给较早那条写 `validTo = 较晚那条.occurredAt`（沿用 `validTo` 字段语义），两条都保留，不建 `contradicts`。
- 同一坑在不同局里的**不同错误细节**（路径/行号不同）——由 §2 归一化吸收，不构成冲突。

## 4 · 合成节点：数据结构与 A6 约束

### 4.1 字段

```js
mergedClaim = {
  id: "c-<hash8>",                 // = hash8(`merge|${kind}|${scopeKey}|${mergeKey}`)，幂等
  kind, scopeKey,                  // 与所有成员相同
  text,                            // = representative.text，逐字，不加任何前缀/拼接
  state,                           // 由 gates.allowedStates({ support: 独立局数, counter }) 决定
  support: [...],                  // 成员 support 并集，按 (episode,seq,quote) 去重，按 occurredAt 升序
  counter: [],                     // 恒空（有 counter 的不合）
  occurredAt, validFrom, validTo,  // 见 §2.6
  recordedAt,                      // = 派生时刻（不可用 Date.now 混入排序；只作第二时钟）
  validity, validityOk,            // 与成员一致
  preconditions,                   // 与成员一致（集合相等才合）
  counters: { support: <条数>, counter: 0, injections: 0, lastInjectedAt: null },
  supersedes: null,                // 保留字段不动（合流不写覆盖链，写 merge 字段）
  merge: {
    version: 1,
    key: mergeKey,                          // 判等键，可复算
    rule: "normalized-equality" | "gated-jaccard",
    members: ["c-...", ...],                // 成员 id，按 occurredAt 升序
    representative: { claimId, episode, seq, quote },  // 逐字出处
    supportEpisodes: <number>,              // 独立局数（派生）
    at: <派生时刻>,
  },
}
```

- **不加** `text` 前缀（不写"合并自 N 条"）。原因：任何前缀都会让 `text` 不再是原文，A6 的"逐字可查"就要靠"剥前缀"补救；新约定不制造这个问题。
- `merge.members` 是**可逆性的唯一依据**：成员 claim 在库里原样存在，合并节点消失后成员仍是完整的 claim。

### 4.2 A6：正文必须逐字可回溯（关键约束）

**规则**：`mergedClaim.text` 必须逐字（子串级）出现在 `merge.representative.quote` 里，且 `merge.representative` 的 `(episode, seq)` 必须同时出现在 `mergedClaim.support` 中。

**为什么必须绑 representative**：卡片渲染的出处行是 `(episode, 日期, seq N)`，而 `src/rooms/inject.mjs` 的 `entryFromClaim` / `pickSourceBySignal` 会按信号判别词从 support 里**换一条**来展示。如果合并节点的 `text` 取自 A 成员、渲染时挑了 B 成员的 support，正文就会与出处对不上——这是 A6 的实质退化。因此：

- 合并节点必须携带 `merge.representative`，渲染/校验时**以它为准**；
- 若渲染层仍按"信号词命中"挑 support，则必须保证挑中的那条 support 的 `quote` 也逐字包含 `text`；做不到时就退回 representative。
- 对历史 `class:*` 章节：正文形如 `class:<name> · <代表错误>`，前缀不是原文。**已在库里的 10 条不回溯改写**（`docs/数据契约.md` §9「只增不改」），但校验规则要显式允许"剥掉 `class:<name> · ` 前缀后逐字命中"，并把该前缀记进 `merge.prefix`。新合流节点不产生这种形态。

### 4.3 与"只增不改"的关系

- 合流**不修改成员**：`text` / `support` / `counter` / `state` / `supersedes` 一个字节都不动。
- 合流**不是覆盖**：不写 `supersedes`。`supersedes` 的语义是"新条目取代旧条目"（`docs/数据契约.md` §9），而合流是"多条并成一条视图"，语义不同，混用会让 `supersedeCoverage` 指标失真。
- 合流节点与成员**同时存在**：读侧默认读合并节点（S3），但成员始终可按 id 展开。

## 5 · 可逆性

### 5.1 从合成节点还原成员

```
members = merge.members.map(id => store.get('claims', id))
```

还原后应满足：`members` 的并集 support ⊇ `merged.support`，且每条成员的 `text` 能在自己的 support quote 里逐字找到（成员本来就满足）。**不需要**额外快照/备份：成员是原件。

### 5.2 "不合了"怎么回退

合流节点是**派生数据**，与 `ensureClassClaims` 生成的类级章节同性质（`docs/数据契约.md` §12：「无副作用：不删、不改写既有 claim」；§9：「归档每次会重写派生 claim 记录」）。因此回退只有一步：

1. 关闭 `consolidate` 开关（S2 的配置键，建议 `consolidate:false`，默认关）；
2. 重跑 `scripts/archive.mjs`（或 `cli rebuild`）——派生集合重算，合并节点不再生成；
3. 成员原样保留，`manifest.counts.claims` 回到合并前的量级。

不需要"撤销脚本"，也不存在"半合并"状态：合并节点要么整批重算，要么整批消失。

### 5.3 幂等

同一库连跑两次 archive，合并节点的 **id 集合、support 序列、text** 必须逐字节相同（id 由 `mergeKey` 决定，support 按 `(episode, seq, quote)` 排序去重）。任何一次不同，都说明判据里混入了时间/随机/Map 顺序。

## 6 · 判据与验收（未来单测直接照抄）

| # | 断言 | 判据 |
|---|---|---|
| **T1** | **A6 不退化** | ∀ 合并节点：`text`（`class:*` 剥前缀后）是 `merge.representative.quote` 的子串；全库 100%；`merge.representative.episode/seq` 在 `support` 里 |
| **T2** | **A5 不越界** | ∀ 合并节点：`scopeKey` 与所有成员逐字节相同；对全库跑 `walk` 后，渲染行里跨域条数 = 0 |
| **T3** | **可逆** | ∀ 合并节点：`merge.members` 全部可在库里取到，且成员 `text`/`support`/`counter`/`state` 与合并前快照逐字节相同；关闭开关重跑后合并节点数 = 0 |
| **T4** | **幂等** | 同一库连跑两次，合并节点 id 集合与 support 序列 JSON 序列化后相等 |
| **T5** | **有界合并、真有收益** | ① 每个合并组 `members.length ≥ 2` 且组内 `kind`/`scopeKey` 唯一；② **只许 Tier 0 / Tier 1 两档**，任何"只命中 1 个口径"的组必须为 0；③ 单 scope 合并节点数 ≤ 该 scope claim 数 × 25%（防过度合并）；④ 全库 claim 数下降 ≥ 3%（≥2 口径的种子实测 64/1232 ≈ 5.2%，留一半余量作下界）；⑤ 跨局组必须满足 `merge.supportEpisodes ≥ 2` 且并集覆盖所有成员的 `(episode, seq)` |

> T5 的 25% 是**上界保护**，不是目标值：合流的目的是"一次看一份大棋谱"，不是"把库压小"。若某天合并比例逼近 25%，说明判据漏了否决项，应先查 V3/V9。

## 7 · 明确不做的

| 不采纳 | 一句理由 |
|---|---|
| 语义向量聚类 / embedding 相似度 | 边界成文法禁止 RAG；且不可复算、不可审计，同一库两次跑可能给不同结果 |
| 模型判断"像不像" / LLM 摘要合并 | 摘要会改写原文，A6 立刻退化；模型判断不可复现，违反"计数不是打分" |
| 跨作用域合并（包括"只在 u: 层合"） | A5 是硬门槛；Q18（`crossScopeClass`）尚未裁定，合流不得先斩后奏 |
| 用 `supersedes` 表达合并 | 语义不同（覆盖 vs 并列），会污染 `supersedeCoverage` |
| 删除被合并的成员 | 只增不改、原件永不删；成员是可逆性的唯一依据 |
| 合并 `class:*` 章节 | 它已经是聚合层，再合会叠出第三层且丢类名 |
| 按时间衰减/热度决定合不合 | 衰减是排序函数，不是存留/合并函数（`方案.md` §10 不采纳清单） |

### 8.2 能合多少（三条独立路径，2026-11-04 实测）

**路径一：精确重复**（同 kind + 同 scope + 同 `text`）—— 3 组 / 6 条（占反模式 0.7%）。
**路径二：`errorKeyOf` 既有归并** —— 10 条并入既有条目（占反模式 1.2%）。
**路径三：T145 重复度体检**（`graph-reader`，只读，1232 条 claim / 34 个 `(scope,kind)` 桶）：

| 口径 | 疑似重复对 | 涉及 claim | 簇 | 可合并条数 | 降幅 |
|---|---|---|---|---|---|
| A：ASCII 词集 Jaccard ≥ 0.6 | 615 | 298（24.2%） | 98 | 200 | 16.2% |
| B：CJK 2-gram 交集 ≥ 4 | 36 | 43（3.5%） | 16 | 27 | 2.2% |
| C：`errorClassKey` 相同 + 前 40 码点相同 | 252 | 179（14.5%） | 61 | 118 | 9.6% |
| A∪B∪C（任一口径） | 817 | 400（32.5%） | 120 | 280 | 22.7% |
| **≥2 口径同时命中（本契约采用）** | — | — | **43** | **64** | **5.2%** |

- **单口径的构成**：A 的 615 对里 **327 对只差数字/十六进制 id**、**只有 3 对完全相同** ⇒ 单口径几乎只是在抹易变标识，会过合（§2.3）。
- **硬门拦截量**：**19 簇**栽在 `validity` 不等上、**另有 11 簇**栽在 `preconditions` 不等上 ⇒ 合并前必须显式检查这两项（V3/V4）。
- **跨局簇**：**57 簇**横跨 ≥2 个 episode ⇒ 合并要累加 support，不能把出处合掉（§1.3）。
- **当前空转的守卫**：`counter` 非空 **0 簇**、`state:disputed` **0 簇**（V5/V6 现在不会触发，但必须保留）。
- **最安全的真重复**：**5 簇**全簇落在同一条 `(episode, seq)` 上 ⇒ Tier 0 无条件可合。

**三条独立路径的交叉验证**：路径三的 ≥2 口径给出 64 条（5.2%），我按归一化阶梯独立跑出 46 条（占可参与池 6.3%、占全库 3.7%）——两条路径的口径不同（一条要求多信号投票，一条要求归一后相等），量级落在同一档（**≈4%–5%**），说明"高精度种子"这个规模不是某个阈值调出来的。本契约采用更严的 ≥2 口径作为 S2 的准入。

进一步按 T145 的定义独立复算三口径（同一份库，2026-11-04）：**C 口径逐位复现**（252 对 / 118 条可合并）；A 口径 600 对（T145 记 615；我用英文词长 ≥3 切分，T145 用 ≥4，差异来自这里）、B 口径 121 对（T145 记 36，差异来自中文切分颗粒度）；**≥2 口径 75 条（T145 记 64）**。C 的逐位一致说明「错误类 + 前 40 码点」这条判据本身没有实现歧义；A/B 的差异只影响候选池大小，不影响 ≥2 档的量级。本契约采用 **≥2 口径**作为 S2 的准入（64–75 条区间），单口径一律不采信。

### 8.3 反例一：`fact` 绝不能用文本相似度合并

库里 128 条 `fact` 全部带 `validity`（file 66 / version 62），同 scope 内**没有任何两条** validity 相同 —— 也就是说，按本契约它们**一条都不合**。

但若按文本 Jaccard ≥0.9 去合，会合并 **38 条**：例如 `FileNotFoundError: … '/tmp/a.json'` 与 `… '/tmp/b.json'`、`cp: cannot stat 'X'` 与 `'Y'`、同一包不同版本的 `version = "<版本>"`。这些是**不同事实**（不同文件不同包），合并即制造假事实。这是本契约禁止 `fact` 走 Tier 1（≥2 口径）的直接证据。

附带发现：版本类 `fact` 的 `text` 只有 `version = "<版本>"`，**不含包名**（包名既不在 `text` 也不在 `validity.value`）；所以连"同一包的两个版本"都无法从 claim 自身机械识别，更不能合并。

### 8.4 反例二：`support` 相同 ≠ 重复

库里有 95 组 claim 的 support 集合完全相同。逐组看：

- **60 组是 `antipattern` 与 `fact` 共享同一 `(scope, episode, seq)`** —— 同一条证据被 R09 同时写成事实与教训。按 §1.2 不合，改记 `derives` 边（另有 62 条文本同时以两种 kind 出现，基本重合）。
- **其余是 `preference`**：其中一个 `(episode, seq)` 上挂了 40 条 preference —— 那是一整条用户消息里的 40 句约束，句子各不相同。

所以"support 相同"既可能意味着"跨 kind 双记"，也可能意味着"同一句话被切成多句"；把它当合并判据会两类都判错。

### 8.5 反例三：跨作用域同名文本

有 **40 条文本**同时出现在 ≥2 个作用域（如 `SyntaxError: …`、`fatal: Needed a single revision`、`Error: web fetch failed`）。按 §1.2 一律不合、不连——这正是 A5 的检查面。

### 8.6 反例四：输出噪声

815 条反模式里有 **81 条**不是"坑"而是命令输出（`ℹ tests …` 汇总行、`total 83 drwx…` 的 `ls` 输出、纯分隔线、`[exit code: 0]` 的"成功"结果）。本契约把它们排除在合并之外（§2.3 V8）；但它们的**抽取层**问题（为什么会被写成 antipattern）应另案由 R09 处理，合流只负责"不放大"。

## 9 · 待裁定 / 不确定（请主人或 Lead 拍板）

1. **`text` 是否允许机械前缀**：本契约选"新节点一律无前缀"（A6 最省事），但历史 `class:*` 已有前缀。若坚持"所有合并节点都带 `class:`/`merge:` 标签在正文里"，A6 的校验就要写"剥前缀"规则，且前缀本身会进模型上下文（+token）。**默认推荐：无前缀，标签进字段。**
2. **合并节点是否参与注入计数**：`counters.injections` 记在成员还是合并节点上，会影响 A2b/H1 的分母口径。**默认推荐：记在渲染出来的那条上（合并节点），成员不记。**
3. **独立局数的字段位置**：本契约放 `merge.supportEpisodes`（派生），不动 `counters.support`。若 `方案.md` §5.1 的晋升阶梯未来要读它，需要在 `gates.allowedStates` 里显式接。**默认推荐：先派生、不接闸。**
4. **跨作用域同名文本（40 条）**：是否要在 `u:` 层做"只读对照视图"（不合并、只在注入时提示"该坑在其他项目也出现过"）？这涉及 Q18（`crossScopeClass`）的边界。**默认推荐：保持 0 越界，不做。**
5. **时间窗**：本契约不设上限。若主人希望"只合最近 N 天的坑"，需要明确 N 与理由（会把老坑拆出去，与"大棋谱"目标相反）。**默认推荐：不设。**
6. **S2 与 S3 的边界**：本契约只定义"条目层合流"；"一份大棋谱"的载体（scope 级合并视图 + 18×18 邻域）属于 S3，`方案.md` §14.4 已列顺序。**需要确认：S3 的节点是否复用本契约的 `merge` 字段，还是另开 `kifu` 节点类型。**
