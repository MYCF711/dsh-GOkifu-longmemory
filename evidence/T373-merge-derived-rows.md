# T373 · ④b 那 22 行「丢内容」：**源库自己的合并节点行**不是内容

> 2026-11-09 · 接 T372（T187 验收时发现 ④b FAIL：丢行 22 行 / 18 组，且与基线逐项相同 ⇒ 既有问题）。

## 一、病灶

④b 的判据是「源卡每一行，要么在影卡同 `claimId` 出现，要么被某个**渲染中的合并节点**的 `merge.members` 覆盖」。
问题在于：**源库里已经有 39 个合并节点**（早前一次合流写进了真库）。于是

- 源卡会为这些节点渲染出行（它们就是普通 claim 记录）；
- 影卡**有意不为合并节点成行**（T187 的全部意义）；
- 判据里没人说"源侧的合并节点行不算内容" ⇒ 一律记 `lostRows`。

## 二、实测（真库 80 组，逐行归类）

```
丢失行合计 14
  其中「源库里本来就是合并节点」 14     ← 全部
  其中「本组成员行」              0
  其余                            0
```

（14 vs 报告里的 22：我的探针按前 80 个合并节点遍历、卡片预算口径略有差异；**归类是无歧义的**。）
样例：`c-1f1ce0f6`、`c-41157b78` —— 两者在源库里都带 `merge` 字段。

**合并节点的「成员」才是内容**，它们由影卡里的合并节点代表；节点行本身是派生物。

## 三、改法

`sampleMergeGroups()` 先取一次**源库侧的合并节点 id 集合**（`source.list('claims')` 里带 `merge` 的），
④b 的分母把它排除；同时单独记 `derivedRowSkipped`（不静默吞掉，报告里看得到）。

```js
if (sourceMergeIds.has(id)) return false;   // 派生物，不是内容
```

## 六、边界（这次是"改判据"，所以要说清）

- 这一刀**没有**让卡片少丢任何真内容：它只是把「源侧派生物」从分母里拿掉；
- ② 号断言专门防"过滤把真问题一起放过"—— 普通行丢了照样红；
- 若将来源库侧不再存合并节点（例如改判据前先清空），这个过滤自然失效、也不会误伤。
