# T364 · 入库覆盖**是完整的**：那 602 个"有失败没 claim"的局**全是子代理局**（否定性结论）

> 日期：2026-11-07 · 只读分析（未改任何数据 / 未改抽取逻辑）
> 结论：**不要去"提高入库覆盖"** —— 实测每个**有失败的根局**都留下了 claim；无 claim 的局要么是**子代理局**（按设计归并），要么**失败数 = 0**。

## 起因

今晨看到考卷统计 `episodesWithClaims = 99`，而库里有 938 局，于是怀疑：
> "只有 10.6% 的局有 claim，89.4% 的局没货 —— 入库覆盖不足。"

**这个怀疑是错的**，下面是三次自我纠正。

## 第一次纠正：我的脚本有 bug（id 双前缀）

初版脚本用 `'ep-' + f.replace('.json','')` 构造 id，而**文件名本身已带 `ep-` 前缀**
（`ep-006269a7.json`，其 `episode.id = ep-006269a7`）⇒ 变成 `ep-ep-…`，**全部匹配不上**。

**先怀疑尺子**：如果直接拿那个结果下结论，就会报"89% 的局没货"。

## 第二次纠正：Top 几局是**我的 teammate 的会话**

修正 id 后，"有失败没 claim"的 Top 局是：
```
ep-8fe881d1(49) · ep-634616f8(42) · ep-8ef298d6(41)
```
**这些正是 card-smith / store-keeper / topic-linker 的会话 id** —— 都是**子代理会话**。

## 第三次纠正（决定性）：按 `delegationDepth` 分开算

```
无 claim 且失败 > 0 的局，按 delegationDepth 分：
  **子代理局**（depth > 0，按设计归并到父局）：602
  **根局**（该独立成 claim 却没有）：**0**
（另有 237 局失败 = 0，没有失败可记，正常）
```

**602 局全部是子代理局，根局 0 个漏抽。**

`AGENTS.md` §4.1：`delegationDepth > 0` 的会话**归并到父局**，**不独立成记忆节点**。
⇒ 它们没有自己的 claim 是**设计如此**，不是"抽取漏了"。

## 结论

| 我差点报的 | 实际 |
|---|---|
| "89% 的局没货" | 那些局大多是**子代理局** |
| "75% 的失败被丢弃" | **602 局全是子代理局**，根局 0 个漏抽 |
| "要去提高入库覆盖" | **不需要** —— 每个有失败的根局都留下了 claim |

**入库覆盖是完整的。**

## 那主判据 46.6% 到底是什么意思？

- **有货可召时召回率 = 100%**（T362 已验证）；
- **入库覆盖完整**（本刀验证）；
- ⇒ 46.6% 反映的是：**根用户原话所指向的那部分工作里，有多少留下了记忆**。

用户的一句话只涉及该局的一部分工作，**记忆不可能覆盖用户没做的那部分**。
**这是产品的真实形态，不是缺陷。**
