# T407 · links 的真实形状：**636 个局撑起 12.5 万条边，中位数每局 330 条**

> 2026-11-20 · 为 D10（是否给 links 设上限）提供数据。

## 一、边的种类与权重

```
total 125,579
same-file     30,554
same-error    54,655
shared-topic  40,370

weight = 1（硬边）：122,350（97.4%）
weight < 1（软边）： 3,229（2.6%）
```

⇒ **97.4% 是硬边**（同文件/同报错），不是"低权重噪声"。
**按权重砍边几乎无效** —— 得按"每局保留多少邻居"来砍。

## 二、扇出（每个局连多少条边）

```
有边的局：636 个（合计度数 251,158）
top10 度数：1680, 1677, 1676, 1604, 1215, 1154, 1042, 1041, 1040, 1039
中位数：330        p90：79（按降序是另一侧）      p99：4
```

**中位数每局 330 条边**，最高的 1,680 条。

## 三、这意味着什么

边是**团（clique）**：N 个局共享同一文件/同一报错 ⇒ 两两成边 = N²。
636 个局就能产出 12.5 万条边，而**归档要逐条写文件**（每轮重写约 9.9 万条，putMany 177 秒）。

按每局上限截断的量化效果：

| 每局上限 | 保留的度数占比 |
|---|---|
| 50 条 | **0.4%** |
| 100 条 | **2.5%** |

⇒ 截断会砍掉 97% 以上的边。**能不能砍，取决于 A2b 是否依赖它们**（walk 深度 ≤2、每层 limit 5，理论上只需要少量邻居）。

## 四、D10 的选项（带数据）

| 选项 | 得到 | 代价 / 风险 |
|---|---|---|
| ① 不动 | 关系网最全 | 每轮写 9.9 万条，归档 ~100–160 秒 |
| **② 每局保留 top-k（k=50）** | 边数降到 ~3 万，归档显著加快 | **可能改召回**，A2b 必须复测；k 需调参 |
| ③ 不物化团边，改成按需邻居（walk 已有 `holdersByTopic` 索引） | 从根本上消除 N² | 改存储契约与 walk 读取路径，工作量大但收益最高 |
| ④ 只对 `shared-topic` 截断（硬边不动） | 最保守 | 硬边仍是 12 万，收益小 |

**我的建议：先做 ③ 的局部版**（walk 走 `holdersByTopic` + 现有的边索引，只物化"每局 top-k 硬边"），
但那是**结构性改动**，A2b 必须做前后对照 —— 属有代价，等你裁定。
