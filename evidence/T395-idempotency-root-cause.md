# T395 · 「连跑两次不幂等」的真因：**每局新增都会改掉所有 topic 的 `idfNorm`**

> 2026-11-20 · 承接 T394 里我标出的「run2 反而写了 8,960 个 topics」。

## 一、先排除的两件事（都实测过）

1. **`deriveStore` 本身是确定性的**：同一份 episodes、同一个 `at`，连算两次
   `topics 8960 / links 44729 / threads 2066`，**内容差异 0**；
2. **与 `at` 无关**：`at=1_700_000_000_000` 与 `at=1_700_000_100_000` 两次派生，**内容差异 0**。

## 二、真因（读一条记录就看到了）

```json
{"df":1,"episodes":["ep-b7a6819f"],"idfNorm":0.9321695359420343,
 "key":"@snowluma/core","kind":"dependency","lastSeenAt":null,
 "_store":{"createdAt":…,"updatedAt":…}}
```

`topic.idfNorm` 是**按全库局数归一化**的值（IDF）。
⇒ **每新增一局，全库的 `idfNorm` 都会变** ⇒ 9,000 个 topic 的记录内容全都变 ⇒ 全量重写。

实测两轮之间确实有新局进来：`run1 新增 episodes 424`、`run2 新增 episodes 125`。

**所以"不幂等"不是 bug，是「分母在变」的必然结果** —— 但它造成了 **每轮 9,000 次 topic 写入 + 1,000 次 link 写入**，
也就是当前剩下的 51.8 秒（topics）+ 36.3 秒（links）的主因。

**这也修正了我上一轮的判断**（我当时写"派生结果在两次之间发生漂移"，那是错的）。

## 三、要不要改：属**有代价**的优化，需主人裁定（D8）

| 选项 | 做法 | 得到 | 代价 |
|---|---|---|---|
| ① 不改（默认） | 保持 `idfNorm` 落盘 | 现状 | 每轮全量重写 topics |
| **② 不落盘、读时算** | topic 只存 `df`，`idfNorm = f(df, 全库局数)` 在读取/渲染时计算 | 写入量降一个数量级 | 改存储契约（字段消失/改名），所有读它的地方（walk/index）要同步改 |
| ③ 量化 | `idfNorm` 保留 2 位小数 | 部分局数变化不再触发重写 | 精度损失，可能影响排序 |
| ④ 只写变化的 | 比较时忽略 `idfNorm`（视为派生视图） | 不改字段 | **语义变化**：磁盘上的值与最新一致，刷新不落盘 |

**我的建议：②**（把派生值从存储里拿出来，是正确的设计），但它动契约，按规矩等你裁定。
在此之前不改 —— 现有实现正确，只是写放大。

## 四、当前归档性能账（最新）

| 阶段 | 耗时 |
|---|---|
| 读日志 + 构建 | ~19 秒 |
| 权威写入（episodes/claims） | ~20–30 秒（因新局数而异） |
| derive | 1.5 秒 |
| 写 topics | ~52 秒 ← **idfNorm churn** |
| 写 links | ~36 秒 |
| manifest | 8.5 秒 |
| verify | 8.5 秒 |
| **合计** | **127–191 秒**（样本：127 / 191 / 295 / 556） |

**波动很大**（127–556 秒），主要随"这期间宿主新写了多少会话"变化。
