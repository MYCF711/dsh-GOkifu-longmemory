# T338 · F3 恢复条件的瓶颈诊断 —— 是「主体抽不出」，不是「恢复判据太严」

> 复算：`tmp/recovery-ab.mjs`（A/B 对照，20 局 / 1575 条失败）。

## 0 · 一句话

**F3 恢复覆盖率 4.51% 的根因是「86.73% 的失败没有文件路径主体」，
而不是「恢复判据太严」—— 把恢复信号放宽（接 `recoverySignalOf`）实测新增 0，接了也白接。**

## 2 · A/B 对照：放宽恢复信号有没有用？

判据对照（对同主体约束下的恢复判定）：
- **A 现判据**：`findRecovery` —— 同主体 **且 exit 0**。
- **B 宽判据**：同主体 **且（exit 0 或 `recoverySignalOf`：tests-pass / build-success / git-clean）**。

```
总失败 1575 · 无主体 1366（86.73%）· 有主体 209（13.27%）
A 抓到 71 · B 抓到 71 · B 新增 0 · 新增信号分布 {}
A 覆盖率 4.51% · B 覆盖率 4.51%（一字不变）
```

**结论**：`recoverySignalOf`（测试通过/构建成功/git-clean）在同主体约束下**从不额外命中** ——
这些信号本身**不带文件主体**，所以要么不出现、要么出现的地方已经是 exit 0。
**接进 `findRecovery` 无用**（且若无主体约束地接，会引入"任意成功凑数"的假阳性，知识库 54 / T311b）。

## 3 · 真瓶颈：86.73% 的失败没有文件路径主体

`subjectOf` 只认**带扩展名的文件路径**。但绝大多数失败是**命令级/运行时错误**，正文没有文件路径：
`Error: unknown job bash-…`、`Error: ENOENT…`（有的有路径有的没有）、独占 `[exit code: 1]`、`npm ERR!…`。
`findRecovery` 的硬规则「**没有主体就没有恢复**」（T311b，防凑数）对它们直接放弃。

**为什么不能拿「错误行前 40 字」当兜底主体**（costOf 的 retry 是这么认重试的）：
恢复 = 后续**成功**事件，而成功事件**不会重述那 40 字错误文本** ⇒「同主体（前40字）+ exit 0」永远不成立。
该兜底对 retry（同错误再现）有效，对恢复（错误消失）无效。

## 4 · 下一刀方向（已诊断清楚，未实施）

**命令主体恢复**：无路径失败大多是「某条命令跑挂了」，其主体应是**触发它的那条命令**，
不是错误文本里的文件路径。路线：
1. 失败事件（`tool/result` 的错误输出）**回溯关联到 `tool/call`**，取**命令主体**（如 `node scripts/check.mjs`）。
2. 恢复 = 后续**同一命令** exit 0（命令级 same-subject-exit-0）。
3. 保留主体约束（命令即主体，不凑数）；重跑本 A/B 看覆盖率能否从 4.51% 显著抬升。

**前置**：确认 `tool/result` ↔ `tool/call` 的关联字段（call id / 命令回指）在事件里可用。
若关联可得，这一刀机械、可验收；若不可得，则命令级恢复同样缺证据，需另议。
