# T59 · 并发跑全量会卡死：实测串行不复现，发版改成「拿不到计数就串行重跑」

> 2026-11-09 · 接 T56（有界超时）。T56 只是"别无限等"，本轮补"卡死了怎么把发版走完"。

## 一、实测面（本机，2026-11-09）

| 观察 | 数据 |
|---|---|
| 并发跑卡死 | **5 次**（03:47 / 03:59 / 04:10 / 10:14 / 更早一次），日志停住、某个隔离子进程**内核态 CPU 持续增长**（如 20 秒采样 238s→364s）、父进程无任何输出，最长干等 25 分钟 |
| 紧接重跑 | 几乎总是通过（10:14 卡死 → 10:16 重跑 **148.5 秒全绿**） |
| **串行**（`--test-concurrency=1`） | **1246 条 / 1240 pass / 0 fail / 6 skip / 252.9 秒 / 未复现** |

结论只能到这一步：**并发下会卡、串行下这次没卡**。不宣称"串行不会卡"（一次样本）。

## 二、改法（重试，不是根治）

`release.mjs` 的 `collectTrackedTestCounts`：

```
并发跑（默认并发）→ 解析 ℹ tests/pass/fail/skipped
  ├─ 解析到了 ⇒ 照旧（有红用例也照旧，标 failed）
  └─ 解析不到（卡死被杀 / 半截输出）⇒ **串行重跑一次**（--test-concurrency=1）
        ├─ 解析到了 ⇒ 用这份计数，标 retriedSerially（台账照常同步）
        └─ 还是解析不到 ⇒ 抛原错
```

为什么按"拿不到计数"而不是按退出码判：**有红用例时 execFile 也会抛错**，但 stdout 里仍有计数 ——
那种情况必须照旧判红，绝不能因为"报错"就重试把它洗绿。

## 三、验收

```
node --test test/release-ledger.test.mjs → 20/20
  ✔ T59 第一次拿不到计数 ⇒ 第二次必须带 --test-concurrency=1，并标 retriedSerially
  ✔ T56 那条仍绿（正常路径的 argv 不变：['--test','--test-timeout=240000', ...files]）
```

## 四、边界（说清）

- **根因未定位**：隔离子进程 argv 里不带文件名，日志是完成序而非派发序，靠现有手段分不出是哪个测试文件。
  下一步的正经挖法是 `--test-concurrency=1` 跑并观察是否能在串行下复现（本轮一次过，说明可能真跟并发/争用有关）。
- **重试会让最坏耗时翻倍**（并发卡满 240 秒 + 串行 ~253 秒 ≈ 8 分钟）——换来的是"不被一次偶发卡死卡住发版"。
- **只改 `release.mjs`**：`ledger-sync` / `ledger-check` 的同类调用被口径闸逐字符钉死，要改得三处一起动。
