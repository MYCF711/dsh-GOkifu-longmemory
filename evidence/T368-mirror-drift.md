# T368 · 影库「不一致」必须分得清：是**漏了**，还是**源库在长**

> 2026-11-09 · 起于一次真实误判。

## 一、我是怎么踩进去的

为了量 T187 的「可折组」，我按 `consolidate-apply --all` 建了一个影库，再看它的自查行：

```
| claims | 2671+66 | 2704 ❌ | 2048 | 623 |
逐 kind 一致：否（不一致：episodes, topics, claims）· 镜像耗时 208.5 s
```

但源库自己的 listing 明明一致：

```
bundle 路径 episodes 1908 · 逐文件 1908
bundle 路径 topics   5009 · 逐文件 5009
```

影库：`episodes 1654`、`topics 4417` —— 正好是**会话开始那次**的数（1654 局 / 4417 主题）。

**结论**：镜像没漏，是**源库在镜像那 208 秒里长大了**（宿主还在跑，会话一结束就归档）。
而旧实现只在**结束时**读 `src.counts()` 去比影库 ⇒ 必然报「不一致」。

## 二、改法

`mirrorAll()` 现在拍**两张快照**：

| 变量 | 什么时候读 | 用途 |
|---|---|---|
| `beforeCounts` | 复制**之前** | 影库对应的就是它 ⇒ 一致性以它为准 |
| `sourceCounts` | 复制**之后** | 只用来判「源库有没有动」 |
| `drift` | 上面两个的差 | 报告里单列一行，不再冒充「不一致」 |

报告多一行：

```
⚠ 源库在镜像期间变化（影库对应的是开始时快照）：episodes 1654→1908 · topics 4417→5009
```

## 三、验收

```
node --test test/t368-mirror-drift.test.mjs → 2/2
  ✔ ① 源库在镜像期间长大 ⇒ 报 drift，且**不算**不一致（expected 基于开始时快照）
  ✔ ② 源库没变但影库少了 ⇒ 仍报不一致（真漏必须红）
node --test "test/*.test.mjs" → 1290 条 / 1284 pass / 0 fail / 6 skip
```

## 四、为什么值得单独一刀

这个误判会直接污染下游结论：

- `merge-acceptance` 的 ④a/④b（影库 ≤ 源库行数）拿两个**不同数据集**在比 ⇒ 会凭空长出「⚠ 反增」；
  我这次就看到 2 组「反增」（`c-f6285fff 10→11`、`c-fbdac848 6→8`），**但那可能是假象**；
- 任何"影库比源库少 N 条"的告警，只要源库在动，就分不清是漏还是长。

所以：**先让工具说真话，再去量指标**。
