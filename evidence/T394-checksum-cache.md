# T394 · checksum 缓存：manifest 36.6→8.5 秒、verify 32.1→8.5 秒

> 2026-11-20 · 承接 T392/T393。归档全链 138 → **127 秒**（另有一次 295 秒的异常样本，见下）。

## 一、根因

`snapshot()` 对 **63,818 个文件**逐个 `readFileSync` + `sha256`。而 `writeManifest()` 与 `verify()`
**各调一次** ⇒ 两次全量读盘 + 哈希（实测 36.6 秒 + 32.1 秒）。

## 二、修复

`checksumOf(abs, rel)`：按 `(mtimeMs, size)` 命中就复用上次 sha256，只对变化的文件重算；
缓存落盘 `<root>/.cache/checksums.json`，跨进程复用。

**语义不变**：sha256 仍是文件内容的哈希，内容变 ⇒ mtime/size 必变 ⇒ 重算。

## 三、实测

| 阶段 | 修复前 | 修复后 |
|---|---|---|
| `writeManifest` | 36.6 秒 | **8.5 秒** |
| `verify` | 32.1 秒 | **8.5 秒** |
| 全链（第二次跑，稳态） | 138 秒 | **127 秒** |

## 四、⚠ 两个必须说清的问题

### ① 有一次 295 秒的异常样本
修复后**第一次**跑是 295 秒，卡在 `after-topics`（权威写入阶段 250 秒）。
同一份代码第二次跑是 127 秒。差异来源未定位 —— 可能是首次填充 checksum 缓存 + 大量 episode 变更。
**不能把 127 秒当成稳定值**，还需要多次采样。

### ② 两次连跑的写入量**不是幂等的**

```
run1: added 741   · topics 写入 0    · links 写入 0
run2: added 13750 · topics 写入 8960 · links 写入 4335
```

**第二次跑反而写了更多**（8,960 个 topics + 4,335 个 links）。
这说明派生结果在两次之间发生了漂移（或 `deriveStore` 的输入不完全相同）。

⇒ **goal 里「连跑两次第二次 ≤60 秒且 manifest 逐字节不变」这条判据，当前不满足**，
且原因不是性能而是**幂等性**。这是比性能更值得先查的问题。

## 五、下一步

1. **先查幂等性**：为什么 run2 会重写 8,960 个 topics？对比 run1/run2 的 `derivedFromStore` 输出差异；
2. 再继续压时间（目标 ≤60 秒）：剩余大头是 topics/links 的写入（51.8 + 36.3 秒）。

**在幂等性查清之前，不宣称"归档已达标"。**
