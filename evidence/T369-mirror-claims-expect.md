# T369 · 「claims 不一致」的第二个误区：按**组数**算新节点

> 2026-11-09 · 接 T368（同一个自查行的第二处误报）。T368 修的是"源库在长"，这一刀修"公式本身错了"。

## 一、读数

安静窗口里重建影库（源库这次没动，`drift` 为空）：

```
| claims | 2671+73 | 2712 ❌ | 30 | 2641 |
逐 kind 一致：否（不一致：claims） · 镜像耗时 230.2 s
```

其余 kind 全对，只有 claims 差 32。逐文件数一遍：

```
源 claims 2671 · 影 claims 2712 · 影多出 41
```

## 二、真因：源库里**已经有合并节点**

```
源库 claims 2671 · 其中带 merge 字段（合并节点） 39
```

本轮 73 个组里，**32 个的合并 id 在源库里已经存在**（早前一次合流的产物，id 由成员列表决定 ⇒ 重复合流得到同一个 id）。
所以影库只会多出 `73 − 32 = 41` 条 —— **镜像一条没漏**，是公式写死了「源库 + 组数」。

## 三、改法

不再数"组数"，直接数 **id 差集**：

```
addedIds = 影库 claims id − 源库 claims id        ← 真正写进去的新节点
expected.claims = 源库 claims + addedIds
```

同时把三个数分开记，便于看出是「重复合流」而不是「漏镜像」：
`extraClaims`（实际新增）· `groupCount`（组数）· `mergedAlreadyInSource`（已存在的合并节点数）。

按新口径复算这次：`2671 + 41 = 2712` = 影库实际条数 ✅。

## 四、验收

```
node --test test/t369-mirror-claims-expect.test.mjs → 2/2
  ✔ ① 部分合并 id 已在源库 ⇒ 按 id 差集算，报「一致」（extraClaims=3 ≠ groupCount=73）
  ✔ ② 影库真少一条 ⇒ 仍报不一致（真漏必须红）
node --test "test/*.test.mjs" → 1292 条 / 1286 pass / 0 fail / 6 skip
```

## 五、这两刀合起来说明什么

同一个自查行，两天里连着两个误区：

| 现象 | 误区 | 真因 |
|---|---|---|
| 「不一致：episodes, topics, claims」 | 以为**镜像漏了** | 源库在 208 秒里长大了（T368） |
| 「不一致：claims」 | 以为**镜像漏了** | 公式按组数算，而源库已有合并节点（T369） |

共同点：**自查行的数字没人对它本身做验证**。所以现在这行同时给出 `drift` / `extraClaims` /
`mergedAlreadyInSource` —— 让"不一致"三个字能被解释，而不是让人再去猜。
